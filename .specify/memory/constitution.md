# ML-SIEMv2 Constitution

## Core Principles

### I. Вертикальные срезы

- Каждая фича (спецификация в `specs/`) ДОЛЖНА заканчиваться работающим сквозным результатом,
  который можно запустить и показать: данные на входе → видимый результат на выходе.
- Запрещено планировать работу «слоями» (сначала все модели, потом вся инфраструктура).
- Инфраструктура — логирование, мониторинг, Docker, CI — наращивается внутри той фичи, которой
  она нужна, а не выносится в отдельные фазы «на потом».
- Первые срезы: пайплайн данных (PCAP → размеченные потоки → разбиение и отчёт о качестве),
  затем минимальная цепочка «детектор → вердикт → инцидент → SOAR → API». Остальное
  добавляется к работающей цепочке. Подготовка данных под конкретную модель (окна,
  нормализация) относится к фиче, где эта модель выбирается.

**Почему:** в v1 план из 22 фаз шёл слоями; через много недель работала только ML-часть,
а показать SIEM целиком было нечего.

### II. Единство признаков (train = serve)

- Признаки для обучения и для работы на живом трафике ДОЛЖНЫ вычисляться одним и тем же кодом
  с одной и той же конфигурацией (единый flow-экстрактор на базе nfstream).
- Любая предобработка (нормализация, кодирование, окна) сохраняется как артефакт вместе
  с моделью и переиспользуется при инференсе, а не пишется заново.
- Изменение схемы признаков требует версии схемы и переобучения зависимых моделей.

**Почему:** расхождение признаков между обучением и работой незаметно ломает детекцию,
и метрики на тесте перестают что-либо значить.

### III. Честная оценка моделей (NON-NEGOTIABLE)

- Основная метрика — PR-AUC (по классам и macro); ROC-AUC и accuracy — только как
  дополнительные. Порог срабатывания выбирается на валидации, не на тесте.
- Разбиение train/val/test — по времени (или по захватам/хостам), без случайного перемешивания
  окон из одной сессии. Утечка между выборками считается багом.
- Каждый заметный результат ДОЛЖЕН пройти проверку на артефакты датасета: не выучила ли модель
  признак генератора, IP, время или порт вместо самой атаки.
- Результаты фиксируются в MLflow вместе с версией данных, конфигом и сидом.

**Почему:** в v1 автоэнкодер показал ROC-AUC 0.98 на UNSW-NB15, но цифра частично завышена:
нормальный трафик и атаки там сгенерированы разными инструментами.

### IV. Решения по детекции — через эксперимент

- Архитектура детекции в v2 пересматривается; архитектуры v1 не переносятся по умолчанию.
- Выбор подхода или модели ДОЛЖЕН опираться на сравнение с простым бейзлайном
  (например, градиентный бустинг или правила) на тех же данных и сплитах.
- Усложнение (новый эксперт, ансамбль, мета-слой) принимается, только если даёт измеримый
  прирост по метрикам принципа III; решение и цифры записываются в журнал.

**Почему:** в v1 Flow CNN+LSTM упёрся в macro PR-AUC 0.443 — сложная модель без сравнения
с бейзлайном не показывает, есть ли от неё польза.

### V. Безопасный SOAR с человеком в контуре

- Логика реагирования детерминированная: плейбуки на правилах, один и тот же инцидент →
  одно и то же предложенное действие.
- Все действия (блокировка IP, изоляция хоста и т. п.) только симулируются и журналируются;
  реальные изменения сети или хостов запрещены.
- Действие выполняется только после подтверждения аналитиком; каждое решение и его автор
  сохраняются в аудит-журнале.

**Почему:** нейросети ошибаются, и автоматическая реакция на ложное срабатывание опаснее,
чем пропущенный алерт в учебном проекте.

### VI. Воспроизводимость и понятный код

- Данные и модели версионируются (DVC), эксперименты — в MLflow, сиды фиксированы.
- К коду пишутся тесты; фича не считается готовой, пока её тесты не проходят.
- Комментарии — на русском, подробные там, где логика неочевидна: объясняют «почему», а не
  пересказывают код. Очевидное не комментируется.
- После каждого рабочего захода дописывается `docs/JOURNAL.md`: что сделано, что решено,
  с какими цифрами.

**Почему:** проект — портфолио; владелец должен уметь объяснить любое решение, а через месяц
вернуться к коду и понять его.

### VII. Прозрачное авторство

- Единственный автор коммитов — владелец репозитория, под его git-профилем.
- В сообщения коммитов и PR не добавляются трейлеры соавторства; локальные настройки
  инструментов разработки не попадают в репозиторий (контролируется `.gitignore`).
- Перед каждым пушем проверяется, что в коммит не попали служебные и локальные файлы.

**Почему:** репозиторий — часть резюме, и его история должна отражать работу владельца.

## Объём и ограничения среды

**Ядро v2 (обязательно):**
- NIDS: детекция атак по сетевому трафику.
- Сквозная цепочка: детекция → инцидент → SOAR → API.
- Веб-интерфейс аналитика (SOC-консоль).
- Демо-стенд на Hyper-V (наблюдатель + атакующая ВМ + ВМ-жертва) — ближе к концу ядра;
  служит для живого демо и сбора собственной «нормы».

**Вне ядра (отдельные спецификации после ядра):** HIDS на Sysmon, развёртывание в minikube.

**Данные:** переиспользуются размеченные датасеты v1 (UNSW-NB15, CTU-13, CSIC) и сырые PCAP;
код пайплайна пишется заново по спецификации.

**Среда:** Windows 11, RTX 3060 Ti (8 ГБ VRAM), 16 ГБ RAM, Python 3.11. Модели и батчи
ДОЛЖНЫ помещаться в 8 ГБ VRAM; обработка больших PCAP — потоково или частями, чтобы
укладываться в 16 ГБ RAM. Docker и WSL2 пока не установлены: фича, которая их требует,
явно указывает это в плане как предварительное условие.

## Процесс разработки и контроль качества

- Порядок работы над фичей: specify → (clarify) → plan → tasks → (analyze) → implement →
  converge. Код без спецификации и плана не пишется, кроме мелких правок и багфиксов.
- Шаг plan ДОЛЖЕН содержать проверку на соответствие этой конституции (Constitution Check);
  отступления записываются с обоснованием в раздел Complexity Tracking.
- Критерии готовности фичи: сквозной сценарий из спецификации запускается; тесты проходят;
  метрики (если есть ML) посчитаны по принципу III и записаны; журнал обновлён.
- Язык спецификаций, планов, документации и комментариев — русский; идентификаторы в коде —
  английские.

## Governance

- Конституция имеет приоритет над остальными документами проекта (планы, спецификации,
  README). При противоречии правится документ, а не игнорируется принцип.
- Поправки вносятся через `/speckit-constitution` с записью причины в Sync Impact Report
  и в `docs/JOURNAL.md`.
- Версионирование — семантическое: MAJOR — удаление или переопределение принципа;
  MINOR — новый принцип или раздел, существенное расширение; PATCH — уточнения формулировок.
- Соответствие проверяется на шагах plan (Constitution Check), analyze и converge каждой фичи.
