# Research: Сквозная цепочка «детекция → инцидент → реагирование → API» (002)

Решения фазы 0. Формат: решение → почему → что ещё рассматривали.

## R1. Кандидаты-детекторы

- **Решение**: два кандидата плюс тривиальная базовая линия.
  - `logreg` — мультиклассовая логистическая регрессия (scikit-learn) на признаках после
    `log1p` для счётчиков/байтов/длительностей и стандартизации. Это «простой бейзлайн»
    конституции (принцип IV).
  - `lgbm` — градиентный бустинг LightGBM, мультиклассовый, на сырых признаках.
  - `prior` — предсказание долями классов из train; не кандидат, а нижняя граница для SC-001
    («выше угадывания по доле классов»).
  Классы: `benign` + 9 классов атак UNSW-NB15. Веса классов — `balanced` у обоих кандидатов
  (классы от 118 до 1.36 млн примеров в train; без весов редкие классы модель просто игнорирует).
- **Почему**: бустинг — сильный и быстрый стандарт для табличных признаков потоков, работает
  на CPU и за минуты обучается на 1.4 млн строк; логрег — понятный, воспроизводимый, объяснимый
  бейзлайн. Вместе они честно отвечают на вопрос «нужна ли сложная модель».
- **Альтернативы**: простая нейросеть (MLP) — отложена: в v1 Flow CNN+LSTM дал macro PR-AUC
  0.443, и без сравнения с бустингом непонятно, была ли от неё польза; её можно добавить третьим
  кандидатом в следующей фиче тем же механизмом. Random Forest — медленнее бустинга на 1.4 млн
  строк при сходном качестве. XGBoost/CatBoost — равноценны LightGBM, выбран один.

## R2. Признаки и предобработка

- **Решение**: вход — ровно 58 полей группы `feature` схемы 001 (`SCHEMA.feature_columns()`),
  порядок фиксирован схемой. Пропуски → 0 (в выходе nfstream их практически нет, правило явное).
  Предобработка входит в артефакт модели (`sklearn.Pipeline`): у `logreg` — `log1p` + `StandardScaler`,
  у `lgbm` — ничего. Поля `dpi` не подаются (FR-004): аудит 001 пометил `requested_server_name`
  как dangerous на `unsw_time`.
- **Почему**: train = serve (принцип II) — одна и та же предобработка сохраняется и применяется
  при инференсе; список полей берётся из схемы, а не пишется руками.
- **Альтернативы**: `protocol` как категориальный признак — у LightGBM возможно, но для
  сравнимости с логрегом оставлен числовым; вернуться к этому можно отдельным экспериментом.

## R3. Порог, скор атаки и предсказанный класс

- **Решение**: скор атаки = `1 − P(benign)`. Порог выбирается на val как максимум F1 бинарной
  задачи «атака / не атака»; при равенстве — больший порог (меньше ложных алертов). Класс алерта —
  самый вероятный класс среди атакующих. PR-AUC по классам — one-vs-rest по вероятностям классов
  (`average_precision_score`); macro — среднее по классам, у которых есть примеры в оцениваемой
  части (класс без примеров помечается «нет примеров», edge case спеки).
- **Почему**: порог нужен именно для решения «алерт / не алерт», а его качество — бинарное;
  F1 — компромисс, понятный аналитику (и ложные тревоги, и пропуски). Test не участвует в выборе.
- **Альтернативы**: порог под заданную точность (например, 0.9) — разумно в продакшене, но
  требует ещё одного «волшебного числа»; можно добавить позже как параметр конфига.

## R4. Правило выбора победителя

- **Решение**: победитель — кандидат с наибольшим macro PR-AUC **на val**; если разница с
  бейзлайном меньше 0.01 — выбирается бейзлайн (проще при равном качестве, принцип IV). Test
  считается для всех кандидатов, но только для отчёта. Дополнительно для победителя — метрики на
  test разбиения `unsw_cross_day` (модель, обученная на train `unsw_time`, не переобучается).
- **Почему**: выбор по test был бы подгонкой под test (принцип III).
- **Замечание**: `unsw_cross_day` проверяет перенос уже выбранной модели; честнее было бы ещё
  обучить её на train `unsw_cross_day`, но это второй эксперимент — отложено, отмечено в отчёте.

## R5. Журнал экспериментов

- **Решение**: MLflow с локальным хранилищем (`mlruns/` в корне, вне git) — каждый кандидат
  отдельным run: параметры, метрики val/test по классам и macro, хеши разбиения и входных
  захватов (из манифестов 001), версия схемы, сид, git-коммит. Дополнительно эксперимент пишет
  `reports/detector_experiment.md` и `models/detector/experiment.json` — они версионируются DVC
  и читаются без MLflow.
- **Почему**: конституция (принцип III) требует MLflow; файл-сводка делает результат видимым
  в репозитории и в DVC.
- **Альтернативы**: только файлы — нарушает конституцию; MLflow tracking server — лишний процесс.

## R6. Артефакт детектора

- **Решение**: `models/detector/` (выход стадии DVC): `model.joblib` (Pipeline предобработки
  и модели), `model_card.json` — версия детектора, кандидат, классы, порог, список признаков,
  `schema_version`, хеши данных, метрики, сид, версии библиотек. Версия детектора —
  `YYYYMMDD-<первые 8 символов хеша конфига и данных>`. Загрузчик сверяет мажорную версию
  схемы входного parquet (`mlsiem.schema_version`) с `model_card.schema_version` и список
  колонок; несовпадение — отказ с сообщением (FR-007).
- **Почему**: один файл модели + читаемая карточка; joblib — стандарт для scikit-learn/LightGBM.
- **Альтернативы**: ONNX — лучше для переносимости, но лишний шаг конвертации сейчас не нужен.

## R7. Детерминизм

- **Решение**: сид из конфига во все генераторы; LightGBM — `deterministic=True`,
  `force_row_wise=True`, фиксированное `num_threads`; логрег — `lbfgs` (детерминирован).
  Вердикты и инциденты вычисляются из отсортированного по `flow_uid` входа; идентификатор
  инцидента — хеш ключа группировки и времени первого алерта в пределах прогона.
- **Почему**: SC-002 требует совпадения на 100%.

## R8. Хранилище SOC (инциденты, алерты, действия, аудит)

- **Решение**: SQLite (стандартный модуль `sqlite3`, без ORM), файл `var/soc.db`, режим WAL.
  Вердикты всех потоков прогона — в `var/runs/<run_id>/verdicts.parquet` (их сотни тысяч,
  в БД нужны только алерты). Прогон записывается в БД одной транзакцией (FR-028: либо целиком,
  либо никак). Оптимистичная блокировка: у инцидента и действия поле `version`, изменение
  `UPDATE … WHERE version = ?`; 0 изменённых строк → конфликт (FR-024). Аудит-журнал —
  таблица только для вставки: триггеры запрещают `UPDATE` и `DELETE` (FR-021).
- **Почему**: встроенная БД без сервера, работает на Windows без Docker, транзакции
  и индексы дают < 1 с на списке инцидентов (SC-006). `var/` — рабочее состояние аналитика,
  а не выход конвейера, поэтому ни в git, ни в DVC не попадает.
- **Альтернативы**: PostgreSQL — нужен сервер (или Docker, которого нет); отложено до фичи
  «хранилище». Файлы JSON — нет транзакций и конкурентного доступа. SQLAlchemy — лишняя
  зависимость на пяти таблицах; при переходе на PostgreSQL можно добавить.

## R9. Группировка алертов в инциденты

- **Решение** (по ответу владельца): ключ — `(src_ip, predicted_class)`. Алерты ключа
  сортируются по `bidirectional_first_seen_ms` (затем `flow_uid`); новый инцидент начинается,
  когда промежуток до предыдущего алерта ключа больше `window_ms` (по умолчанию 900 000 мс).
  Векторно: `diff` по группе → `cum_sum` признаков разрыва → номер инцидента.
- **Замечание о данных**: в UNSW-NB15 все атаки идут с 4 адресов `175.45.176.0–3`, поэтому
  инцидентов будет десятки–сотни на ~10 тыс. алертов — SC-004 (≥ 10×) выполним с запасом.

## R10. Серьёзность

- **Решение** (по ответу владельца): таблица «класс → базовый уровень» и порог числа алертов
  в `configs/soc.yaml`; уровень поднимается на ступень при `n_alerts ≥ bump_at` (100), максимум —
  `critical`. Умолчания — из Assumptions спеки.

## R11. Плейбуки

- **Решение**: упорядоченный список правил в `configs/soc.yaml`, срабатывает первое подходящее
  (детерминированно, FR-017). Условия — по полям инцидента (класс, серьёзность, число уникальных
  целей, адреса в защищённом списке). Умолчания:
  1. источник или единственная цель в защищённом списке → `manual_review`;
  2. класс `exploits`/`shellcode`/`backdoor`/`worms` и одна цель → `isolate_host` (цель);
  3. класс `exploits`/`shellcode`/`backdoor`/`worms` и несколько целей → `block_source_ip`;
  4. класс `dos`/`generic`/`fuzzers` → `block_source_ip`;
  5. класс `reconnaissance`/`analysis` и серьёзность ≥ средней → `block_source_ip`;
  6. иначе → `observe`.
  Симуляция пишет в таблицу действий и аудит-журнал описание «что было бы сделано»
  (тип, объект, правило) — никаких команд ОС, сетевых вызовов или изменений файрвола (FR-019).
- **Почему**: правила в конфиге читаются глазами и проверяются тестами; первое совпадение —
  простейшая детерминированная семантика.

## R12. API

- **Решение**: FastAPI + uvicorn, слушает только `127.0.0.1`. Аналитик — заголовок `X-Analyst`
  (обязателен для изменяющих запросов, FR-023). Версия для оптимистичной блокировки — поле
  `expected_version` в теле запроса. Ошибки — JSON `{"error": "<код>", "message": "<по-русски>"}`,
  коды `not_found` (404), `invalid_transition` (409), `conflict` (409), `bad_request` (400/422).
  Постраничность — `limit`/`offset` с ответом `total`. Контракт — [contracts/api.md](contracts/api.md);
  OpenAPI-схема генерируется FastAPI автоматически.
- **Почему**: типизированные модели запросов/ответов, автоматическая документация (пригодится
  UI), тестирование через `TestClient` без поднятия сервера.
- **Альтернативы**: Flask — нет встроенной валидации и схемы; только CLI — не подходит для UI.

## R13. Проигрывание данных

- **Решение**: `mlsiem soc run --split unsw_time --part test [--limit N]` читает потоки части
  разбиения (join `data/splits/<split>.parquet` с `data/flows/unsw/*.parquet`, лениво, только
  нужные колонки) в хронологическом порядке; `--limit` берёт первые N по времени.
  `mlsiem soc run --pcap FILE` сначала вызывает экстрактор 001 (`run_extract`) в
  `var/runs/<run_id>/flows.parquet`, дальше тот же путь. Метки из датасета при проигрывании
  разбиения сохраняются в вердиктах только для сводки «сколько алертов верных» и в детектор
  не подаются.
- **Почему**: одна точка входа для обоих сценариев спеки (FR-026, FR-027).

## R14. Производительность и память

- **Оценка**: инференс LightGBM на 282 тыс. × 58 — секунды; группировка — polars, доли секунды;
  запись ~10 тыс. алертов и сотен инцидентов в SQLite одной транзакцией — секунды. Итого прогон
  test — порядка минуты, запас до 15 минут (SC-003) большой. Обучение: 1.41 млн × 58 float32
  ≈ 330 МБ; LightGBM — минуты; логрег на полном train может идти 5–10 минут — допустимо
  (эксперимент — стадия DVC, не интерактивная операция).

## R15. Тесты

- **Решение**: pytest.
  - Модульные: предобработка и порог (синтетика), выбор победителя, проверка версии схемы,
    группировка (разрывы окна, ровно один инцидент на алерт), серьёзность, плейбуки (каждое
    правило + защищённый список + детерминизм), машина состояний инцидента и действия, аудит
    (запрет UPDATE/DELETE), оптимистичная блокировка.
  - API: `TestClient` на временной БД — все операции FR-022, ошибки и коды.
  - Интеграционный: крошечный синтетический набор потоков → обучение за секунды → прогон →
    инциденты через API; повторный прогон — те же инциденты.
  - Медленные (`-m slow`): эксперимент на реальных данных 001, прогон полного test, PCAP CTU-13 №7.
