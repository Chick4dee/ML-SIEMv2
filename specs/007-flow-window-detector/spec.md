# Feature Specification: Детектор на окнах потоков (нейросеть против бустинга)

**Feature Branch**: `007-flow-window-detector`

**Created**: 2026-09-26

**Status**: Draft

**Input**: User description: "Детектор на окнах потоков: соревнование «нейросеть vs бустинг» по
плану после 005. Все развилки решать вариантами по умолчанию (без вопросов пользователю),
фиксировать их в разделе Assumptions. Номер 006 зарезервирован за отложенным стендом — эта фича
007."

## Контекст

Детектор 002 и эксперты 004 оценивают **каждый поток отдельно**. Но многие атаки заметны не по
одному потоку, а по поведению источника за короткое время: много коротких соединений к разным
портам, серия однотипных запросов, резкий всплеск объёма. Отдельный поток при этом может
выглядеть совсем обычно. В v1 это пытались решить сложной нейросетью (Flow CNN+LSTM) без
честного сравнения с простой моделью, и она упёрлась в macro PR-AUC 0.443 (конституция, IV).

Фича 007 ставит честный эксперимент: **окно** — это потоки одного источника за короткий
промежуток времени. Для окна соревнуются две модели:

- **бустинг** на сводных признаках окна (число потоков, разнообразие портов и адресов,
  статистики признаков потоков);
- **нейросеть**, которая видит последовательность потоков окна целиком.

Обе сравниваются между собой и с тем, что уже есть: с текущей моделью прогона 002/004, чьи
оценки потоков сведены к окну. Сложное принимается, только если измеримо лучше простого. Иначе
честно фиксируется отрицательный результат, как в 004. Победитель (если он лучше текущей модели)
встраивается в цепочку как эксперт окон. Пакетный прогон и онлайн-потребитель 005 открывают
инциденты и по окнам, и консоль показывает, почему окно признано атакой.

Термины: **источник** — атакующая сторона потока по правилу направления 004; **окно** — потоки
одного источника, начавшиеся в пределах интервала фиксированной длины; **метка окна** — атака,
если в окне есть хотя бы один атакующий поток (класс — самый частый атакующий класс окна), иначе
норма; **текущая модель** — модель прогона по правилам 004 (ансамбль, иначе детектор 002).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Эксперимент «бустинг против нейросети» на окнах (Priority: P1)

Разработчик одной командой строит окна по разбиению `unsw_time` из 001, обучает на train обе
модели окон, сравнивает их на val по macro PR-AUC и со ссылочной оценкой текущей модели,
сведённой к окнам, и получает отчёт: кто победил, на сколько, с порогом, выбранным на val, и
итоговыми цифрами на test.

**Why this priority**: это и есть вопрос фичи: дают ли окна и нейросеть прирост. Без этого
ответа встраивать в цепочку нечего.

**Independent Test**: запустить эксперимент на разбиении → в экспериментах есть три записи
(бустинг окон, нейросеть окон, текущая модель на окнах), отчёт называет победителя по правилу
выбора или объявляет отрицательный результат; повторный запуск с тем же сидом даёт те же цифры в
пределах допуска.

**Acceptance Scenarios**:

1. **Given** разбиение `unsw_time` из 001, **When** запускается эксперимент, **Then** окна
   строятся отдельно для train, val и test, и ни одно окно не содержит потоков из двух частей
   разбиения.
2. **Given** обученные модели окон, **When** выбирается победитель, **Then** решение
   принимается только по val: нейросеть побеждает бустинг, если она лучше не меньше чем на
   минимальный прирост из конфига, иначе выбирается бустинг (простое лучше при равном
   качестве).
3. **Given** победитель среди моделей окон, **When** он сравнивается с текущей моделью на тех же
   окнах val, **Then** он принимается в цепочку, только если лучше на минимальный прирост; иначе
   отчёт фиксирует отрицательный результат, а цепочка остаётся без изменений.
4. **Given** выбранный порог, **When** считаются итоговые цифры, **Then** они считаются на test
   один раз и не влияют ни на выбор модели, ни на порог.
5. **Given** эксперимент завершён, **When** открыт отчёт, **Then** в нём macro PR-AUC и PR-AUC
   по классам на val и test для всех трёх участников, «атака/нет» PR-AUC, точность и полнота на
   пороге, число окон по классам, время обучения и предсказания, и классы с малым числом окон
   помечены как ненадёжные.
6. **Given** один сид и те же данные, **When** эксперимент повторяется, **Then** цифры
   совпадают в пределах допуска, указанного в отчёте (у нейросети на видеокарте допускается
   небольшая недетерминированность).

### User Story 2 - Проверка на артефакты и перенос (Priority: P2)

Разработчик убеждается, что победитель ловит поведение, а не особенности датасета: модель не
видит адресов и абсолютного времени, результат переносится на разбиение `unsw_cross_day`, а
отдельная проверка показывает, не опирается ли модель на признаки-подсказки генератора трафика.

**Why this priority**: конституция III обязательна для любого заметного результата; в v1
высокая цифра автоэнкодера оказалась частично артефактом. Но проверка идёт после эксперимента
US1.

**Independent Test**: запустить проверку для победителя → отчёт с переносом на
`unsw_cross_day`, результатом «без подозрительных признаков» или списком подозрительных, и
сравнением с тем же для модели 002.

**Acceptance Scenarios**:

1. **Given** модель окон, **When** проверяется набор её входов, **Then** в нём нет адресов,
   идентификаторов потоков и абсолютного времени, только относительные величины внутри окна.
2. **Given** победитель, **When** он без переобучения оценивается на test разбиения
   `unsw_cross_day`, **Then** отчёт показывает macro PR-AUC переноса и падение относительно
   `unsw_time`, с оговоркой о пересечении частей, известной из 002.
3. **Given** победитель, **When** выполняется проверка на артефакты (важность признаков и
   повтор эксперимента без самых подозрительных признаков), **Then** отчёт показывает, насколько
   падает качество, и делает вывод «опирается / не опирается на артефакты».
4. **Given** проверка нашла сильную опору на артефакт, **When** выносится вердикт, **Then**
   победитель не принимается в цепочку до исправления, а находка записывается в журнал.

### User Story 3 - Эксперт окон в цепочке: инциденты по окнам (Priority: P3)

Если эксперимент принял модель окон, аналитик видит в консоли инциденты, открытые по окнам:
пакетный прогон и онлайн-сеанс 005 строят окна по мере поступления потоков, эксперт окон
выносит вердикт по окну, и атакующее окно становится алертом, который группируется в инцидент
по тем же правилам, что алерты потоков.

**Why this priority**: сквозной результат (конституция I). Но он имеет смысл, только если US1
дал положительный результат и US2 его подтвердил.

**Independent Test**: прогнать test `unsw_time` пакетно и онлайн с принятой моделью → в
консоли есть инциденты с алертами окон, у каждого видно окно (источник, интервал, число
потоков, цели) и вклад эксперта окон; сравнение пакетного и онлайн-результата — эквивалентно.

**Acceptance Scenarios**:

1. **Given** принятая модель окон, **When** выполняется пакетный прогон, **Then** каждое окно
   получает вердикт, атакующие окна становятся алертами с источником, интервалом, числом
   потоков и классом, и алерты группируются в инциденты по правилам 002/004.
2. **Given** онлайн-сеанс 005, **When** потоки приходят по одному, **Then** окно выносится на
   вердикт, когда оно закрыто по времени трафика (с учётом допустимого опоздания 005), и
   результат совпадает с пакетным прогоном того же входа.
3. **Given** один и тот же поток попал в алерт потока и в алерт окна, **When** строится
   инцидент, **Then** это один инцидент источника: алерты разных видов не дублируют инциденты, а
   в карточке видно, какие алерты от потоков, какие от окон.
4. **Given** карточка инцидента в консоли, **When** аналитик открывает алерт окна, **Then** он
   видит потоки окна, скор и класс окна и сводку, почему окно признано атакой (самые влиятельные
   сводные признаки или самые подозрительные потоки окна).
5. **Given** модель окон не принята (отрицательный результат), **When** выполняется прогон,
   **Then** цепочка работает как в 005, без алертов окон, а старые прогоны открываются как
   раньше.
6. **Given** инцидент, открытый только по окну, **When** предлагается действие, **Then** плейбук
   выбирается по классу окна по тем же детерминированным правилам и выполняется только после
   подтверждения аналитиком (конституция V).

### User Story 4 - Разбор ошибок окон (Priority: P4)

Разработчик получает разбор: какие классы и какие длины окон модель путает, сколько атакующих
окон пропущено и почему (например, атака растянута на много окон по одному потоку), сколько
ложных окон на норме, и сравнение с ошибками модели потоков: какие атаки окна ловят, а потоки
нет, и наоборот.

**Why this priority**: это вклад в магистерскую работу и основа следующих решений, но цепочка
работает и без него.

**Independent Test**: построить разбор по test → матрица ошибок окон, таблица «поймано окнами /
поймано потоками / обоими / никем» по классам, примеры пропущенных окон.

**Acceptance Scenarios**:

1. **Given** предсказания на test, **When** строится разбор, **Then** есть матрица ошибок по
   классам и зависимость качества от числа потоков в окне.
2. **Given** предсказания модели окон и текущей модели потоков, **When** они сравниваются,
   **Then** по каждому классу видно, сколько атакующих окон поймали только окна, только потоки,
   обе модели и ни одна.
3. **Given** разбор, **When** он завершён, **Then** выводы и цифры записаны в журнал.

---

### Edge Cases

- **Окно из одного потока.** Источник сделал одно соединение за интервал — окно всё равно
  строится; модель окон не должна быть хуже модели потоков на таких окнах, и отчёт показывает
  качество отдельно для малых окон.
- **Очень большое окно.** Источник за интервал открыл десятки тысяч потоков (скан, флуд) —
  нейросеть видит ограниченное число потоков окна (по правилу из конфига), сводные признаки
  считаются по всем; отчёт показывает, сколько окон было усечено.
- **Смешанное окно.** В окне и атакующие, и обычные потоки — метка «атака»; доля таких окон
  видна в отчёте.
- **Граница частей разбиения.** Окна не пересекают границы train/val/test; неполные окна у
  границы строятся только из потоков своей части.
- **Редкие классы.** Некоторых классов на уровне окон очень мало (в потоках были классы от 118
  примеров); их PR-AUC помечается ненадёжным, а не скрывается.
- **Нехватка видеопамяти или памяти хоста.** Обучение нейросети укладывается в 8 ГБ VRAM и
  16 ГБ RAM; если данные не помещаются, окна подаются частями, а не падает весь эксперимент.
- **Нет видеокарты.** Эксперимент работает и на процессоре (медленнее), и отчёт указывает, на
  чём обучалась модель.
- **Онлайн-режим и тишина.** Если новых потоков нет, открытое окно всё равно закрывается по
  времени, когда время трафика ушло вперёд; при полной тишине — по отметке «конец данных» или
  при остановке сеанса.
- **Модель заменили во время сеанса.** Как в 005: сеанс работает моделью, с которой стартовал.

## Requirements *(mandatory)*

### Functional Requirements

**Окна**

- **FR-001**: Система ДОЛЖНА строить окна из потоков в схеме признаков 001: ключ окна —
  источник по правилу направления 004, интервал фиксированной длины по времени начала потока
  (длина из конфига), без пересечения частей разбиения.
- **FR-002**: Для окна ДОЛЖНЫ вычисляться сводные признаки (число потоков, число разных целей и
  портов, статистики признаков потоков) и последовательность потоков окна для нейросети
  (упорядоченная по времени, ограниченная по длине с правилом из конфига).
- **FR-003**: Построение окон и признаков окна ДОЛЖНО быть одним кодом для обучения, пакетного
  прогона и онлайн-сеанса (конституция II); предобработка (нормализация, кодирование)
  сохраняется как часть артефакта модели и переиспользуется при инференсе.
- **FR-004**: Входы моделей окон НЕ ДОЛЖНЫ содержать адресов, идентификаторов потоков и
  абсолютного времени; допустимы только относительные величины внутри окна.
- **FR-005**: Метка окна ДОЛЖНА выводиться из меток потоков 001 по правилу из раздела
  «Контекст»; метки используются только для обучения и оценки, в модель не подаются.

**Эксперимент**

- **FR-006**: ДОЛЖЕН быть эксперимент с тремя участниками на одних и тех же окнах: бустинг на
  сводных признаках, нейросеть на последовательностях и текущая модель (оценки её потоков,
  сведённые к окну по правилу из конфига, по умолчанию максимум).
- **FR-007**: Выбор ДОЛЖЕН делаться только по val по macro PR-AUC надёжных классов (классы,
  у которых на val не меньше порога окон из конфига; остальные показываются в отчёте, но в
  выборе не участвуют, потому что их PR-AUC — шум): сначала бустинг против
  нейросети (нейросеть побеждает при приросте не меньше минимального из конфига), затем
  победитель против текущей модели (принимается при таком же приросте). Порог выбирается на val.
  Test используется один раз для итоговых цифр.
- **FR-008**: Результаты всех участников ДОЛЖНЫ записываться в эксперименты с версией данных,
  версией схемы признаков, конфигом, сидом и устройством обучения.
- **FR-009**: Нейросеть ДОЛЖНА обучаться в пределах 8 ГБ видеопамяти и 16 ГБ памяти хоста, с
  ранней остановкой по val и фиксированным сидом; эксперимент ДОЛЖЕН работать и без видеокарты.
- **FR-010**: Если ни одна модель окон не принята, эксперимент ДОЛЖЕН завершаться успешно с
  отчётом «отрицательный результат» и не менять модель цепочки.

**Проверки**

- **FR-011**: ДОЛЖНА быть проверка победителя на артефакты: состав входов (FR-004), важность
  признаков, повтор без самых подозрительных признаков, перенос на test `unsw_cross_day` без
  переобучения; вывод и цифры — в отчёте и журнале.
- **FR-012**: Победитель с подтверждённой сильной опорой на артефакт НЕ ДОЛЖЕН приниматься в
  цепочку.

**Цепочка**

- **FR-013**: Принятая модель окон ДОЛЖНА загружаться через общий интерфейс загрузки моделей
  004 как эксперт окон со всеми проверками (версия схемы, предобработка на месте) до начала
  прогона или сеанса.
- **FR-014**: Пакетный прогон и онлайн-потребитель 005 ДОЛЖНЫ выносить вердикт по окну, когда
  окно закрыто по времени трафика (с учётом допустимого опоздания 005), и превращать атакующие
  окна в алерты окон с источником, интервалом, числом потоков, целями, скором и классом.
- **FR-015**: Алерты окон ДОЛЖНЫ группироваться в инциденты по тем же правилам, что алерты
  потоков (ключ — атакующая сторона и класс, окно группировки 15 минут), без дублирования
  инцидентов; повторная доставка потоков не создаёт дублей алертов окон (идемпотентность 005).
- **FR-016**: Онлайн-обработка того же входа ДОЛЖНА давать те же алерты окон и инциденты, что
  пакетный прогон; команда сравнения 005 ДОЛЖНА учитывать алерты окон.
- **FR-017**: Консоль и API ДОЛЖНЫ показывать алерт окна: интервал, потоки окна, скор, класс и
  пояснение (самые влиятельные сводные признаки или самые подозрительные потоки окна);
  карточка инцидента различает алерты потоков и окон. Старые прогоны открываются как раньше.
- **FR-018**: Плейбуки ДОЛЖНЫ выбираться по классу алерта окна по тем же детерминированным
  правилам; действия только симулируются и выполняются после подтверждения аналитиком.

**Общее**

- **FR-019**: Все параметры (длина окна, предел длины последовательности, правило сведения
  оценок потоков к окну, минимальный прирост, гиперпараметры участников, сид) ДОЛЖНЫ быть в
  конфиге, не в коде.
- **FR-020**: Модели окон ДОЛЖНЫ версионироваться как модели 002/004; отчёты, сообщения и
  комментарии — на русском.

### Key Entities

- **Окно**: источник, интервал, часть разбиения (для обучения), потоки окна, сводные признаки,
  последовательность, метка и класс (для оценки), признак «усечено».
- **Модель окон**: версионированный артефакт — вид (бустинг / нейросеть), предобработка, порог,
  классы, версия схемы признаков, длина окна.
- **Отчёт эксперимента**: участники, метрики на val и test, решение о выборе с правилом, время,
  устройство.
- **Отчёт проверки на артефакты**: состав входов, важности, результат без подозрительных
  признаков, перенос, вердикт.
- **Алерт окна**: сеанс или прогон, окно, скор, класс, пояснение; связан с инцидентом и с
  потоками окна.
- **Разбор ошибок**: матрица ошибок, качество по размеру окна, сравнение с моделью потоков.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Эксперимент (построение окон, обучение обоих участников, оценка всех трёх) на
  `unsw_time` проходит одной командой не дольше 2 часов на железе владельца, укладываясь в 8 ГБ
  видеопамяти и 16 ГБ памяти хоста.
- **SC-002**: Решение о выборе принимается по заранее записанному правилу, и отчёт позволяет
  проверить его по цифрам val без пересчёта; test не влияет на выбор и порог (проверяется
  тестом).
- **SC-003**: Повторный запуск с тем же сидом даёт macro PR-AUC бустинга, совпадающий до
  0.001, а нейросети — в пределах 0.01.
- **SC-004**: 100% окон содержат потоки только одной части разбиения; входы моделей окон не
  содержат адресов и абсолютного времени (проверяется тестом).
- **SC-005**: Отчёт проверки на артефакты и перенос на `unsw_cross_day` построены для
  победителя; результат (положительный или отрицательный) и цифры записаны в журнал.
- **SC-006**: Если модель окон принята, онлайн-обработка test `unsw_time` даёт 100% совпадение
  алертов окон и инцидентов с пакетным прогоном; в реальном времени инцидент по окну
  появляется в консоли не позже чем через 15 секунд после того, как время трафика ушло за
  конец окна плюс допустимое опоздание 005 (окно раньше закрывать нельзя, иначе пакетный и
  онлайн-результат разойдутся).
- **SC-007**: Если модель окон принята, пропускная способность онлайн-сеанса на test
  `unsw_time` в режиме «как можно быстрее» остаётся в пределах целей 005 (вся часть не дольше
  10 минут).
- **SC-008**: Все тесты 001–005 проходят без изменения ожиданий, кроме тех, что прямо зависят
  от состава экспертов или версии схемы хранилища; при отрицательном результате поведение
  цепочки не меняется.

## Assumptions

Развилки решены вариантами по умолчанию (по просьбе владельца, без вопросов):

- **Данные**: основное разбиение — `unsw_time`, перенос — `unsw_cross_day`. CTU-13 в эту фичу
  не входит: его отдельный эксперт отложен вместе со стендом (решение 004), и CTU не смешивается
  с UNSW (решение 001).
- **Длина окна** по умолчанию — 60 секунд времени трафика; для оценки и цепочки окна не
  перекрываются. Для обучения train дополняется сдвинутыми окнами (шаг 15 с), потому что окон
  мало: по замеру 2026-09-26 в train `unsw_time` ≈14.5 тыс. окон (атакующих ≈2.4 тыс.), в val
  ≈2.3 тыс., в test ≈2.6 тыс.
- **Предел последовательности для нейросети** — 128 потоков окна (первые по времени): медиана
  окна — ≈120 потоков, 99-й перцентиль — ≈260; сводные признаки считаются по всем потокам окна.
- **Надёжные классы** для выбора — не меньше 20 окон на val (сейчас это exploits, fuzzers,
  reconnaissance); PR-AUC «атака/нет» и все классы показываются в отчёте.
- **Метка окна** — «атака», если в окне есть хотя бы один атакующий поток; класс — самый частый
  атакующий класс окна.
- **Участники**: бустинг на сводных признаках — того же семейства, что победитель 002 (бейзлайн
  по принципу IV); нейросеть — компактная модель последовательностей, помещающаяся в 8 ГБ
  видеопамяти. Конкретная архитектура выбирается в плане.
- **Сведение текущей модели к окну** — максимум оценок потоков окна по каждому классу.
- **Правило выбора** — как в 002/004 (macro PR-AUC на val, минимальный прирост 0.01), но macro
  считается по надёжным классам (см. выше).
- **Ключ окна** — атакующая сторона по правилу направления 004 (`direction auto`), так что окна
  и инциденты группируются по одному ключу.
- **Эксперт окон дополняет** модель потоков, а не заменяет её: алерты потоков остаются, окна
  добавляют свои. Замена модели потоков — отдельное решение после этой фичи.
- **Видеокарта** RTX 3060 Ti; обучение нейросети на процессоре допускается, но цель по времени
  SC-001 ставится для видеокарты. Новые зависимости для нейросети фиксируются в плане.
- **Хранилище**: та же SQLite `var/soc.db`, схема мигрирует при необходимости (с копией перед
  миграцией, как в 003–005).
- **Собственная норма со стенда** в эту фичу не входит, потому что стенд (006) отложен.
