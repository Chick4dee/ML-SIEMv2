# Implementation Plan: Детектор на окнах потоков (нейросеть против бустинга)

**Branch**: `007-flow-window-detector` | **Date**: 2026-09-26 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/007-flow-window-detector/spec.md`

## Summary

Потоки одного атакующего (правило направления 004) собираются в окна по 60 с на сетке от эпохи.
На окнах `unsw_time` соревнуются три участника:
- LightGBM на ~190 сводных признаках окна;
- компактный двунаправленный GRU на последовательности до 128 потоков (PyTorch, CUDA);
- текущая модель 002/004, у которой оценки потоков сведены к окну максимумом.

Выбор — только по val, по macro PR-AUC надёжных классов (≥ 20 окон на val), с приростом 0.01, в
два шага. Потом аудит на артефакты: если модель на них опирается, принятие снимается.

Победитель сохраняется всегда. В цепочку он включается, только если принят. Эксперт окон
выдаёт алерты окон в той же таблице `alerts` (`alert_kind = 'window'`), и группировка в
инциденты не меняется. Онлайн-потребитель 005 держит открытые окна в SQLite в общей
транзакции и закрывает их по водяному знаку «время трафика − допустимое опоздание». Поэтому
пакетный и онлайн-результат совпадают.

Окон мало (train ≈14.5 тыс., val ≈2.3 тыс.), поэтому:
- train дополняется сдвинутыми окнами (×4);
- ранняя остановка идёт по хвосту train, а не по val;
- отрицательный результат — законный исход (FR-010).

## Technical Context

**Language/Version**: Python 3.11 (как 001–005)

**Primary Dependencies**:
- уже есть: polars, numpy, scikit-learn, LightGBM, MLflow, FastAPI/Jinja2/htmx (003),
  confluent-kafka (005);
- **новое**: PyTorch 2.x (колёса CUDA 12.8) в отдельной группе зависимостей `nn`
  (`tool.uv.sources` → индекс PyTorch).

**Storage**:
- SQLite `var/soc.db`, миграция схемы 4 → 5 (R14);
- артефакты `models/windows/` (DVC);
- отчёты `reports/windows_*.md`;
- MLflow (`mlflow.db` + `mlruns/`), эксперимент `windows`.

**Testing**:
- pytest: быстрые тесты на синтетике и фикстурах (`synthetic_split`, `tiny_detector`,
  `tiny_ensemble`) плюс новая фикстура `tiny_windows` (модель окон с `force`);
- `slow` — на реальных данных 001;
- `stand` — на брокере 005;
- тесты нейросети помечаются `nn` и пропускаются без PyTorch.

**Target Platform**: Windows 11, хост владельца; брокер 005 — Linux-ВМ Hyper-V.

**Project Type**: CLI + локальный веб-сервис (единый пакет `mlsiem`).

**Performance Goals**:
- эксперимент ≤ 2 ч (ожидаемо — минуты);
- онлайн-обработка test `unsw_time` в режиме «как можно быстрее» ≤ 10 мин, с сохранением
  запаса по хвосту SC-002 005 (≤ 30 с);
- в реальном времени алерт окна ≤ 15 с после закрытия окна.

**Constraints**:
- 8 ГБ VRAM, 16 ГБ RAM (окна в RAM ≈ 1.8 ГБ);
- без Docker и WSL2;
- инференс эксперта окон в цепочке — на CPU;
- без адресов, портов-значений и абсолютного времени во входах моделей.

**Scale/Scope**:
- окон: train ≈14.5 тыс. (×4 с аугментацией), val ≈2.3 тыс., test ≈2.6 тыс.;
- 3 участника, 4 новые команды CLI, 2 дополнения к командам 005;
- схема БД 5.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Принцип | Как выполняется | Статус |
|---|---|---|
| I. Вертикальные срезы | Сквозной результат: эксперимент → отчёт → (если принят) эксперт окон в пакетном и онлайн-прогоне → инцидент в консоли. При отрицательном результате сквозная интеграция всё равно проверяется режимом `force` (как `force_variant` в 004) | ✅ |
| II. Train = serve | Одна функция `build_windows` + сохранённая предобработка (`preprocess.joblib`) для обучения, `soc run` и потребителя; проверка версии схемы 001 при загрузке | ✅ |
| III. Честная оценка | PR-AUC (macro надёжных — выбор; все классы и «атака/нет» — в отчёте); окна внутри частей временного разбиения; ранняя остановка на хвосте train, порог на val, test один раз; аудит на артефакты (R10) с правом снять принятие; MLflow с версией данных, конфигом, сидом | ✅ |
| IV. Решения через эксперимент | Бейзлайны: бустинг (против нейросети) и текущая модель (против победителя); `min_gain` 0.01; результат в журнал | ✅ |
| V. SOAR с человеком | Плейбуки не меняются; алерт окна — обычный алерт; действия — симуляция после подтверждения | ✅ |
| VI. Воспроизводимость | DVC-стадия `train_windows`, сиды, допуск воспроизводимости в отчёте; тесты; комментарии по-русски; журнал | ✅ |
| VII. Авторство | Без трейлеров; коммитит владелец | ✅ |
| Среда | 8 ГБ VRAM, 16 ГБ RAM учтены (R4, R18); Docker/WSL2 не нужны | ✅ |

**Уточнение (не нарушение)**: метрика выбора — macro PR-AUC **надёжных** классов, а не всех, как
в 002/004. Причина — классы с 1–5 окнами на val (research R8). Порог надёжности записан в конфиг
до запуска. Macro по всем классам остаётся в отчёте. Спека поправлена (FR-007).

**Повторная проверка после Phase 1**: data-model и контракты не добавляют ни реальных действий
SOAR, ни новых источников признаков вне схемы 001. PyTorch вынесен в отдельную группу, так что
базовая установка не утяжеляется. Нарушений нет, Complexity Tracking — только про новую
зависимость.

## Complexity Tracking

| Отступление | Зачем нужно | Почему не проще |
|---|---|---|
| Новая тяжёлая зависимость PyTorch (≈2.5 ГБ с CUDA) | Нейросеть — предмет эксперимента фичи (соревнование «нейросеть против бустинга») | sklearn MLP не работает с последовательностями переменной длины с маской и не использует видеокарту. Зависимость вынесена в группу `nn`, цепочка без неё работает, а быстрые тесты её не требуют |
| Две новые таблицы SQLite (`window_pending`, `window_closed`) | Открытые окна должны пережить перезапуск потребителя в той же транзакции, что позиция (гарантии 005) | Хранение в памяти теряет окна при перезапуске: позиция в Kafka уже подтверждена, перечитывать нечего |
