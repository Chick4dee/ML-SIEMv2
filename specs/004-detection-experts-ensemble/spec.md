# Feature Specification: Несколько экспертов-детекторов и мета-слой

**Feature Branch**: `004-detection-experts-ensemble`

**Created**: 2026-09-24

**Status**: Draft

**Input**: User description: "004: несколько экспертов-детекторов + мета-слой. Сейчас (002)
в цепочке один эксперт — классификатор LightGBM на признаках nfstream (UNSW-NB15), вердикты идут
в инциденты, SOAR и консоль (003). Нужно: добавить ещё экспертов с разными взглядами на трафик
(например, детектор аномалий без учителя, обученный только на нормальном трафике, для неизвестных
атак; эксперт по ботнет-поведению на CTU-13), и мета-слой, который объединяет их вердикты в один
итоговый вердикт с объяснением, какие эксперты сработали. Итоговый вердикт должен быть лучше
лучшего одиночного эксперта по macro PR-AUC на временном сплите (без утечек, конституция).
Попутно разобрать ложные инциденты из 002/003, где «источником» оказываются адреса жертв
(149.171.126.0/24) или фона (59.166.0.0/24) — 14 из 66 инцидентов. Цепочка инцидент → SOAR →
API → консоль должна работать с новым вердиктом без поломок; в карточке инцидента видно вклад
экспертов. Подход к моделям пересматриваем, архитектуры v1 не копируем слепо."

## Clarifications

### Session 2026-09-24

- Q: Какую роль играет эксперт по ботнетам на CTU-13? → A: в 004 не делается; эксперты фичи —
  классификатор 002 и детектор аномалий на UNSW-NB15, CTU-эксперт — вместе со стендом.
- Q: Принимать ли ансамбль, если macro PR-AUC не вырос, но скрытый класс ловится заметно
  лучше? → A: да, два условия: либо macro PR-AUC +0.01 на val, либо поимка скрытого класса
  +0.10 при падении macro PR-AUC не больше 0.01 (FR-010).
- Q: Что делать с алертом, если поток признан ответом жертвы? → A: алерт остаётся, стороны
  переворачиваются — группировка и SOAR идут по атакующей стороне, исходные адреса видны
  с пометкой «ответный поток» (FR-015, FR-023).
- Q: Какое действие SOAR предлагает для инцидента класса «аномалия»? → A: всегда «требуется
  ручной разбор», без блокировки и изоляции (FR-017).
- Q: Как выбирать порог детектора аномалий? → A: по бюджету ложных срабатываний на нормальных
  потоках val — не больше 0.5% (FR-003, SC-002).

## User Scenarios & Testing *(mandatory)*

Два пользователя. Владелец проекта в роли ML-инженера добавляет экспертов, собирает из них
мета-слой и должен честно показать, что объединение лучше одного детектора — или честно
признать, что нет. Аналитик SOC продолжает работать в консоли 003, но теперь видит, какие
эксперты подняли тревогу и почему инцидент вообще появился, а ложных инцидентов с адресов
жертв и фона становится меньше.

Термины: **эксперт** — отдельный детектор со своим «взглядом» на поток (классификатор атак
из 002, детектор аномалий и т. п.); **мета-слой** — правило или модель, которая по ответам всех
экспертов выдаёт один **итоговый вердикт**; **ансамбль** — набор экспертов плюс мета-слой,
сохранённый как одна версия.

### User Story 1 - Эксперимент «эксперты + мета-слой» против лучшего одиночного эксперта (Priority: P1)

Владелец запускает эксперимент: каждый эксперт обучается на своих данных без доступа к val и
test, мета-слой учится объединять их ответы на данных, которые эксперты не видели при обучении,
порог итогового вердикта выбирается на val, итог считается на test разбиения `unsw_time`.
В результатах — таблица: каждый эксперт в одиночку, простое объединение (например, «сработал
хотя бы один») и мета-слой, с macro PR-AUC и PR-AUC по классам на val и test. Ансамбль
принимается в цепочку, только если на val он заметно лучше лучшего одиночного эксперта — по
macro PR-AUC или по поимке скрытого класса (FR-010); иначе остаётся одиночный эксперт,
и это решение записано с цифрами.

**Why this priority**: это ядро фичи и требование конституции (принцип IV): усложнение
принимается только при измеримом приросте. Без этого эксперимента остальные истории
не имеют смысла.

**Independent Test**: запустить эксперимент на данных фич 001–002 и проверить, что появились
таблица сравнения, решение (ансамбль или одиночный эксперт) с правилом выбора и сохранённый
артефакт выбранного варианта.

**Acceptance Scenarios**:

1. **Given** данные и разбиения фичи 001 и эксперт 002, **When** владелец запускает эксперимент,
   **Then** в таблице есть минимум: эксперт 002 в одиночку, каждый новый эксперт в одиночку,
   простое объединение и мета-слой — с macro PR-AUC и PR-AUC по классам на val и test.
2. **Given** законченный эксперимент, **When** выбирается вариант для цепочки, **Then** выбор
   сделан только по val, в результатах видно правило выбора и минимальный требуемый прирост,
   а test используется лишь для итоговой оценки выбранного варианта.
3. **Given** мета-слой не дал нужного прироста над лучшим одиночным экспертом на val, **When**
   эксперимент завершён, **Then** в цепочку идёт лучший одиночный эксперт, а отрицательный
   результат записан в журнал с цифрами, а не скрыт.
4. **Given** данные, на которых учится мета-слой, **When** проверяется отсутствие утечек,
   **Then** ни один пример, на котором обучался эксперт, не участвует в обучении мета-слоя
   или выборе порога, а test не участвует ни в чём, кроме итоговой оценки.
5. **Given** тот же конфиг, данные и сид, **When** эксперимент запускается повторно,
   **Then** все метрики и выбранный вариант совпадают.

### User Story 2 - Детектор аномалий для неизвестных атак (Priority: P2)

Владелец добавляет эксперта, который учится только на нормальном трафике и помечает всё,
что на него не похоже. Главная ценность — ловить атаки, которых не было в обучении
классификатора. Это проверяется отдельным экспериментом «класс атаки, скрытый от обучения»:
классификатор обучается без одного класса, и смотрится, ловит ли этот класс детектор аномалий
и помогает ли ему мета-слой. Эксперт проходит проверку на артефакты датасета: не отличает ли он
«норму» от «атак» по признакам генератора трафика, а не по поведению.

**Why this priority**: без эксперта с другим взглядом на трафик объединять нечего; детектор
аномалий — самый понятный второй взгляд и прямо закрывает слабость классификатора
(он знает только те классы, на которых учился).

**Independent Test**: обучить детектор аномалий на нормальных потоках train, посчитать его
PR-AUC «атака / не атака» на val и test, провести эксперимент со скрытым классом и аудит
артефактов — всё без участия мета-слоя.

**Acceptance Scenarios**:

1. **Given** нормальные потоки train, **When** обучается детектор аномалий, **Then** в обучении
   не участвует ни один поток атаки, и для него записан PR-AUC «атака / не атака» на val и test.
2. **Given** эксперимент со скрытым классом, **When** из обучения классификатора убран один
   класс атаки, **Then** записано, какая доля потоков этого класса поймана классификатором,
   детектором аномалий и итоговым вердиктом при их порогах, выбранных на val.
3. **Given** обученный детектор аномалий, **When** проводится аудит артефактов, **Then**
   записано, какие признаки сильнее всего отличают «аномалии» от нормы, и отдельно отмечено,
   если среди них есть признаки, выдающие генератор трафика, а не поведение атаки.
4. **Given** поток, который детектор аномалий пометил, а классификатор — нет, **When** такой
   поток становится алертом, **Then** его класс в алерте — отдельный класс «аномалия»,
   а не произвольный класс атаки.

### User Story 3 - Итоговый вердикт в цепочке и вклад экспертов в консоли (Priority: P3)

Сквозная команда 002 теперь прогоняет потоки через выбранный вариант (ансамбль или одиночный
эксперт). Алерты, инциденты, серьёзность, плейбуки, API и консоль 003 работают как раньше.
В карточке инцидента и в деталях алерта аналитик видит, какие эксперты сработали, с какой
уверенностью, и итоговое решение мета-слоя с коротким объяснением. Старые прогоны 002/003
по-прежнему открываются и выглядят как раньше.

**Why this priority**: конституция требует вертикального среза — ансамбль должен дойти
до аналитика, а не остаться таблицей в журнале экспериментов.

**Independent Test**: выполнить сквозную команду с ансамблем на test-части `unsw_time`,
открыть в консоли инцидент и алерт и убедиться, что вклад экспертов виден, а все операции
002/003 (решения, аудит, фильтры) проходят свои тесты.

**Acceptance Scenarios**:

1. **Given** выбранный ансамбль, **When** запускается сквозная команда, **Then** каждый поток
   получает итоговый вердикт и ответы всех экспертов, а алерты, инциденты и предложения
   действий формируются по тем же правилам, что в 002.
2. **Given** алерт, **When** аналитик открывает его детали, **Then** видно, какие эксперты
   сработали, их уверенность и пороги, итоговое решение и одно-два предложения объяснения
   («сработали классификатор и детектор аномалий», «сработал только детектор аномалий»).
3. **Given** инцидент, **When** аналитик открывает карточку, **Then** видна сводка по
   экспертам: сколько алертов инцидента поднял каждый эксперт.
4. **Given** прогон, выполненный в 002 или 003 одиночным детектором, **When** его открывают
   в консоли или API, **Then** он отображается без ошибок, а блок экспертов показывает только
   одного эксперта или явно сообщает, что прогон сделан до появления ансамбля.
5. **Given** ансамбль и тот же вход, **When** сквозная команда запускается повторно, **Then**
   вердикты, инциденты, серьёзность и предложения действий совпадают на 100%.
6. **Given** один из экспертов ансамбля отсутствует или повреждён, **When** запускается
   сквозная команда, **Then** она останавливается до начала обработки с понятным сообщением,
   какого эксперта не хватает.

### User Story 4 - Разбор ложных инцидентов с адресов жертв и фона (Priority: P4)

Владелец разбирает 14 из 66 инцидентов прогона 002, у которых «источник» — адрес из сети
жертв (149.171.126.0/24) или фона (59.166.0.0/24): какие это потоки — ответы жертвы атакующему,
реальные ошибки детектора или честные атаки из этих сетей по разметке. По итогам разбора
вносится исправление (например, учёт направления потока при определении атакующего или при
группировке), и на том же прогоне видно, сколько таких инцидентов осталось и не потерялись ли
настоящие.

**Why this priority**: это известный долг 002/003, который мешает аналитику и делает метку
`target_elsewhere` в консоли шумной; но он не блокирует ансамбль и может идти последним.

**Independent Test**: сформировать отчёт разбора по 14 инцидентам, применить исправление,
перепрогнать test-часть `unsw_time` и сравнить число инцидентов с источником из сетей жертв
и фона и число настоящих атакующих инцидентов до и после.

**Acceptance Scenarios**:

1. **Given** прогон 002, **When** выполняется разбор, **Then** для каждого из 14 инцидентов
   указана причина: ответное направление, ошибка детектора или атака по разметке датасета —
   с числом потоков каждого вида.
2. **Given** исправление, **When** test-часть прогоняется заново, **Then** число инцидентов
   с источником из сетей жертв и фона уменьшилось, а каждый оставшийся имеет причину из отчёта.
3. **Given** исправление, **When** сравниваются прогоны до и после, **Then** ни один инцидент,
   источник которого — атакующий по разметке датасета, не пропал.
4. **Given** правило определения атакующей стороны, **When** оно применяется к потоку,
   **Then** оно использует только данные самого потока и прогона и не опирается на разметку
   датасета или на знание, какие сети в UNSW-NB15 — жертвы.

### Edge Cases

- Эксперты противоречат друг другу (классификатор уверенно говорит «норма», детектор аномалий
  — «аномалия»): итоговый вердикт определяет мета-слой, а в объяснении видны оба ответа.
- Сработал только детектор аномалий, класс атаки неизвестен: алерт получает класс «аномалия»,
  серьёзность которого задана в конфигурации; группировка идёт по тому же ключу, что в 002.
- Детектор аномалий «отличает» норму по признаку генератора (в UNSW-NB15 норма и атаки
  созданы разными инструментами): это фиксируется в аудите артефактов, и такой признак
  исключается или результат помечается как завышенный.
- Мета-слою не хватает примеров редкого класса в данных для его обучения (в train `unsw_time`
  есть классы от 118 примеров): PR-AUC такого класса помечается как ненадёжный, а не скрывается.
- Эксперт даёт одинаковую уверенность многим потокам: итоговый вердикт и порог остаются
  детерминированными.
- Ансамбль и эксперт в нём собраны на разных версиях схемы признаков: ансамбль отказывается
  работать с понятным сообщением.
- Инцидент, в котором часть алертов подняли разные эксперты: сводка по экспертам в карточке
  складывается в число алертов инцидента (алерт с несколькими сработавшими экспертами
  учитывается у каждого, и это объяснено в подписи).
- Время обработки выросло из-за нескольких экспертов: сквозная команда всё равно укладывается
  в бюджет времени и памяти 002.

## Requirements *(mandatory)*

### Functional Requirements

**Эксперты**

- **FR-001**: Система ДОЛЖНА поддерживать несколько экспертов; каждый эксперт — отдельный
  версионированный артефакт со своими данными обучения, предобработкой, порогом, списком
  выходов (классы или оценка аномальности) и версией схемы признаков.
- **FR-002**: Эксперт 002 (классификатор атак UNSW-NB15) ДОЛЖЕН войти в эксперимент без
  изменений как первый эксперт и точка сравнения.
- **FR-003**: ДОЛЖЕН быть добавлен детектор аномалий, обучаемый только на нормальных потоках
  train; потоки атак в его обучении запрещены. Его порог ДОЛЖЕН выбираться на val по бюджету
  ложных срабатываний: доля нормальных потоков val выше порога не больше `anomaly_fpr`
  (по умолчанию 0.5%, задаётся в конфигурации); разметка атак в выборе порога не участвует.
- **FR-004**: Эксперт по ботнетам на CTU-13 в этой фиче НЕ делается: в разметке UNSW-NB15
  нет ботнетов, а в CTU-13 почти нет нормы, поэтому честно измерить его вклад в итоговый
  вердикт нельзя. Он переносится в фичу стенда, где появится собственная норма.
- **FR-005**: На вход любого эксперта ДОЛЖНЫ подаваться только поля группы `feature` схемы
  признаков фичи 001 (как FR-004 фичи 002); поля `identity` и `time` запрещены, `dpi` —
  только после отдельного эксперимента с аудитом артефактов.
- **FR-006**: Для каждого эксперта ДОЛЖНЫ записываться метрики по его назначению: для
  классификатора — PR-AUC по классам и macro; для детектора аномалий — PR-AUC «атака /
  не атака». Проверка переноса на `unsw_cross_day` записывается отдельно и с пометкой, если
  её test пересекается с train `unsw_time` (находка 002).

**Мета-слой и эксперимент**

- **FR-007**: Мета-слой ДОЛЖЕН выдавать для каждого потока итоговый вердикт того же вида, что
  вердикт 002 (класс, уверенность, превышение порога), плюс ответы всех экспертов и краткое
  объяснение, какие эксперты повлияли на решение.
- **FR-008**: Мета-слой ДОЛЖЕН обучаться только на данных, которые не использовались для
  обучения экспертов; test НЕ ДОЛЖЕН участвовать ни в обучении, ни в выборе порога, ни
  в выборе варианта. Схема разделения данных между экспертами, мета-слоем и порогом ДОЛЖНА
  быть записана в результатах эксперимента.
- **FR-009**: Эксперимент ДОЛЖЕН сравнивать минимум: каждый эксперт в одиночку, простое
  объединение без обучения (например, «сработал хотя бы один эксперт» или среднее
  уверенностей) и обучаемый мета-слой — на одном и том же val и test разбиения `unsw_time`.
- **FR-010**: Вариант для цепочки ДОЛЖЕН выбираться только по val. Ансамбль принимается, если
  выполнено одно из двух условий: (а) его macro PR-AUC выше, чем у лучшего одиночного
  эксперта, минимум на `min_gain` (по умолчанию 0.01, как в 002); или (б) в эксперименте
  «скрытый класс» (FR-011) итоговый вердикт ловит долю потоков скрытого класса больше, чем
  классификатор без этого класса, минимум на `min_unknown_gain` (по умолчанию 0.10), и при
  этом macro PR-AUC ансамбля ниже лучшего одиночного эксперта не больше чем на `min_gain`.
  Оба порога задаются в конфигурации. Если ни одно условие не выполнено, в цепочку идёт лучший
  одиночный эксперт, а результат записывается как отрицательный; в результатах видно, какое
  условие сработало.
- **FR-011**: ДОЛЖЕН проводиться эксперимент «скрытый класс»: минимум для одного класса
  атаки классификатор обучается без этого класса, и записывается доля потоков скрытого класса,
  пойманная каждым экспертом и итоговым вердиктом при порогах, выбранных на val.
- **FR-012**: Для каждого нового эксперта и для мета-слоя ДОЛЖЕН проводиться аудит артефактов
  датасета (принцип III): какие признаки определяют решение и нет ли среди них признаков
  генератора трафика; вывод записывается в журнал.
- **FR-013**: Результаты экспертов, объединений и мета-слоя ДОЛЖНЫ записываться в журнал
  экспериментов с версией данных, конфигом, сидом и версией схемы признаков; повторный
  эксперимент с теми же данными, конфигом и сидом ДОЛЖЕН давать те же метрики и тот же выбор.
- **FR-014**: Ансамбль ДОЛЖЕН сохраняться как один версионированный артефакт, ссылающийся на
  версии входящих экспертов; он ДОЛЖЕН отказываться работать, если эксперт отсутствует,
  повреждён или собран на несовместимой версии схемы признаков, и сообщать, что не так.

**Цепочка, API, консоль**

- **FR-015**: Сквозная команда 002 и путь для нового PCAP ДОЛЖНЫ работать с выбранным вариантом
  (ансамбль или одиночный эксперт) без изменения правил алертов, серьёзности, плейбуков
  (кроме нового правила для класса «аномалия», FR-017), статусов, аудита и защиты консоли. Правило группировки 002 меняется только в одном: в ключе
  вместо «IP-источник потока» используется «атакующая сторона» по FR-023.
- **FR-016**: Для каждого алерта ДОЛЖНЫ сохраняться ответы всех экспертов (уверенность,
  сработал ли относительно своего порога) и объяснение итогового вердикта.
- **FR-017**: Поток, признанный атакой только за счёт детектора аномалий, ДОЛЖЕН получать класс
  «аномалия»; этот класс ДОЛЖЕН иметь базовую серьёзность в таблице конфигурации и участвовать
  в фильтрах API и консоли наравне с классами атак. Для инцидента класса «аномалия» плейбуки
  ДОЛЖНЫ всегда предлагать «требуется ручной разбор» (независимо от серьёзности и числа
  алертов) с правилом «класс атаки неизвестен»; блокировка и изоляция не предлагаются. Это
  новое правило плейбука, остальные правила 002 не меняются.
- **FR-018**: API ДОЛЖЕН отдавать вклад экспертов для алерта и сводку по экспертам для
  инцидента; изменения API — только добавления, существующие поля и операции 002/003 не
  меняются.
- **FR-019**: Консоль ДОЛЖНА показывать в деталях алерта ответы экспертов и объяснение
  итогового вердикта, а в карточке инцидента — сколько алертов поднял каждый эксперт.
- **FR-020**: Прогоны, сделанные до этой фичи, ДОЛЖНЫ открываться в API и консоли без ошибок;
  блок экспертов для них показывает единственного эксперта или явную пометку «прогон до
  ансамбля». Существующая база с данными 002/003 ДОЛЖНА переходить на новую версию без потери
  инцидентов, решений и аудита.
- **FR-021**: В сводке прогона ДОЛЖНО быть видно, какой вариант использован (версия ансамбля
  или эксперта) и сколько алертов поднял каждый эксперт.

**Ложные инциденты с адресов жертв и фона**

- **FR-022**: ДОЛЖЕН быть сформирован отчёт разбора инцидентов прогона 002 с источником из
  сетей жертв и фона: для каждого — число потоков по причинам (ответное направление, ошибка
  детектора, атака по разметке датасета).
- **FR-023**: По итогам разбора ДОЛЖНО быть внесено правило определения атакующей стороны
  (например, по направлению и роли сторон в потоке). Если правило признаёт поток ответным,
  алерт сохраняется, но атакующей стороной считается цель потока: по ней идут группировка
  в инцидент и объект действий плейбуков, а исходные адреса потока остаются в алерте
  с пометкой «ответный поток». Правило ДОЛЖНО опираться только на данные потока и прогона,
  но не на разметку датасета и не на знание сетей UNSW-NB15 (метки 003 остаются подсказкой,
  а не входом правила).
- **FR-024**: Эффект исправления ДОЛЖЕН измеряться на test-части `unsw_time`: число инцидентов
  с источником из сетей жертв и фона и число инцидентов с атакующим источником по разметке —
  до и после; результат записывается в журнал.

### Key Entities

- **Эксперт**: версионированный детектор — назначение (классы атак, аномальность),
  данные обучения, предобработка, порог, выходы, версия схемы признаков, метрики.
- **Мета-слой**: правило или модель объединения — входы (ответы экспертов), данные обучения,
  порог итогового вердикта.
- **Ансамбль**: версия набора «эксперты + мета-слой», которую использует цепочка; ссылки на
  версии экспертов, схема разделения данных, правило выбора.
- **Эксперимент ансамбля**: таблица одиночных экспертов, объединений и мета-слоя с метриками
  на val/test, результаты «скрытого класса», аудит артефактов, выбранный вариант.
- **Ответ эксперта**: для потока — уверенность эксперта и сработал ли он относительно своего
  порога.
- **Итоговый вердикт**: класс (включая «аномалия»), уверенность, превышен ли порог, ответы
  экспертов, объяснение.
- **Прогон, алерт, инцидент, действие, аудит** — как в 002/003; прогон дополнительно хранит
  версию ансамбля, алерт — ответы экспертов.
- **Отчёт разбора источников**: инциденты с источником из сетей жертв и фона, причины по
  потокам, результат до и после исправления.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Таблица эксперимента содержит каждого эксперта в одиночку, минимум одно простое
  объединение и мета-слой с macro PR-AUC и PR-AUC по классам на val и test; выбранный вариант
  по macro PR-AUC на test не ниже эксперта 002 (0.697) больше чем на 0.01, а при выборе
  ансамбля на val выполнено одно из условий FR-010 (записано, какое). Если ансамбль не прошёл
  ни одно условие — это записано
  в журнале с цифрами, и критерий считается выполненным честным отрицательным результатом.
- **SC-002**: В эксперименте «скрытый класс» итоговый вердикт ловит больше потоков скрытого
  класса, чем классификатор без этого класса, при этом доля нормальных потоков test, ставших
  алертами из-за детектора аномалий, не больше 1% (вдвое больше бюджета `anomaly_fpr` на val —
  запас на сдвиг между val и test); иначе отрицательный результат записан с цифрами.
- **SC-003**: Повторный эксперимент с тем же сидом даёт те же метрики и тот же выбор
  (расхождение 0); повторный сквозной прогон — те же вердикты, инциденты, серьёзности
  и предложения действий на 100%.
- **SC-004**: Сквозная команда с ансамблем на полной test-части `unsw_time` (около 282 тыс.
  потоков) завершается не дольше чем за 15 минут и укладывается в 16 ГБ памяти.
- **SC-005**: Все автоматические тесты 002 и 003 проходят без изменения их ожиданий, кроме
  явно добавленных полей и ожиданий группировки для ответных потоков (FR-023); на потоках,
  которые правило не признало ответными, инциденты совпадают с 002; прогоны 002/003
  открываются в консоли без ошибок и не перегруппировываются.
- **SC-006**: По деталям алерта аналитик за 30 секунд может сказать, какие эксперты сработали
  и почему поток признан атакой.
- **SC-007**: На test-части `unsw_time` после исправления 0 инцидентов, возникших только из-за
  ответного направления потоков; число инцидентов с источником из сетей жертв и фона меньше 14;
  0 инцидентов с атакующим источником по разметке теряется; каждый оставшийся инцидент
  с источником из этих сетей имеет причину в отчёте разбора.
- **SC-008**: Для каждого нового эксперта и мета-слоя в журнале есть вывод аудита артефактов;
  0 экспертов, получающих на вход поля `identity` или `time`.

## Assumptions

- Данные и артефакты — результаты фич 001–003: потоки, разбиения `unsw_time`,
  `unsw_cross_day`, `ctu13_scenario`, эксперт 002 (`lgbm`, macro PR-AUC test 0.697), база
  инцидентов со схемой 003. CTU-13 и UNSW-NB15 не смешиваются в одних обучающих данных.
- Разделение данных под мета-слой по умолчанию: эксперты учатся на train, мета-слой учится
  на части val с перекрёстным разбиением внутри val, порог выбирается на val; итог — на test.
  Точная схема (включая соблюдение временного порядка внутри val) выбирается на шаге plan.
- Кандидаты мета-слоя: простое правило и простая обучаемая модель над ответами экспертов;
  сложные схемы (нейросеть поверх экспертов) — только если простые не дают прироста и хватит
  времени. Выбор библиотек и моделей экспертов — на шаге plan, архитектуры v1 не переносятся
  по умолчанию.
- Класс «аномалия» по умолчанию получает среднюю базовую серьёзность; уточняется в конфигурации.
- Скрытый класс для FR-011 по умолчанию выбирается на шаге plan из классов с достаточным числом
  примеров в val и test (например, `exploits` или `dos`); допускается несколько.
- Разбор ложных инцидентов (US4) делается на прогоне test-части `unsw_time` с тем детектором,
  которым он был сделан в 002, чтобы число 14 было сопоставимо; эффект исправления на прогоне
  ансамбля записывается дополнительно.
- Аналитик, аутентификация, локальный доступ, защита консоли — без изменений относительно 003.
- Окружение: Windows 11, 16 ГБ RAM, 8 ГБ VRAM, без Docker и WSL2.
- Вне объёма: потоковая шина и работа в реальном времени, стенд на Hyper-V, эксперт по ботнетам
  на CTU-13, HIDS, переобучение на собственной «норме» стенда, массовые операции в консоли,
  контейнеры.
