# Feature Specification: SOC-консоль аналитика

**Feature Branch**: `003-soc-console-ui`

**Created**: 2026-09-24

**Status**: Draft

**Input**: User description: "003 SOC UI: веб-интерфейс аналитика SOC поверх цепочки 002 (детектор →
алерты → инциденты → SOAR-плейбуки с подтверждением аналитиком → API). Серверный рендеринг HTML
с HTMX (без SPA-фреймворка и сборки фронтенда), работает локально на 127.0.0.1 рядом
с существующим FastAPI. Аналитик видит список инцидентов с фильтрами (статус, серьёзность, класс
атаки, IP-источник) и сортировкой, открывает карточку инцидента (связанные алерты, таймлайн,
вероятности детектора, аудит действий), меняет статус и назначение, просматривает предложенные
SOAR-действия и подтверждает/отклоняет их (действия по-прежнему симулируются), видит журнал
аудита. Обзорная панель: счётчики инцидентов по статусу/серьёзности/классу, последние алерты.
Список обновляется без перезагрузки страницы. Имя аналитика — как в 002 (без аутентификации,
X-Analyst). Учитывать находку 002: часть инцидентов — с адресов жертв/фона, UI должен помогать
это увидеть."

## User Scenarios & Testing *(mandatory)*

Главный пользователь — аналитик SOC. В фиче 002 он работал с инцидентами только через
программный интерфейс; теперь у него появляется консоль в браузере: открыл страницу — увидел,
что происходит, разобрал инцидент, принял решение по действию. Второй пользователь — владелец
проекта на демонстрации: консоль — это то, что показывают вместо таблиц и JSON.

Консоль не добавляет новой логики детекции и реагирования: все правила (переходы статусов,
подтверждение действий, аудит, защита от одновременных изменений) остаются в цепочке 002,
консоль ими пользуется и понятно показывает их результат.

### User Story 1 - Список инцидентов и карточка (Priority: P1)

Аналитик открывает консоль, представляется своим именем и видит список инцидентов выбранного
прогона: серьёзность, статус, класс атаки, источник, цели, число алертов, время, ответственный.
Он фильтрует список (статус, серьёзность, класс атаки, IP-источник, ответственный) и сортирует
его, затем открывает карточку инцидента: сводка, почему такая серьёзность, алерты постранично
с уверенностью детектора, временная шкала алертов, история изменений и записи аудит-журнала
по этому инциденту.

**Why this priority**: это минимальная работающая консоль — без неё аналитику нечего открывать
в браузере. Всё остальное (решения, панель, обновление) опирается на список и карточку.

**Independent Test**: поднять консоль на данных готового прогона 002, открыть список,
применить каждый фильтр и сортировку, открыть карточку инцидента и сверить её содержимое
с данными API 002.

**Acceptance Scenarios**:

1. **Given** готовый прогон с инцидентами, **When** аналитик открывает консоль, **Then** видит
   список инцидентов последнего прогона, по умолчанию упорядоченный по серьёзности (сначала
   критические), затем по времени (сначала новые), постранично.
2. **Given** список, **When** аналитик задаёт фильтры по статусу, серьёзности, классу атаки,
   IP-источнику и ответственному (в любом сочетании), **Then** остаются только подходящие
   инциденты, число найденных показано, а выбранные фильтры сохраняются в адресе страницы,
   так что ссылкой можно поделиться и вернуться к тому же виду.
3. **Given** список, **When** аналитик сортирует его по серьёзности, времени начала, времени
   последнего алерта или числу алертов, **Then** порядок меняется без перезагрузки страницы.
4. **Given** инцидент, **When** аналитик открывает карточку, **Then** видны: ключ группировки
   (источник и класс), цели, интервал времени, число алертов, серьёзность с объяснением,
   статус, резолюция, ответственный, предложенное действие с сработавшим правилом, история
   изменений и записи аудит-журнала по инциденту.
5. **Given** карточку инцидента с тысячами алертов, **When** аналитик листает алерты, **Then**
   они выводятся постранично с контекстом (источник, цель, порты, протокол, время, класс,
   уверенность), а карточка открывается так же быстро, как для инцидента с одним алертом.
6. **Given** карточку, **When** аналитик смотрит временную шкалу, **Then** видно, как алерты
   распределены во времени внутри интервала инцидента.
7. **Given** алерт в карточке, **When** аналитик раскрывает его, **Then** видит вероятности
   детектора по классам для этого потока и порог срабатывания.
8. **Given** несколько прогонов, **When** аналитик выбирает другой прогон, **Then** список,
   фильтры и счётчики относятся к выбранному прогону.

### User Story 2 - Решения аналитика из консоли (Priority: P2)

Из карточки инцидента аналитик берёт инцидент себе (или назначает другого), переводит его
«в работу», закрывает с резолюцией «подтверждён» или «ложное срабатывание» и комментарием,
подтверждает или отклоняет предложенное действие. После подтверждения он видит, что именно
было бы сделано (симуляция). Каждое решение тут же отражается в истории и аудит-журнале.

**Why this priority**: консоль без решений — только просмотрщик; ради решений аналитик её
и открывает. Правила при этом те же, что в 002 (принцип V: человек в контуре, только симуляция).

**Independent Test**: на заранее созданном инциденте пройти из консоли: назначить, перевести
в работу, подтвердить действие, закрыть; на другом — отклонить действие с комментарием;
проверить историю и аудит-журнал; попробовать недопустимые операции и увидеть понятные ошибки.

**Acceptance Scenarios**:

1. **Given** инцидент без ответственного, **When** аналитик нажимает «взять себе», **Then**
   ответственным становится текущий аналитик, изменение попадает в историю с автором
   и временем, а список показывает нового ответственного.
2. **Given** инцидент, **When** аналитик назначает ответственным другое имя или снимает
   назначение, **Then** изменение сохраняется и попадает в историю.
3. **Given** инцидент «новый», **When** аналитик переводит его «в работу», а затем закрывает
   с резолюцией и комментарием, **Then** статус меняется, карточка и список обновляются без
   перезагрузки страницы, переходы видны в истории.
4. **Given** закрытие инцидента, **When** резолюция не выбрана, **Then** консоль не даёт
   отправить решение и объясняет, что резолюция обязательна.
5. **Given** предложенное действие, **When** аналитик подтверждает его после явного вопроса
   «вы уверены?» с описанием действия и объекта, **Then** действие помечено выполненным,
   показана запись симуляции («что было бы сделано»), и в интерфейсе явно сказано, что
   реальных изменений в сети нет.
6. **Given** предложенное действие, **When** аналитик отклоняет его, **Then** консоль требует
   комментарий, действие помечается отклонённым, а кнопки решения по нему исчезают.
7. **Given** два аналитика открыли один инцидент, **When** второй отправляет решение на основе
   устаревшего вида, **Then** решение не применяется, консоль сообщает о конфликте, показывает
   актуальное состояние и предлагает повторить.
8. **Given** любая операция, меняющая состояние, **When** имя аналитика не задано, **Then**
   консоль не отправляет её и просит представиться.

### User Story 3 - Подсказки о подозрительных источниках (Priority: P3)

Аналитик видит в списке и карточке метку, если источник инцидента, вероятно, не атакующий:
адрес относится к сети жертв или к фоновому трафику, либо этот же адрес выступает целью в других
инцидентах прогона (признак ответного направления). По метке можно отфильтровать такие
инциденты, увидеть объяснение и закрыть их как ложные срабатывания.

**Why this priority**: в прогоне 002 17 из 66 инцидентов пришли с адресов жертв (149.171.126.x)
и фона (59.166.0.x). Без подсказки аналитик тратит время на каждый такой инцидент, а на
демонстрации они портят впечатление от консоли. Исправление самой группировки — задача
детекции, а консоль должна хотя бы сделать проблему видимой.

**Independent Test**: на прогоне 002 проверить, что все инциденты с источниками из заданных
в конфигурации сетей жертв и фона помечены, что метка «источник — цель в других инцидентах»
ставится ровно там, где адрес встречается среди целей, и что фильтр по метке их отбирает.

**Acceptance Scenarios**:

1. **Given** в конфигурации заданы именованные сети (например, «жертвы» и «фон»), **When**
   источник инцидента попадает в одну из них, **Then** в списке и карточке видна метка
   с названием сети.
2. **Given** адрес-источник инцидента встречается среди целей других инцидентов того же
   прогона, **When** аналитик смотрит инцидент, **Then** видна метка «источник — цель в других
   инцидентах» со ссылками на эти инциденты.
3. **Given** метки, **When** аналитик включает фильтр «только подозрительные источники» или
   «скрыть подозрительные источники», **Then** список показывает соответствующие инциденты.
4. **Given** помеченный инцидент, **When** аналитик открывает карточку, **Then** видит, почему
   поставлена метка (какая сеть или какие инциденты), и может закрыть его как «ложное
   срабатывание» обычным путём из US2.
5. **Given** метки, **When** они вычисляются, **Then** серьёзность, статус и предложенное
   действие инцидента не меняются — метка только подсказывает.

### User Story 4 - Обзорная панель и живое обновление (Priority: P4)

На стартовой странице аналитик видит сводку выбранного прогона: инциденты по статусам,
серьёзности и классам атак, сколько действий ждут решения, сколько инцидентов без
ответственного, последние алерты. Счётчики кликабельны — ведут в список с соответствующим
фильтром. Панель и список сами подтягивают изменения (новый прогон, решения других аналитиков)
без перезагрузки страницы.

**Why this priority**: панель — первое, что видно на демонстрации, и способ понять обстановку
за секунды; но работать с инцидентами можно и без неё, поэтому она после решений и подсказок.

**Independent Test**: открыть панель, сверить счётчики с данными API 002, кликнуть по счётчику
и получить отфильтрованный список; в другом окне изменить инцидент или загрузить новый прогон
и убедиться, что панель и список обновились сами в пределах интервала обновления.

**Acceptance Scenarios**:

1. **Given** прогон, **When** аналитик открывает панель, **Then** видит счётчики инцидентов
   по статусу, серьёзности и классу атаки, число действий «предложено», число инцидентов без
   ответственного и число инцидентов с подозрительным источником; все числа совпадают с API.
2. **Given** панель, **When** аналитик кликает по счётчику, **Then** открывается список
   с фильтром, дающим ровно это число инцидентов.
3. **Given** панель, **When** аналитик смотрит блок последних алертов, **Then** видит
   последние (по времени потока) алерты прогона с классом, уверенностью, источником, целью
   и ссылкой на инцидент.
4. **Given** открытые панель или список, **When** другой аналитик меняет инцидент или появляется
   новый прогон, **Then** изменения видны без перезагрузки страницы не позже чем через интервал
   обновления, а о появлении нового прогона консоль сообщает и предлагает на него переключиться.
5. **Given** аналитик вводит комментарий или заполняет форму, **When** срабатывает
   автообновление, **Then** введённое не теряется.

### User Story 5 - Журнал аудита (Priority: P5)

Аналитик (или проверяющий) открывает отдельную страницу аудит-журнала: все записи с фильтрами
по аналитику, типу события и инциденту, постранично, новые сверху. Из записи можно перейти
к инциденту.

**Why this priority**: аудит уже виден в карточке инцидента (US1); отдельная страница нужна
для проверки «кто что делал» по всему прогону, но не блокирует работу аналитика.

**Independent Test**: выполнить несколько решений из консоли, открыть журнал, отфильтровать
по аналитику и типу события и сверить записи с API 002.

**Acceptance Scenarios**:

1. **Given** решения аналитиков, **When** открывается журнал, **Then** каждая запись показывает
   время, автора, событие, инцидент, действие и детали на русском языке, новые сверху.
2. **Given** журнал, **When** заданы фильтры по аналитику, типу события и инциденту, **Then**
   показаны только подходящие записи.
3. **Given** журнал, **When** аналитик ищет возможность изменить или удалить запись, **Then**
   такой возможности в консоли нет.

---

### Edge Cases

- Хранилище пустое (ни одного прогона): консоль открывается и объясняет, какой командой
  получить первый прогон, а не показывает ошибку.
- Прогон без инцидентов (например, PCAP без атак): список пуст с понятным сообщением, панель
  показывает нули.
- Фильтры не дают ни одного инцидента: пустой список с сообщением и кнопкой «сбросить фильтры».
- Некорректное значение фильтра в адресе страницы (опечатка в серьёзности, неверный IP):
  фильтр игнорируется с предупреждением, остальные применяются.
- Инцидент по ссылке не найден (другой прогон, опечатка): понятная страница «не найдено»
  со ссылкой на список.
- Цепочка 002 возвращает ошибку (недопустимый переход, конфликт, неверный запрос): консоль
  показывает сообщение 002 на русском рядом с тем элементом, где сделано действие, и не теряет
  введённый комментарий.
- Сервис недоступен во время автообновления: консоль показывает, что данные могли устареть,
  и продолжает попытки, не сбрасывая страницу.
- В браузере отключены скрипты: основные страницы (список, карточка, журнал) открываются
  и читаются; фильтры работают через обычную отправку формы.
- Очень длинный список целей или комментарий: отображение не ломает раскладку (сокращение
  с возможностью раскрыть).
- Имя аналитика содержит спецсимволы или разметку: выводится как текст, а не выполняется.
- Инцидент закрыт — кнопки смены статуса скрыты, назначение по-прежнему можно поменять
  (не меняет статус и резолюцию).
- Адрес попадает в несколько именованных сетей: показываются все метки.

## Requirements *(mandatory)*

### Functional Requirements

**Доступ и аналитик**

- **FR-001**: Консоль ДОЛЖНА открываться в браузере на этой же машине и не ДОЛЖНА быть доступна
  из сети по умолчанию.
- **FR-002**: Аналитик ДОЛЖЕН представиться именем перед первой операцией, меняющей состояние;
  имя запоминается в браузере, видно в шапке и может быть сменено. Проверка подлинности не
  требуется (как в 002).
- **FR-003**: Все операции, меняющие состояние, ДОЛЖНЫ выполняться от имени текущего аналитика
  через правила цепочки 002 (переходы статусов, подтверждение действий, оптимистичная
  блокировка, аудит); консоль НЕ ДОЛЖНА обходить или дублировать эти правила.

**Список инцидентов**

- **FR-004**: Список ДОЛЖЕН показывать для каждого инцидента: серьёзность, статус, резолюцию,
  класс атаки, источник, цели (сокращённо), число алертов, время начала и последнего алерта,
  ответственного, состояние предложенного действия и метки подозрительного источника.
- **FR-005**: Список ДОЛЖЕН фильтроваться по прогону, статусу, серьёзности, классу атаки,
  IP-источнику (точный адрес или префикс сети), ответственному (включая «без ответственного»),
  состоянию действия и метке подозрительного источника — в любом сочетании.
- **FR-006**: Список ДОЛЖЕН сортироваться по серьёзности, времени начала, времени последнего
  алерта и числу алертов в обе стороны; по умолчанию — серьёзность по убыванию, затем время
  по убыванию.
- **FR-007**: Список ДОЛЖЕН выводиться постранично; фильтры, сортировка и страница ДОЛЖНЫ
  отражаться в адресе страницы, чтобы вид можно было открыть повторно по ссылке.
- **FR-008**: Смена фильтров, сортировки и страницы ДОЛЖНА обновлять список без полной
  перезагрузки страницы.

**Карточка инцидента**

- **FR-009**: Карточка ДОЛЖНА показывать все поля инцидента из 002, объяснение серьёзности,
  предложенное действие с правилом и состоянием, историю изменений и записи аудит-журнала
  по инциденту.
- **FR-010**: Алерты инцидента ДОЛЖНЫ выводиться постранично с контекстом потока (источник,
  цель, порты, протокол, время, класс, уверенность); для алерта ДОЛЖНЫ быть доступны
  вероятности детектора по классам и порог срабатывания.
- **FR-011**: Карточка ДОЛЖНА показывать временную шкалу алертов инцидента (распределение
  числа алертов по времени внутри интервала инцидента).

**Решения**

- **FR-012**: Инцидент ДОЛЖЕН иметь поле «ответственный»; аналитик ДОЛЖЕН мочь взять инцидент
  себе, назначить другое имя или снять назначение. Каждое изменение ДОЛЖНО попадать в историю
  инцидента и аудит-журнал с автором и временем.
- **FR-013**: Аналитик ДОЛЖЕН мочь менять статус инцидента только по допустимым переходам 002;
  консоль ДОЛЖНА предлагать только допустимые переходы, требовать резолюцию при закрытии
  и позволять добавить комментарий.
- **FR-014**: Аналитик ДОЛЖЕН мочь подтвердить или отклонить предложенное действие; перед
  подтверждением консоль ДОЛЖНА явно спросить согласие, назвав действие и объект; отклонение
  ДОЛЖНО требовать комментарий.
- **FR-015**: После подтверждения консоль ДОЛЖНА показывать запись симуляции и явное
  указание, что реальных изменений сети и хостов не было.
- **FR-016**: При конфликте одновременных изменений консоль ДОЛЖНА сообщить о нём, показать
  актуальное состояние и не применять устаревшее решение.
- **FR-017**: Ошибки цепочки 002 ДОЛЖНЫ показываться аналитику на русском рядом с элементом,
  где выполнено действие; введённые данные формы при этом не теряются.

**Подозрительные источники**

- **FR-018**: В конфигурации ДОЛЖЕН задаваться список именованных сетей (название, диапазоны
  адресов, роль: «жертвы», «фон» и т. п.); по умолчанию — сети жертв и фона UNSW-NB15.
- **FR-019**: Инцидент ДОЛЖЕН получать метку, если его источник входит в именованную сеть
  с ролью «жертвы» или «фон», либо если этот адрес встречается среди целей других инцидентов
  того же прогона. У метки ДОЛЖНО быть объяснение (сеть или список инцидентов-ссылок).
- **FR-020**: Метки НЕ ДОЛЖНЫ менять серьёзность, статус, резолюцию и предложенное действие;
  решение о закрытии остаётся за аналитиком.

**Обзорная панель и обновление**

- **FR-021**: Панель ДОЛЖНА показывать для выбранного прогона: число инцидентов по статусам,
  серьёзности и классам атак; число действий, ждущих решения; число инцидентов без
  ответственного; число инцидентов с подозрительным источником; сводку прогона (потоки,
  алерты, инциденты, детектор, время); последние алерты (по умолчанию 20).
- **FR-022**: Каждый счётчик панели ДОЛЖЕН вести в список с фильтром, который даёт ровно это
  число инцидентов.
- **FR-023**: Панель и список ДОЛЖНЫ обновляться без перезагрузки страницы с настраиваемым
  интервалом (по умолчанию 10 секунд); появление нового прогона ДОЛЖНО сообщаться аналитику
  с предложением переключиться, без самопроизвольной смены прогона.
- **FR-024**: Автообновление НЕ ДОЛЖНО сбрасывать введённые данные форм, раскрытые элементы
  и текущую позицию в списке.
- **FR-025**: При недоступности сервиса консоль ДОЛЖНА показывать, что данные могут быть
  устаревшими, и восстанавливаться сама, когда сервис снова доступен.

**Журнал аудита**

- **FR-026**: Отдельная страница ДОЛЖНА показывать аудит-журнал постранично, новые сверху,
  с фильтрами по аналитику, типу события и инциденту; события и детали — на русском языке;
  из записи есть переход к инциденту.
- **FR-027**: Консоль НЕ ДОЛЖНА давать возможности изменить или удалить запись аудит-журнала.

**Общее**

- **FR-028**: Все надписи, сообщения и подписи значений (статусы, серьёзность, типы действий,
  события аудита) ДОЛЖНЫ быть на русском языке; классы атак — в исходных названиях датасета.
- **FR-029**: Любые данные, пришедшие от пользователя или из трафика (имена, комментарии,
  адреса), ДОЛЖНЫ выводиться как текст и не исполняться как разметка или скрипт.
- **FR-030**: Консоль НЕ ДОЛЖНА требовать отдельной сборки клиентской части и сторонних сервисов
  из интернета во время работы: всё нужное поставляется вместе с проектом.
- **FR-031**: Консоль ДОЛЖНА запускаться одной командой вместе с программным интерфейсом 002,
  который остаётся доступен и работает как прежде.
- **FR-032**: Основные страницы (панель, список, карточка, журнал) ДОЛЖНЫ открываться и читаться
  при отключённых скриптах в браузере; решения при этом допускается выполнять только
  с включёнными скриптами.

### Key Entities

- **Инцидент** (из 002): добавляется поле «ответственный» (имя аналитика или пусто); его
  изменения — в истории и аудите.
- **Именованная сеть**: название, диапазоны адресов, роль («жертвы», «фон», «инфраструктура»…);
  задаётся в конфигурации.
- **Метка подозрительного источника**: вычисляется для инцидента — вид (сеть жертв, сеть фона,
  источник — цель в других инцидентах) и объяснение; не хранится как решение.
- **Вид списка**: сочетание фильтров, сортировки и страницы, закодированное в адресе страницы.
- **Сводка панели**: счётчики и последние алерты для выбранного прогона.
- **Аналитик** (из 002): имя, указанное в консоли; хранится в браузере.
- Алерт, вердикт (вероятности по классам), действие, прогон, запись аудит-журнала — без
  изменений из 002.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На данных полного прогона 002 (66 инцидентов, ~8 тыс. алертов) панель, список
  с любым сочетанием фильтров и карточка самого большого инцидента открываются аналитику
  не дольше чем за 1 секунду.
- **SC-002**: Аналитик, впервые открывший консоль, за 2 минуты находит самый серьёзный новый
  инцидент, говорит, кто атакует, кого и что предлагается сделать, и принимает решение
  по действию — без чтения документации.
- **SC-003**: 100% инцидентов прогона 002 с источниками из сетей жертв и фона (17 из 66) имеют
  метку, и ни один инцидент с источником вне этих сетей и не встречающимся среди целей не
  помечен ошибочно.
- **SC-004**: Все числа на панели совпадают с данными API 002 на 100%, и клик по каждому
  счётчику даёт список ровно из этого числа инцидентов.
- **SC-005**: 0 решений, выполненных в обход правил 002: каждое решение из консоли есть
  в истории/аудите с автором, недопустимые переходы и устаревшие решения отклоняются
  с понятным сообщением (проверяется автоматическими тестами для каждого вида решения).
- **SC-006**: Изменение, сделанное в другом окне, видно на открытых панели и списке не позже
  чем через 15 секунд без действий аналитика.
- **SC-007**: Все пользовательские сценарии US1–US5 покрыты автоматическими тестами и проходят;
  отдельный тест подтверждает, что введённая в комментарий разметка выводится как текст.
- **SC-008**: Консоль запускается одной командой на рабочей машине без доступа в интернет.

## Assumptions

- Данные и правила — из фичи 002: хранилище прогонов, инцидентов, алертов, действий и аудита,
  вердикты с вероятностями по классам, переходы статусов, оптимистичная блокировка. Поле
  «ответственный» — единственное расширение модели 002; допустимо, чтобы оно было задано
  и для закрытых инцидентов.
- Техническое ограничение от владельца: интерфейс — серверный рендеринг страниц с HTMX для
  частичного обновления, без SPA-фреймворка и без сборки фронтенда; работает на 127.0.0.1
  рядом с существующим сервисом 002. Детали (шаблоны, стили, раскладка процессов) — на шаге plan.
- Аналитик — одно имя без пароля и ролей; несколько аналитиков = несколько окон браузера на этой
  же машине. Настоящая аутентификация и доступ из сети — вне объёма.
- Запуск новых прогонов (детектор, PCAP) остаётся в командной строке 002; консоль их только
  показывает и сообщает о новых.
- Именованные сети по умолчанию: «жертвы» — 149.171.126.0/24, «фон» — 59.166.0.0/24 (наблюдения
  из прогона 002); могут уточняться в конфигурации.
- Метки подозрительного источника вычисляются в пределах одного прогона; исправление самой
  группировки (по паре адресов, отбрасывание ответных направлений) — задача будущей фичи
  детекции, а не консоли.
- Массовые операции (закрыть несколько инцидентов разом) — вне объёма; закрытие помеченных
  инцидентов выполняется по одному обычным путём.
- Основной браузер — актуальный Chromium/Firefox на десктопе; мобильная раскладка — вне объёма,
  но страницы не должны ломаться на узком окне.
- Интервал автообновления по умолчанию — 10 секунд; обновление опросом, без постоянного
  соединения.
- Временная шкала — простая гистограмма числа алертов по времени; интерактивные графики
  (масштабирование, выделение) — вне объёма.
- Вне объёма: новые детекторы и мета-слой, изменение правил плейбуков и серьёзности,
  повторное открытие закрытых инцидентов, экспорт отчётов, уведомления вне консоли, стенд,
  контейнеры, HIDS.
