# Research: SOC-консоль аналитика (003)

Решения фазы 0. Формат: решение → почему → что ещё рассматривали. Исходные точки — код
фичи 002 (`src/mlsiem/soc/`: `store.py`, `api.py`, `config.py`) и её контракт
[api.md](../002-detection-incident-chain/contracts/api.md).

## R1. Где живёт консоль и как она получает данные

- **Решение**: новый подпакет `src/mlsiem/ui/` — FastAPI-роутер со страницами и фрагментами,
  который подключается в то же приложение, что и API 002 (`soc.api.create_app`). Страницы
  на корне (`/`, `/incidents`, …), API остаётся на `/api/v1`, статика — `/static`. Обработчики
  консоли вызывают функции `soc.store` напрямую — ровно те же, что вызывает API.
- **Почему**: один процесс и одна команда запуска (FR-031); все правила (переходы, версии,
  аудит) уже сосредоточены в `store`, а API — тонкий слой над ним. Консоль становится вторым
  тонким слоем над тем же ядром, поэтому обойти правила 002 она не может (FR-003), а ошибки
  приходят теми же исключениями `NotFound / InvalidTransition / Conflict / BadRequest`
  с готовым русским текстом (FR-017).
- **Альтернативы**: консоль ходит в собственный API по HTTP (`httpx`) — лишний сетевой круг,
  двойная сериализация и проблема «под каким именем» (X-Analyst в latin-1, а имя в консоли
  может быть кириллицей). Отдельный процесс/порт — усложняет запуск и не даёт ничего взамен.

## R2. Рендеринг и частичное обновление

- **Решение**: серверные шаблоны Jinja2 (уже в зависимостях 001) + htmx 2.x. Каждая страница
  собирается из фрагментов (`_incident_table.html`, `_action_panel.html`, …). Обработчик
  отдаёт целую страницу на обычный запрос и только фрагмент, если есть заголовок `HX-Request`
  (кроме `HX-Boosted`). Смена фильтров/сортировки/страницы — `hx-get` с `hx-push-url`, так что
  адрес страницы всегда отражает вид (FR-007, FR-008).
- **Почему**: выбор владельца (без SPA и сборки). Шаблоны уже знакомы по отчётам 001. Схема
  «страница = набор фрагментов» даёт работу без скриптов даром (FR-032): без JS фильтр — это
  обычная GET-форма, ссылка пагинации — обычная ссылка.
- **Альтернативы**: Alpine.js поверх htmx — не нужен, интерактивности (раскрыть алерт,
  диалог подтверждения) хватает htmx + `<details>` + `<dialog>`; React/Vue — исключены
  ограничением.

## R3. Поставка htmx и стилей без интернета

- **Решение**: файл `htmx.min.js` конкретной версии 2.x кладётся в
  `src/mlsiem/ui/static/vendor/` (лицензия 0BSD — текст рядом), версия и SHA-256 записываются
  в `static/vendor/README.md` и проверяются тестом. Стили — свой `console.css` (~300 строк,
  CSS-переменные, светлая/тёмная тема через `prefers-color-scheme`), без CSS-фреймворка. Свой
  маленький `console.js` (без inline-скриптов) — только индикатор «данные могут устареть»,
  подстановка CSRF-заголовка и диалоги подтверждения.
- **Почему**: FR-030 — ни CDN, ни сборки; тест с хешем гарантирует, что файл никто молча
  не заменил. Без CSS-фреймворка консоль меньше и её проще объяснить.
- **Альтернативы**: CDN — нарушает FR-030 и SC-008; Pico/Bootstrap — лишние 50–200 КБ ради
  таблиц и кнопок.

## R4. Имя аналитика

- **Решение**: имя хранится в cookie `mlsiem_analyst` (URL-кодированное, до 64 символов,
  `SameSite=Strict`, `HttpOnly` не нужен — секрета нет). Устанавливается формой
  `POST /analyst`, показывается в шапке, меняется там же. Изменяющие операции без cookie
  отклоняются с просьбой представиться (FR-002, US2 сц. 8). Имя обрезается по краям, пустое
  и содержащее управляющие символы — отклоняется.
- **Почему**: сервер должен знать автора в каждой форме, а cookie приходит сам, без JS. В
  отличие от заголовка `X-Analyst`, cookie спокойно переносит кириллицу (через URL-кодирование).
- **Альтернативы**: localStorage + JS-подстановка — не работает без скриптов и не видна
  серверу при полном рендере; поле «имя» в каждой форме — неудобно и провоцирует опечатки.

## R5. Поле «ответственный» и миграция базы

- **Решение**: `incidents.assignee TEXT NULL` + новое событие аудита `incident_assigned`.
  В `store.py` появляется версия схемы (`PRAGMA user_version`): 0/1 → 2. Миграция v2:
  `ALTER TABLE incidents ADD COLUMN assignee`; пересоздание `audit_log` с расширенным
  `CHECK (event IN …)` (перенос строк с сохранением `entry_id`, затем триггеры заново);
  индекс `alerts(run_id, first_seen_ms)` для панели. Вся миграция — одна транзакция,
  `init_db` вызывает её идемпотентно.
- **Почему**: CHECK на событиях аудита в SQLite нельзя изменить `ALTER`-ом, а старые базы
  `var/soc.db` уже содержат аудит — терять его нельзя (принцип V). `DROP TABLE` внутри
  миграции не вызывает триггеров удаления (в SQLite неявный DELETE при DROP триггеры не
  запускает), поэтому запрет на UPDATE/DELETE в обычной работе остаётся. Миграция покрывается
  тестом: база 002 с записями → миграция → записи и их `entry_id` на месте, триггеры работают.
- **Альтернативы**: писать назначение событием `incident_status_changed` — путает журнал;
  «пересоздать базу прогоном» — теряет решения аналитиков.

## R6. Решение не ответственным (FR-012a)

- **Решение**: предупреждение — поведение консоли: при отправке формы решения, если
  `assignee` задан и не равен текущему имени, htmx показывает `<dialog>` «Ответственный — X.
  Всё равно продолжить?», а форма несёт `ack_not_assignee=1`. Сервер консоли без этого флага
  возвращает фрагмент с тем же вопросом вместо применения (так работает и без JS, и при гонке,
  если назначение сменилось, пока открыта карточка). Отметка в аудите — в `store`: функции
  `change_status`, `confirm_action`, `reject_action` сами читают `assignee` в своей транзакции
  и добавляют в `details` поля `assignee` и `by_non_assignee: true|false`.
- **Почему**: отметка в аудите должна быть честной независимо от интерфейса (API тоже),
  поэтому считается в ядре под той же блокировкой, что и решение. Предупреждение — чисто UX,
  API 002 его не требует (обратная совместимость).
- **Альтернативы**: передавать флаг из UI в store — тогда API-клиент мог бы его не передать
  и «спрятать» факт.

## R7. Защита от межсайтовых запросов (FR-029a)

- **Решение**: две независимые проверки на каждый изменяющий запрос консоли (`POST` вне
  `/api/v1`):
  1. **Источник**: если есть `Sec-Fetch-Site`, он должен быть `same-origin`; иначе, если есть
     `Origin`, он должен совпадать с адресом консоли (`http://127.0.0.1:<port>` или
     `http://localhost:<port>`). Нет ни того, ни другого — переходим к проверке токена.
  2. **Токен** (подписанный double-submit): при первом заходе сервер ставит cookie
     `mlsiem_csrf` = случайные 32 байта; токен формы = `HMAC-SHA256(secret, cookie) + метка
     времени`, подпись действительна 12 часов. Токен приходит скрытым полем `csrf_token` (без JS)
     или заголовком `X-CSRF-Token` (htmx, `hx-headers` на `<body>`). `secret` — случайный на
     процесс; перезапуск сервера делает старые токены недействительными → ответ «страница
     устарела, обновите её», введённый комментарий возвращается в форму (edge case спеки).
  Отказ: `403`, фрагмент с сообщением, `logging.warning` в логгер `mlsiem.ui.security`
  (метод, путь, Origin, Sec-Fetch-Site) — без изменений в базе. Плюс заголовки
  `X-Frame-Options: DENY` и `Content-Security-Policy: default-src 'self'; frame-ancestors
  'none'` на всех страницах консоли (защита от кликджекинга кнопки «подтвердить»).
- **Почему**: локальный адрес от CSRF не защищает — браузер сам отправит форму с чужой
  страницы на `127.0.0.1`. Проверка источника отсекает современные браузеры, токен — всё
  остальное; подпись токена секретом не даёт подложить свой cookie. Это стандартная схема
  OWASP, без внешних зависимостей (hmac + secrets из stdlib).
- **API 002** этой проверки не требует: его изменяющие запросы — JSON с кастомным заголовком
  `X-Analyst`, а такой запрос с чужого сайта браузер отправит только после CORS-preflight,
  который API не разрешает (CORS-middleware нет). Это фиксируется тестом (OPTIONS без CORS →
  нет разрешающих заголовков).
- **Альтернативы**: библиотеки `starlette-csrf`/`fastapi-csrf-protect` — лишняя зависимость
  ради ~60 строк; только `SameSite=Strict` cookie — не защищает старые браузеры и не
  проверяется тестом так же явно.

## R8. Подсказки о подозрительных источниках (US3)

- **Решение**: модуль `soc/flags.py`, чистая функция `source_flags(incidents, networks)` для
  всех инцидентов одного прогона. Метки:
  - `network:<name>` — источник входит в именованную сеть с ролью `victims` или `background`
    (`ipaddress.ip_network`, IPv4 и IPv6);
  - `target_elsewhere` — адрес источника встречается в `targets` других инцидентов того же
    прогона; объяснение — список этих `incident_id` (до 10 ссылок и «ещё N»).
  Сети — новый раздел `networks` в `configs/soc.yaml` (название, роль, список CIDR);
  по умолчанию `149.171.126.0/24` («жертвы UNSW-NB15») и `59.166.0.0/24` («фон UNSW-NB15»).
  Метки вычисляются на лету (не хранятся), кэшируются в памяти по `(run_id, max(updated_at))`
  — на прогоне из сотен инцидентов расчёт занимает миллисекунды.
- **Почему**: метка — подсказка, а не решение (FR-020), поэтому ей не место в таблице
  инцидентов; изменить список сетей в конфиге и сразу увидеть результат удобнее, чем
  пересчитывать базу. Функция чистая — легко проверить на данных прогона 002 (SC-003: 14 из 66).
- **Альтернативы**: сохранять метки при прогоне — пришлось бы перезапускать прогон после
  правки конфига; исправлять группировку — вне объёма (задача детекции).

## R9. Фильтры, сортировка и «ответственный» в хранилище и API

- **Решение**: `store.list_incidents` расширяется параметрами: `src_ip` (точный адрес или
  CIDR-префикс — через список адресов источников прогона, отфильтрованных `ipaddress`),
  `assignee` (имя или `__none__`), `action_state`, `incident_ids` / `exclude_ids` (для
  фильтра по меткам) и `sort` из белого списка (`severity`, `first_seen`, `last_seen`,
  `n_alerts`, каждый с `asc|desc`; вторичный ключ — `incident_id` для стабильного порядка).
  Новая функция `store.assign(conn, incident_id, analyst, assignee, expected_version, comment)`.
  API 002 получает те же параметры и `POST /incidents/{id}/assign` — только добавления,
  обратная совместимость v1 сохраняется (порядок по умолчанию в API не меняется).
  Порядок по умолчанию в консоли — серьёзность ↓, затем время начала ↓ (спека US1 сц. 1).
- **Почему**: одна реализация фильтров для консоли и API — одна пачка тестов; белый список
  сортировок исключает SQL-инъекцию через параметр.
- **Альтернативы**: фильтровать в Python после выборки — не масштабируется на большие прогоны
  и ломает постраничность.

## R10. Вероятности детектора и порог (FR-010)

- **Решение**: вероятности по классам не в SQLite, а в `var/runs/<run_id>/verdicts.parquet`
  (столбцы `p_<класс>`). Консоль читает их по требованию, когда аналитик раскрывает алерт:
  `pl.scan_parquet(...).filter(pl.col("flow_uid") == uid)` — фрагмент `hx-get` в `<details>`.
  Порог: начиная с 003 прогон записывает `threshold` и `classes` детектора в `runs.summary`;
  для старых прогонов — из `models/detector/model_card.json`, если `detector_version`
  совпадает, иначе «порог неизвестен (детектор прогона заменён)». Нет файла вердиктов —
  «вероятности недоступны», без ошибки страницы.
- **Почему**: сотни тысяч вердиктов в БД не нужны; чтение одной строки из parquet с
  отбором по столбцу занимает десятки миллисекунд.
- **Альтернативы**: копировать вероятности алертов в таблицу `alerts` при прогоне — ещё
  10 столбцов на каждый алерт ради редкого раскрытия; можно сделать позже, если окажется
  медленно.

## R11. Гистограмма и хронология (FR-011, FR-011a)

- **Решение**: гистограмма — SQL-группировка алертов инцидента по корзинам
  (`(first_seen_ms − start) / width`, 40 корзин, для короткого интервала — не уже 1 с) и
  серверный inline-SVG в шаблоне (столбики, подписи начала/конца, число в `<title>` для
  подсказки). Хронология — слияние: первый и последний алерт (время трафика), создание
  инцидента (`created_at`), записи аудита инцидента (предложение, назначения, смены статуса,
  решения, симуляция). Сортировка по времени; у каждой строки явная подпись «время трафика»
  или «время решения», время в UTC.
- **Почему**: SVG без JS — работает без скриптов и не тянет библиотеку графиков; всё строится
  из уже существующих данных. Аудит — единственный полный источник решений (история
  инцидента не содержит решений по действию).
- **Альтернативы**: Chart.js/uPlot — лишняя библиотека ради одного статичного графика
  (интерактивность вне объёма).

## R12. Автообновление, «устаревшие данные» и сохранность ввода

- **Решение**: опрос htmx: `hx-trigger="every {{ refresh }}s"` только на «читающих»
  контейнерах — таблица списка, счётчики панели, лента последних алертов, баннер новых
  прогонов. Формы (статус, назначение, решения) в опрашиваемые контейнеры не входят, поэтому
  опрос их не трогает (FR-024). Карточка инцидента не перерисовывается опросом целиком: она
  опрашивает лёгкий фрагмент-«штамп» с `version` инцидента и действия; если версия изменилась,
  показывается полоса «инцидент изменён другим аналитиком — обновить», а поля ввода остаются.
  Раскрытые `<details>` и позиция в списке сохраняются: список меняется `hx-swap="outerHTML"`
  только если сервер вернул другое содержимое (ETag по `(run_id, фильтры, max(updated_at),
  count)`, при совпадении — `204`, htmx ничего не меняет). Ошибки опроса (`htmx:sendError`,
  `htmx:responseError`) включают в `console.js` полосу «данные могут быть устаревшими»,
  первый успешный ответ её снимает (FR-025). Новый прогон: баннер с кнопкой «переключиться»,
  выбранный прогон сам не меняется (FR-023). Интервал — `ui.refresh_seconds` в `soc.yaml`
  (по умолчанию 10).
- **Почему**: опрос проще постоянного соединения и достаточен для одного-двух аналитиков
  (SC-006: ≤ 15 с при интервале 10 с). ETag/204 убирает мигание и сброс прокрутки.
- **Альтернативы**: SSE/WebSocket — отдельное расширение htmx и долгие соединения ради
  выигрыша в секунды; вне объёма по спеке.

## R13. Подписи на русском и время

- **Решение**: модуль `ui/labels.py` — словари «код → подпись» для статусов, резолюций,
  серьёзности, типов и состояний действий, событий аудита, ролей сетей; фильтры Jinja
  `label`, `utc_ms` (миллисекунды трафика → `2015-02-18 01:15:02 UTC`), `utc_iso`. Классы атак
  выводятся как в датасете. Тест проверяет, что у каждого значения из `store`/`config`
  (статусы, события, действия) есть подпись — новые значения без перевода не проскочат.
- **Почему**: FR-028; одна точка перевода вместо строк, разбросанных по шаблонам.

## R14. Тестирование консоли

- **Решение**: `TestClient` FastAPI + разбор HTML `beautifulsoup4` (dev-зависимость).
  Проверяются: полные страницы и фрагменты (`HX-Request`), фильтры/сортировка/пагинация
  против данных `store`, все решения и их ошибки (переход, конфликт, резолюция, пустой
  комментарий, нет имени, не ответственный), CSRF (чужой `Origin`, `Sec-Fetch-Site:
  cross-site`, нет токена, просроченный токен → 403 и база без изменений), экранирование
  (`<script>` в комментарии и имени выводится как текст), работа без JS (формы и ссылки
  имеют `action`/`href`, а не только `hx-*`), метки на синтетике и (slow) на реальном прогоне
  002, счётчики панели = число строк списка по ссылке счётчика, время ответа на данных
  полного прогона (< 1 с, SC-001). Данные — фикстуры 002 `synthetic_split`/`tiny_detector`
  плюс фабрика инцидентов прямо в SQLite для краевых случаев.
  Ручная проверка в браузере (опрос, диалоги, баннеры) — в quickstart.
- **Почему**: поведение htmx в браузере без браузера не проверить, но всё, что решает
  сервер (какой фрагмент, какая ошибка, что в базе), проверяется быстро и детерминированно.
- **Альтернативы**: Playwright — тяжёлая зависимость с браузерами; можно добавить позже
  для стенда.

## R15. Новые зависимости

- **Решение**: `python-multipart` (разбор HTML-форм в FastAPI — без него `Form(...)` не
  работает); dev — `beautifulsoup4`. htmx — вендоринг файла (R3), не пакет.
- **Почему**: минимум; Jinja2, FastAPI, uvicorn, polars уже есть.
