# Research: Лабораторный стенд и живой сенсор (006)

Решения по открытым вопросам плана. Формат: **Решение** / **Почему** / **Альтернативы**.
Нумерация R1–R18. Опирается на инфраструктуру 005 (брокер, сети, скрипты `stand/hyperv/*.ps1`,
`configs/stream.yaml`) и на экстрактор 001 (`src/mlsiem/data/extract.py`, `SCHEMA.extractor`).

## Машины стенда

### R1. ОС и образ машин жертвы и атакующего

**Решение**: обе машины — Ubuntu Server 24.04 LTS, тот же ISO, что брокер 005 (повторно не
скачивается). По ~1 ГБ статической памяти и ~10 ГБ динамического диска каждая. Gen 2, Secure
Boot с UEFI CA — как `mlsiem-broker`.

**Почему**: один образ → меньше скачиваний и меньше расхождений в экстракторе (train = serve
касается nfstream, но единая ОС убирает различия в сетевом стеке). Память укладывается в
бюджет хоста (SC-009): брокер 2 ГБ + сенсор +1 ГБ на той же ВМ + жертва 1 ГБ + атакующий 1 ГБ +
потребитель/консоль на хосте ≈ 5 ГБ ВМ, остаётся ≥ 4 ГБ (16 ГБ хост).

**Альтернативы**: Kali Linux для атакующего — отвергнут: +образ ~4 ГБ, тяжелее, а нужные
инструменты (nmap, hydra, ffuf/gobuster, hping3/slowhttptest) есть в репозиториях Ubuntu.
Отдельные Windows-машины — отвергнуты по памяти и лицензиям.

### R2. Фиксированные адреса и сети

**Решение**: сеть стенда `mlsiem-lab` (Private, из 005) получает подсеть `10.88.0.0/24`:
жертва `10.88.0.20`, атакующий `10.88.0.30`, сенсорный адаптер — без IP. Служебной сети у
машин стенда нет (см. R6). Адреса — статические, задаются автоустановкой (cloud-init) по
MAC, как у брокера; фиксированы в `configs/stream.yaml` (новый раздел `lab`).

**Почему**: отдельная подсеть `10.88` визуально отделяет сеть стенда от служебной `10.77`.
Статика по MAC → пересоздание машины сохраняет адрес (FR-005, Edge «Пересоздание машины»).

**Альтернативы**: DHCP на машине-жертве — отвергнут: адрес «плавает», ломается разметка набора
по журналу.

### R3. Автоустановка жертвы и атакующего

**Решение**: тот же механизм, что брокер 005 — seed-ISO с cloud-init (autoinstall), собираемый
командой `mlsiem stand seed-iso --role victim|attacker`. Роль определяет: список пакетов
(late-commands `apt install`), статический адрес, набор служб (жертва) или инструментов
(атакующий), тестовую учётку SSH для сценария перебора (жертва). Установочный адаптер — Default
Switch (DHCP, только на время установки), затем отключается скриптом `30-post-install`.

**Почему**: переиспользуем проверенный путь 005 (pycdlib, шаблоны `stand/broker/`). Один
механизм для всех трёх машин — меньше кода и инструкции.

**Альтернативы**: ручная установка по инструкции без автоустановки — отвергнута (не
воспроизводимо, FR-001).

### R4. Службы машины-жертвы

**Решение**: веб-сервер (nginx со статической страницей и несколькими путями для фаззинга),
OpenSSH (с тестовой учёткой `labuser` и заведомо слабым тестовым паролем из конфига), FTP
(vsftpd, анонимный read для «передачи файлов»), DNS-резолвер (dnsmasq, отвечает в пределах
стенда). Все службы — пустые, без данных владельца (FR-003).

**Почему**: покрывают цели сценариев (скан портов, фаззинг веб-путей, подбор SSH, DoS на веб)
и фоновой нормы (веб/SSH/файлы/DNS). Штатные пакеты Ubuntu, простая настройка.

**Альтернативы**: один универсальный сервис — отвергнут: сценариям нужны разные протоколы.

### R5. Инструменты атакующей машины

**Решение**: из репозиториев Ubuntu на этапе установки — `nmap` (скан портов), `ffuf` или
`gobuster` (перебор веб-путей), `hydra` (подбор SSH), `slowhttptest`/`hping3` (ограниченная
нагрузка на веб), `tcpreplay` + заготовленный pcap (контрольный сценарий, R9). Средство запуска
сценариев — небольшой Python/shell-раннер на атакующей машине, вызываемый с хоста (R6).

**Почему**: стандартные, широко documented инструменты; каждый закрывает один сценарий.
Эксплуатация с выполнением кода на жертве — вне объёма (Assumptions), поэтому Metasploit и
подобное не ставятся.

**Альтернативы**: написать свои скан/перебор на Python — отвергнуто: больше кода, менее
реалистичный трафик, чем у nmap/hydra.

### R6. Управление атакующей машиной и журнал сценариев без сети к хосту

**Решение**: хост управляет атакующей машиной через **Hyper-V PowerShell Direct**
(`Invoke-Command -VMName` / `Copy-VMFile`) — канал гипервизора без сети. У машин стенда нет
адаптера в служебной сети. Раннер сценариев на атакующей машине пишет журнал в локальный файл,
хост забирает его `Copy-VMFile` (машина → хост, тоже через Direct).

**Почему**: сохраняет изоляцию FR-005 (нет мостика сеть-стенда ↔ хост), а демо запускается
одной командой с хоста (FR-015). PowerShell Direct работает для Linux-гостей в Hyper-V через
hv_sock/службу гостя при наличии интеграционных служб; если гостевой компонент недоступен,
запасной путь — именованный последовательный порт (`Set-VMComPipe`) с простым текстовым
протоколом «команда → строки журнала».

**Почему именно так, а не SSH через mgmt**: второй адаптер атакующего в `mlsiem-mgmt` открыл бы
путь из сети стенда к хосту/брокеру — прямое нарушение изоляции. Канал гипервизора такого пути
не создаёт.

**Риск и проверка**: PowerShell Direct к Linux-гостю требует рабочей интеграционной службы;
проверяется шагом `check` сразу после подъёма машин. Запасной COM-канал — в плане как
fallback (не реализуем заранее, только если Direct не поднимется).

**Альтернативы**: SSH через служебную сеть — отвергнут (ломает изоляцию). Ручной вход на
машину — отвергнут (FR-015). Общая папка Hyper-V — у Linux-гостей нет.

## Сенсор

### R7. Размещение сенсора и зеркалирование трафика (ГЛАВНЫЙ РИСК)

**Решение**: сенсор — процесс на **брокерной машине** (экономия ВМ). Брокерной машине
добавляется второй сетевой адаптер в коммутаторе `mlsiem-lab` **без IP-адреса**, в режиме
приёмника зеркалирования: `Set-VMNetworkAdapter -PortMirroring Destination`. Адаптерам жертвы и
атакующего в `mlsiem-lab` ставится `-PortMirroring Source`. Так копии всех кадров жертвы и
атакующего приходят на сенсорный адаптер, не давая сенсору своего адреса в сети стенда (FR-006).
Брокерной машине добавляется +1 ГБ RAM (итого 3 ГБ).

**Почему**: порт-мирроринг Hyper-V работает между адаптерами **одного** виртуального
коммутатора (здесь все три — на `mlsiem-lab`), в том числе Private. Сенсор без IP в сети стенда
не нарушает изоляцию и физически видит только зеркало `mlsiem-lab` (служебная сеть — другой
коммутатор, в зеркало не попадает, FR-006/SC-003 п. «служебный трафик»). Отдельная ВМ-сенсор не
нужна → минус ~1 ГБ RAM.

**Проверка первым делом (план T-ранний)**: поднять порт-мирроринг на макете из двух гостей и
убедиться, что сенсорный адаптер видит ICMP между ними. Если на конкретной сборке Hyper-V
зеркало на Private-коммутаторе не доставляет кадры — **fallback R7a**.

**R7a (запасной)**: отдельная лёгкая ВМ-сенсор (Ubuntu, 768 МБ) с адаптером-приёмником в
`mlsiem-lab`; остальной план не меняется (сенсор так же без IP в стенде, управление — Direct).

**Альтернативы**: SPAN на физическом железе — нет (всё виртуально). Промежуточный мост/bridge и
nfqueue — сложнее и трогает трафик стенда (риск повлиять на задержки). Сенсор на хосте Windows —
отвергнут: хост не в сети стенда, нет Npcap и прав админа в обычной сессии (Assumptions 005).

### R8. Живой захват nfstream и единство признаков (train = serve)

**Решение**: сенсор вызывает тот же `NFStreamer` с теми же настройками `SCHEMA.extractor`
(idle 120 с, active 1800 с, statistical_analysis, accounting_mode 0), но `source=<iface>`
(живой интерфейс) вместо pcap-файла. Завершённый поток (по таймауту) сразу кодируется
`encode_flow` (как 005) и отправляется в брокер. Схему колонок проверяем так же, как в
`extract.py` (несовпадение → новая версия схемы, ошибка).

**Почему**: один и тот же код экстрактора на обучении и вживую — буквальное требование
конституции II. nfstream штатно умеет живой режим на интерфейсе Linux.

**Проверка train = serve (SC-003, FR-007)**: сенсор одновременно пишет pcap сеанса (R12);
тест прогоняет этот pcap экстрактором 001 офлайн и сверяет признаки потоков по ключу с тем, что
сенсор отправил вживую. Допуск — на округление числовых признаков и на потоки, обрезанные
границей записи.

**Подвох**: живой nfstream не завершит поток, пока не истечёт idle-таймаут (120 с) → поток
уходит в брокер с задержкой; это отражено в целях (SC-005 считает задержку сверх таймаута) и в
Edge «Длинные потоки». Для живого режима idle-таймаут из `SCHEMA.extractor` не трогаем (иначе
признаки разойдутся с обучением); демо-сценарии короткие, поэтому 120 с терпимы.

**Альтернативы**: уменьшить idle-таймаут для живого режима ради скорости — отвергнуто: ломает
train = serve. Свой разбор пакетов — отвергнуто (дубль nfstream, расхождение признаков).

### R9. Контрольный сценарий (гарантированное демо)

**Решение**: из test `unsw_time` заранее отбираются pcap-фрагменты заведомо узнаваемых атак
(класс с высокой поимкой модели на test 001, например Exploits/Generic) и сохраняются в
артефакт стенда. Контрольный сценарий воспроизводит такой фрагмент с атакующей машины на жертву
через `tcpreplay` с **подменой адресов** на адреса стенда (`tcprewrite --srcipmap/--dstipmap`,
пересчёт контрольных сумм). Сенсор видит эти кадры как живой трафик → знакомые модели признаки →
инцидент.

**Почему**: модель обучена на UNSW 2015; «родной» трафик стенда она может не узнавать (Edge
«Модель не узнаёт атаки»). Контрольный сценарий гарантирует, что **цепочка** (сенсор → брокер →
потребитель → инцидент) демонстрируема независимо от переноса модели. Подмена адресов делает
инцидент указывающим на атакующую машину стенда.

**Подвох**: tcpreplay переигрывает исходные тайминги; поток завершится по той же логике
nfstream. Переписанные адреса должны лежать в `mlsiem-lab`, иначе FR-013 отклонит сценарий.

**Альтернативы**: обучить модель на трафике стенда ради демо — вне объёма (Assumptions, нет
переобучения в 006). Инъекция готовых признаков в брокер минуя сенсор — отвергнуто: не «живое»
демо, не проверяет сенсор.

### R10. Буфер сенсора при недоступности брокера и учёт потерь

**Решение**: сенсор держит ограниченный очередной буфер отправки (размер в конфиге, по
умолчанию потоки за ~5 мин нормы). При недоступности брокера потоки копятся в буфере и
досылаются после восстановления (confluent-kafka producer с локальной очередью + явный учёт).
При переполнении буфера или перегрузке захвата (nfstream/libpcap `drop`) потерянные
пакеты/потоки считаются и показываются в показателях сеанса (FR-009), сессия помечается «с
потерями».

**Почему**: честный учёт потерь — требование (FR-009, Edge «Шторм пакетов»), нельзя
замалчивать. confluent-kafka уже в зависимостях (005).

**Проверка (SC-006)**: тест на записи — ронять «брокер» (MemoryBroker 005) на ≤ 5 мин при
нормальной интенсивности → 0 потерь; при искусственной перегрузке → потери видны в статусе.

**Альтернативы**: неограниченный буфер — отвергнут (риск памяти ВМ). Писать на диск при отказе
брокера — избыточно для демо (5-минутное окно буфера хватает).

## Сценарии, журнал, набор

### R11. Конфиг и реестр сценариев

**Решение**: новый раздел `scenarios` в `configs/stream.yaml` (или отдельный `configs/lab.yaml`,
подключаемый к тому же конфигу) — список: имя, версия, инструмент и его аргументы-шаблоны,
цель (служба жертвы), ожидаемый класс таксономии UNSW или `out_of_taxonomy`, лимит скорости,
лимит длительности. Раннер на атакующей машине читает запись сценария, проверяет, что все цели
в `lab`-подсети (FR-013), и запускает инструмент с лимитами.

**Почему**: «все числа потока живут в конфиге» — стиль 005 (FR-023 005). Версия сценария →
воспроизводимость и привязка набора к версии.

**Альтернативы**: сценарии в коде — отвергнуто (стиль проекта, менять без правки кода).

### R12. Запись трафика сеанса и построение размеченного набора

**Решение**: сенсор параллельно захвату пишет pcap сеанса с ротацией по объёму (лимит в
конфиге, по умолчанию 5 ГБ) на диск брокерной машины. Команда `mlsiem lab dataset build`
забирает pcap и журнал сценариев на хост (Direct/Copy-VMFile), прогоняет pcap экстрактором 001
и размечает каждый поток по журналу: поток с атакующего адреса на цель сценария в окне запуска →
класс сценария; поток, пересекающий границу окна (начат до начала или закончен позже конца плюс
допуск) → `ambiguous`; остальное → `benign`. Набор сохраняется под `data/lab/<версия>/` в схеме
признаков 001, версионируется DVC, сопровождается отчётом.

**Почему**: строит размеченный набор тем же экстрактором (единство признаков), разметка по
журналу однозначна при последовательных сценариях (Edge «Два сценария»). Ambiguous исключаются
из метрик, но считаются (FR-020).

**Подвох**: часы атакующей машины и сенсора должны совпадать (допуск 1 с, R13), иначе окна
журнала и времена потоков не сопоставимы.

**Альтернативы**: размечать на лету в сенсоре — отвергнуто: сенсор не знает про сценарии
(изоляция), и разметка должна быть пересобираемой из записи.

### R13. Синхронизация часов и проверка стенда

**Решение**: все машины синхронизируют часы (systemd-timesyncd на внутренний источник или на
брокерную машину как NTP внутри служебной — но машины стенда без служебной сети, поэтому проще:
часы задаются при старте через Hyper-V Time Synchronization Integration Service от хоста).
`mlsiem lab check` сверяет часы атакующей машины и сенсора (через Direct) и расхождение > 1 с
(конфиг) считает проблемой (FR-005, Edge «Часы расходятся»).

**Почему**: Integration Service синхронизирует гостя с хостом без сети → годится для
изолированных машин. Единые часы — условие надёжной разметки.

**Альтернативы**: NTP через служебную сеть — отвергнуто (нет служебной сети у машин стенда).

### R14. Фоновая норма

**Решение**: раннер нормы (на атакующей или на жертве — на атакующей, рядом со сценариями)
по конфигу гоняет обычный трафик к службам жертвы: периодические HTTP-запросы (curl), входы по
SSH с **правильным** паролем тестовой учётки и команды, скачивание файла по FTP, DNS-запросы.
Интенсивность и состав — в конфиге (FR-019). Норма пишет свои интервалы в журнал как запуск с
ожидаемым классом `benign`.

**Почему**: даёт «чужую» benign для измерения ложных срабатываний (US4/US5) и наполняет набор.

**Альтернативы**: записать норму один раз и переигрывать — отвергнуто: менее живо, и у нас уже
есть живой сенсор.

## Оценка, наблюдаемость, совместимость

### R15. Отчёт оценки модели на наборе стенда

**Решение**: команда `mlsiem lab evaluate --dataset <версия> --run <run_id>` берёт модель и
порог из артефакта прогона как есть (без подбора на стенде), считает PR-AUC (macro по
представленным классам и «атака/нет»), поимку потоков по каждому сценарию, FPR и число ложных
инцидентов на норме, пишет в MLflow (эксперимент `lab`) версию модели, версию набора и конфиг,
а итог и вывод — в `docs/JOURNAL.md` (FR-022, FR-024, конституция III/VI). Для сценария с
поимкой ниже порога конфига — разбор (R16).

**Почему**: честная оценка переноса на чужой трафик — главная ML-находка фичи; порог не
подбирается на стенде (принцип III).

### R16. Разбор непойманных сценариев

**Решение**: для каждого слабопойманного сценария отчёт указывает причину из трёх: (а) класс
вне таксономии UNSW (по полю сценария); (б) признаки вне распределения обучения — доля признаков
потока за диапазоном [min,max] train 001 выше порога; (в) потоки не дошли до модели — потери
сенсора по показателям сеанса. Диапазоны train берутся из артефакта/статистик данных 001.

**Почему**: «не поймано» не должно прятаться в среднем (FR-023, Edge «Модель не узнаёт атаки»).

**Альтернативы**: только общий PR-AUC — отвергнуто (не объясняет провал переноса).

### R17. Показатели сенсора в статусе и консоли

**Решение**: сеанс живого сенсора — строка `runs` с источником `sensor:live` (термины 005),
статус по FR-018 005 (перезапуск продолжает сеанс, завершение явной командой `stream close`).
Показатели сенсора (пакетов/с, потоков/с, потери пакетов, занятость буфера, живость) пишутся в
`stream_stats` рядом с показателями 005 и показываются командой `stream status` и на панели
консоли; признак «с потерями» — флаг сеанса. Для источников 005 отображение не меняется
(FR-025).

**Почему**: переиспользуем модель сеанса и таблицу показателей 005, добавляя только
сенсор-специфичные счётчики. Консоль 003/005 меняется минимально.

**Альтернативы**: отдельная таблица для сенсора — отвергнуто (дубль логики статуса).

### R18. Схема хранилища и совместимость тестов

**Решение**: миграция SQLite 5 → 6 добавляет сенсор-специфичные поля показателей в
`stream_stats` (packets_per_s, drops, buffer_fill, liveness) и, если нужно, флаг сеанса
`lossy`; источник `sensor:live` не требует новой таблицы. Быстрые тесты фичи не требуют ВМ и
прав админа: захват подменяется записанным pcap, брокер — MemoryBroker 005, управление машинами
не вызывается. Живые проверки помечены маркером `stand`/`lab` и идут только по явной команде
(FR-026). Тесты 001–005 и 007, где они не проверяют перечень источников или версию схемы, не
меняются (FR-027).

**Почему**: минимальная миграция под новые показатели; изоляция медленных/живых тестов — как в
005/007.

**Подвох (из опыта 007)**: при изменении версии схемы хранилища обновляется только
`test_store_migration_v5.py` (на 5 → 6) и места, прямо завязанные на номер схемы; остальные
ожидания не трогаются. `dvc repro` новой стадии набора стенда делать `--single-item`, чтобы не
каскадить на `train_detector`/`train_windows` (инцидент 007).
