# Implementation Plan: Лабораторный стенд и живой сенсор

**Branch**: `006-lab-stand-live-sensor` | **Date**: 2026-10-01 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/006-lab-stand-live-sensor/spec.md`

## Summary

Поверх брокера и сетей 005 на Hyper-V поднимаются две машины сети стенда `mlsiem-lab`:
**жертва** `10.88.0.20` (web/SSH/FTP/DNS) и **атакующий** `10.88.0.30` (nmap, ffuf, hydra,
slowhttptest, tcpreplay). **Живой сенсор** — процесс на брокерной машине со вторым адаптером в
`mlsiem-lab` без IP, который принимает зеркало портов Hyper-V и тем же экстрактором nfstream
001 превращает трафик стенда в потоки, отправляя их в брокер как источник `sensor:live`. Дальше
работает готовая онлайн-цепочка 005 (модель → алерт → инцидент → SOAR → консоль).

Атаки запускаются с хоста одной командой через PowerShell Direct (без сети к машинам стенда →
изоляция сохраняется), пишут журнал сценариев. **Контрольный сценарий** (повтор узнаваемого
трафика UNSW с подменой адресов на адреса стенда) гарантирует живое демо независимо от переноса
модели. Стенд генерирует фоновую норму и собирает **первый собственный размеченный набор**
(`data/lab/`, DVC), по которому честно оценивается перенос моделей 002–007 на «чужой» трафик:
PR-AUC, поимка по сценариям, FPR на норме, с разбором непойманного.

Сквозной результат (конституция I): владелец запускает `lab demo` → через минуты видит в
консоли инцидент с атакующим адресом стенда.

## Technical Context

**Language/Version**: Python 3.11 (пакет `mlsiem`) + PowerShell 5.1 (скрипты Hyper-V) +
гостевой Linux (Ubuntu Server 24.04, службы/инструменты).

**Primary Dependencies**:
- уже есть: nfstream (001, живой режим на интерфейсе), confluent-kafka + MemoryBroker (005),
  polars/numpy/scikit-learn/LightGBM/MLflow, FastAPI/Jinja2/htmx (003), pycdlib (seed-ISO 005),
  PyTorch в группе `nn` (007, нужен только если эксперт окон в цепочке);
- **новое на машинах стенда** (ставится из репозиториев Ubuntu при установке, не на хосте):
  nginx, openssh-server, vsftpd, dnsmasq (жертва); nmap, ffuf/gobuster, hydra,
  slowhttptest/hping3, tcpreplay (атакующий);
- **новых Python-зависимостей на хосте не требуется**.

**Storage**:
- SQLite `var/soc.db`, миграция схемы 5 → 6 (R18, data-model);
- набор стенда `data/lab/<версия>/` (DVC), отчёты `reports/lab_eval_*.{md,json}`;
- запись pcap сеанса — на диске брокерной/сенсорной ВМ с ротацией (R12);
- MLflow (`mlflow.db` + `mlruns/`), эксперимент `lab`.

**Testing**:
- pytest: быстрые тесты без ВМ и прав админа — захват подменяется записанным pcap, брокер —
  MemoryBroker 005, управление машинами не вызывается (новые фикстуры `lab_pcap`,
  `lab_scenarios`);
- маркер `stand` — на брокере 005 (из 005);
- **новый маркер `lab`** — живые проверки на поднятом стенде (сенсор, сценарии, изоляция),
  запускаются только явной командой.

**Target Platform**: Windows 11 хост (Hyper-V, потребитель, консоль); Linux-ВМ Hyper-V (брокер
+ сенсор, жертва, атакующий).

**Project Type**: CLI + локальный веб-сервис (единый пакет `mlsiem`) + инфраструктурные
PowerShell-скрипты.

**Performance Goals**:
- живой инцидент по контрольному сценарию ≤ 3 мин после конца сценария (SC-004);
- задержка поток → брокер ≤ 5 с сверх idle-таймаута экстрактора для 95% потоков (SC-005);
- при недоступности брокера ≤ 5 мин — 0 потерь при нормальной норме (SC-006).

**Constraints**:
- 16 ГБ RAM хоста: брокер+сенсор 3 ГБ + жертва 1 ГБ + атакующий 1 ГБ + потребитель/консоль ≈
  5–6 ГБ ВМ, запас ≥ 4 ГБ (SC-009); стенд можно поднимать частями (без фоновой нормы);
- изоляция сети стенда (FR-005): никакого сетевого мостика к хосту/брокеру — управление только
  через канал гипервизора;
- единство признаков: idle/active-таймауты nfstream в живом режиме не меняются (R8).

**Scale/Scope**: демо-стенд на одного владельца; набор стенда — порядка часов нормы и десятков
запусков сценариев, не для обучения в 006.

## Constitution Check

*GATE: пройден до Phase 0, перепроверен после Phase 1.*

- **I. Вертикальные срезы** — ✅ фича кончается работающим демо (`lab demo` → инцидент в
  консоли). Инфраструктура (скрипты ВМ, сенсор) наращивается внутри этой фичи, не «на потом».
- **II. Единство признаков (train = serve)** — ✅ сенсор использует тот же `NFStreamer` и
  `SCHEMA.extractor`, что 001; совпадение живых и офлайн-признаков проверяется тестом (R8, SC-003).
  Таймауты экстрактора в живом режиме не трогаются.
- **III. Честная оценка (NON-NEGOTIABLE)** — ✅ оценка на наборе стенда: PR-AUC, порог с
  валидации 001 (не подбирается на стенде), разбор непойманного, запись в MLflow и журнал даже
  при плохом результате (R15/R16, US5). Набор стенда отделён от UNSW/CTU-13.
- **IV. Решения через эксперимент** — ⚪ новых моделей фича не вводит; переобучение вне объёма.
  Применяется к оценке переноса существующих моделей (честная находка, а не новая архитектура).
- **V. Безопасный SOAR с человеком в контуре** — ✅ действия по инцидентам стенда только
  симулируются; ни один компонент не меняет сеть машин стенда по решению аналитика (FR-018).
- **VI. Воспроизводимость и понятный код** — ✅ набор под DVC, оценка в MLflow, сиды; тесты
  (быстрые без ВМ + живой маркер); комментарии по-русски; запись в `docs/JOURNAL.md`.
- **VII. Прозрачное авторство** — ✅ коммитит владелец; служебные файлы не попадают в репо.

**Среда (объём и ограничения конституции)**: Docker/WSL2 не требуются (FR-001). Hyper-V — уже
предусловие 005. Память укладывается в 16 ГБ с запасом (SC-009).

## Основные риски и порядок снятия

1. **Зеркалирование портов на Private-коммутаторе (R7)** — снять ПЕРВЫМ (quickstart §1). Нет →
   fallback R7a (отдельная ВМ-сенсор), остальной план не меняется.
2. **PowerShell Direct к Linux-гостю (R6)** — проверить сразу после подъёма машин. Нет →
   fallback COM-канал (`Set-VMComPipe`).
3. **Перенос модели на трафик стенда (Edge)** — ожидаемо слабый; это находка US5, а не сбой.
   Демо держится на контрольном сценарии (R9), не на переносе.
4. **Задержка idle-таймаута nfstream (R8)** — поток уходит через ≥ 120 с; демо-сценарии
   короткие, цели считают задержку сверх таймаута.
