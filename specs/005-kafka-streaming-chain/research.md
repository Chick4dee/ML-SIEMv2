# Research: потоковая обработка через Kafka (фича 005)

Решения фазы 0. Каждое — «Решение / Почему / Альтернативы». Ссылки — к [spec.md](spec.md).
Исходное состояние — код 001–004 на 2026-09-25: пакетная цепочка `soc run` (load_model →
вердикты → правило направления → группировка → плейбуки → SQLite одной транзакцией), консоль
003 с автообновлением, схема БД 3.

## R1. Брокер и машина стенда

**Решение**: Apache Kafka 4.x (последний стабильный выпуск на момент реализации, архив с
downloads.apache.org, проверка SHA-512) в режиме KRaft **combined** (`process.roles=broker,controller`),
один узел, фактор репликации 1, на Ubuntu Server 24.04 LTS в Hyper-V (Gen 2, 2 vCPU, 2 ГБ RAM
статически, диск 20 ГБ динамический). Java — `openjdk-21-jre-headless` из репозитория Ubuntu,
куча брокера `-Xms512m -Xmx512m`. Kafka — systemd-сервис от отдельного пользователя `kafka`,
данные в `/var/lib/kafka`. `auto.create.topics.enable=false`: топики создаёт скрипт.

**Почему**: KRaft — единственный режим Kafka 4 (ZooKeeper удалён), combined-режим на одном узле
— штатная конфигурация для разработки. 2 ГБ с кучей 512 МБ оставляют хосту запас (SC-007).
24.04 — LTS с самым отлаженным автоустановщиком. Своя машина вместо Docker/WSL2 — ограничение
конституции, и это же первая машина стенда 006.

**Альтернативы**: Redpanda (совместима по протоколу, но официально — контейнеры или deb для
x86 с требованием ≥2 ядер и больших ресурсов; отклонена ради «настоящей» Kafka по выбору
владельца); Kafka нативно на Windows (не поддерживается, известные проблемы с удалением
сегментов лога); Mosquitto/RabbitMQ (нет журнала с позициями и перечитыванием — ломает
«перезапуск без потерь»).

## R2. Сети стенда (clarify Q3, FR-003a)

**Решение**: три виртуальных коммутатора Hyper-V:
- `mlsiem-mgmt` — **Internal** (служебная сеть): хост `10.77.0.1/24` на своём vEthernet,
  брокер `10.77.0.10/24`, в 006 сенсор `10.77.0.20`. Статические адреса, без DHCP;
- `mlsiem-lab` — **Private** (сеть стенда): машины между собой, хост и брокер в неё не
  включены вовсе. В 005 создаётся пустой (заготовка для 006);
- `Default Switch` (встроенный NAT Hyper-V) — второй адаптер брокерной машины **только на время
  установки** (пакеты, Kafka); после установки адаптер отключается скриптом.

Kafka слушает `PLAINTEXT://10.77.0.10:9092` (клиенты) и `CONTROLLER://127.0.0.1:9093`;
межсетевой экран машины (ufw) пропускает 9092 только из `10.77.0.0/24`, SSH — только с хоста.

**Почему**: изоляция «физическая» — у брокерной машины просто нет адаптера в сети стенда, а
Private-коммутатор недоступен даже хосту. ufw — второй слой на случай ошибки в подключении
адаптеров. Статические адреса делают конфиг воспроизводимым.

**Альтернативы**: одна сеть с фильтром по адресам (отклонено в clarify — адрес подделывается);
аутентификация SASL/TLS в Kafka (вне объёма; изоляции достаточно для стенда).

## R3. Воспроизводимое создание машины без Docker/WSL2

**Решение**: PowerShell-скрипты в `stand/hyperv/` + автоустановка Ubuntu:
1. `00-check.ps1` — проверки без изменений: Hyper-V включён, права администратора, свободные
   RAM/диск, наличие образа; печатает план действий и ресурсы (FR-002).
2. `10-network.ps1` — создать `mlsiem-mgmt`/`mlsiem-lab` и адрес хоста (идемпотентно: если есть —
   ничего не делать).
3. `20-vm-broker.ps1` — создать ВМ `mlsiem-broker` с ISO Ubuntu live-server и вторым
   «seed»-ISO автоустановки; Secure Boot с шаблоном `MicrosoftUEFICertificateAuthority`.
4. `30-post-install.ps1` — после установки: отключить адаптер `Default Switch`, проверить
   брокер.
5. `90-remove.ps1` — удалить ВМ и коммутаторы (по подтверждению).

Каждый скрипт, меняющий систему, спрашивает подтверждение (`-Confirm`/`ShouldProcess`) и
печатает, что сделает; `-WhatIf` показывает план без изменений. Образ ISO скачивает владелец
(ссылка и SHA-256 в инструкции) или скрипт после явного подтверждения.

Seed-ISO автоустановки (`autoinstall` + cloud-init: пользователь, SSH-ключ хоста, статические
адреса, пакеты, установка Kafka из архива с проверкой SHA-512, systemd-юнит, ufw, создание
топиков) собирает Python-командой `mlsiem stand seed-iso` на библиотеке `pycdlib` (чистый
Python) — на Windows нет штатного `genisoimage`/`oscdimg`. Шаблоны конфигов — в
`stand/broker/` (в git), параметры — из `configs/stream.yaml`.

Известное ограничение: установщик Ubuntu при автоустановке с внешнего seed просит одно
подтверждение «Continue with autoinstall?» в консоли ВМ — это шаг инструкции. SC-001 (≤ 30 мин
без скачивания) это учитывает.

**Почему**: Hyper-V управляется только PowerShell; `autoinstall` — штатный механизм Ubuntu;
`pycdlib` снимает зависимость от внешних утилит. Скрипты идемпотентны — повтор безопасен
(US1 п. 2).

**Альтернативы**: облачный образ Ubuntu (VHD для Azure привязан к датасорсу Azure; qcow2 требует
`qemu-img`); Vagrant/Packer (лишние инструменты); ручная установка по скриншотам
(невоспроизводимо).

## R4. Python-клиент Kafka и заглушка для тестов

**Решение**: `confluent-kafka` (librdkafka; готовые колёса для Windows/Python 3.11). Весь доступ
к брокеру — через узкий интерфейс `stream.broker.Broker` (produce с ключом и заголовками, flush,
subscribe/poll пачкой, commit позиций, запрос концов партиций для отставания, список топиков).
Две реализации: `KafkaBroker` (confluent-kafka) и `MemoryBroker` (в памяти, с партициями,
позициями, повторной доставкой после «сбоя») — на ней идут все быстрые тесты без ВМ.
Тесты на настоящем брокере — маркер `@pytest.mark.stand`, по умолчанию выключены (как `slow`).

**Почему**: confluent-kafka — быстрый и поддерживаемый клиент с идемпотентным продюсером и
ручным подтверждением позиций; librdkafka даёт нужную пропускную способность (SC-002).
Интерфейс-обёртка позволяет тестировать гарантии (at-least-once, перезапуск, дубли) детерминированно.

**Альтернативы**: kafka-python (чистый Python, медленнее в разы на 282 тыс. сообщений);
aiokafka (асинхронность не нужна потребителю-пачечнику); тесты только на живом брокере
(медленно и требует ВМ на каждом прогоне тестов).

## R5. Формат сообщения (FR-005, FR-006, FR-007)

**Решение**: одно сообщение = один поток, значение — JSON (сериализация `orjson`, уже есть в
окружении — объявляется явной зависимостью):
- ключ сообщения — `source_id` (все потоки одного источника в одной партиции, порядок сохраняется);
- заголовки: `mlsiem-kind` (`flow` | `end`), `mlsiem-schema` (версия схемы 001), `mlsiem-source`;
- тело `flow`: `{"flow_uid", "source_id", "seq", "sent_at_ms", "schema_version", "fields": {...}}`,
  где `fields` — **все** колонки `SCHEMA.columns` кроме группы `label` в порядке схемы; метка —
  отдельным полем `label` только у размеченного входа (FR-007);
- тело `end`: `{"source_id", "n_sent", "last_seq", "sent_at_ms"}` — отметка «конец данных»
  (clarify Q4).

Типы восстанавливаются по `SCHEMA.dtypes()` при сборке кадра (int64/float64/string/bool, `null`
сохраняется). Проверка на потребителе: мажорная версия схемы совпадает с моделью, все поля схемы
есть и приводятся к типу; иначе — в топик отвергнутых с причиной.

Топики: `mlsiem.flows` (1 партиция по умолчанию), `mlsiem.flows.rejected` (1), срок хранения
7 дней (конфиг).

**Почему**: JSON читается глазами и одинаков для любого производителя (сенсор 006 на Linux);
float64 в JSON через `repr` не теряет точности. Ключ по источнику сохраняет порядок внутри
источника. Одна партиция по умолчанию — один потребитель читает строго по порядку отправки,
что упрощает эквивалентность; число партиций — параметр.

**Альтернативы**: Avro/Protobuf + Schema Registry (ещё один сервис на 2 ГБ машине); Arrow-пачки
по 1000 потоков (быстрее, но сенсор шлёт поток сразу по завершении — пачки ломают задержку);
msgpack (не читается глазами, выигрыш не нужен при целевой скорости).

## R6. Проигрыватели (FR-008, FR-009)

**Решение**: `mlsiem stream replay --split S --part P | --pcap FILE`, `--speed N | --speed max`,
`--limit`. Потоки сортируются по `(bidirectional_first_seen_ms, flow_uid)`; в режиме ×N пауза
перед потоком = разница времени трафика / N (по часам, с компенсацией накопившегося
отставания, без сна меньше 1 мс). PCAP — экстрактор 001 в поток кадра, дальше тот же путь.
`source_id` = `replay:<вход>:<время запуска>`; `seq` — номер потока в источнике.
Продюсер — идемпотентный (`enable.idempotence=true`, `acks=all`), в конце — `end` и `flush`;
ошибка доставки → код 1 и сводка «отправлено N из M». Повторная отправка того же `source_id`
с `--resume` продолжает после последнего подтверждённого `seq` (для сбоя проигрывателя).

**Почему**: порядок по времени начала — как в пакетном режиме и как сенсор без опозданий;
идемпотентный продюсер убирает дубли на стороне брокера, а `flow_uid` — на стороне потребителя.

**Альтернативы**: пауза по времени окончания потока (реалистичнее для сенсора, но расходится с
порядком пакетной группировки; опоздания проверяются отдельным тестом с перемешиванием).

## R7. Потребитель: пачки, транзакция, позиции (FR-012, FR-015, FR-016, FR-019)

**Решение**: `mlsiem stream consume [--model DIR]` — цикл:
1. poll до `batch.max_messages` (2000) или `batch.max_wait_ms` (500 мс);
2. разбор и проверка (отвергнутые → топик отвергнутых сразу, синхронно, до шага 5);
3. по источникам: сеанс найден или создан; `flow_uid`, уже записанные в этом сеансе, отбрасываются
   (таблица `stream_seen` — идентификаторы обработанных потоков сеанса; дубли не считаются);
4. вердикты — `LoadedModel.verdict_frame` (та же функция, что пакетный режим), направление,
   алерты, инкрементальная группировка (R8), плейбуки (R9);
5. **одна транзакция SQLite**: алерты, инциденты (вставка/обновление), действия, аудит, вердикты
   пачки → `var/runs/<run_id>/verdicts/part-<n>.parquet` (файл пишется до транзакции, имя
   фиксируется в транзакции), позиции (`stream_offsets`: топик, партиция, следующая позиция),
   показатели;
6. только после COMMIT — `commit` позиций в Kafka (синхронно).

При старте позиция берётся из `stream_offsets` в SQLite (источник истины), а не из Kafka:
если процесс упал между шагами 5 и 6, повтор сообщений отсеется по `stream_seen`, а если до 5
— сообщения прочитаются заново. Это даёт «ровно один раз» по эффекту при доставке «хотя бы один
раз» (SC-005).

Единственность потребителя — строка-аренда `stream_lease` в SQLite (хост, PID, время
продления каждые 5 с, истекает через 30 с); второй запуск при живой аренде — отказ с
объяснением (FR-019). Модель загружается и проверяется до первого poll (US3 п. 7).

**Почему**: запись результата и позиции одной транзакцией — стандартный приём «transactional
outbox наоборот» для at-least-once источника и единственного хранилища; Kafka-транзакции не
нужны, т. к. результат пишется не в Kafka.

**Альтернативы**: подтверждать в Kafka до записи (теряются данные при сбое — нарушает FR-016);
exactly-once Kafka Streams (Java, не наш стек).

## R8. Инкрементальная группировка и слияние (FR-013, FR-014, clarify Q2)

**Решение**: состояние группировки — это сами инциденты в SQLite: для ключа
`(attacker_ip, класс)` нужны интервалы его инцидентов в сеансе. Для каждого нового алерта
(в пачке сортируются по `(first_seen_ms, flow_uid)`):
- найти инцидент ключа, чьё окно `[first_seen − W, last_alert_start + W]` содержит время
  начала алерта (W = окно группировки; границы включительные, как «разрыв ≤ W» в 002). Важно:
  пакетная группировка меряет разрыв по **времени начала** потоков алертов, поэтому правая
  граница — максимум времени начала алертов инцидента (`last_alert_start_ms`, новая колонка), а
  не `last_seen_ms` (время конца последнего потока) → дописать; если таких два (алерт «между» и склеивает их) →
  **слияние**: поздний поглощается ранним (алерты переносятся, счётчики и серьёзность
  пересчитываются, у поглощённого `status` не меняется, но ставится `merged_into` и снимается
  «предложенное» действие, событие аудита `incident_merged`). Если у поглощаемого решение уже
  принято (действие не в `proposed` или статус не `new`) — слияния нет, алерт дописывается в
  ранний, а пара записывается в `stream_divergences` для отчёта сравнения (FR-021);
- иначе — новый инцидент.

Идентификатор нового инцидента — `inc-<хеш>` от (сеанс, ключ, время первого алерта), как в
002, и после создания не меняется. Эквивалентность с пакетным режимом сравнивается по
содержанию (ключ, границы, число алертов, серьёзность, действие), не по идентификатору.

Серьёзность и пояснение пересчитываются функцией `severity()` 002; изменение пишется в
`incident_history` (поле `severity`, автор `system`) и аудит `incident_updated`. Код один: пакетная
`group_alerts` остаётся для `soc run`, а доказательство совпадения — тест «инкрементально
пачками разного размера и в перемешанном в пределах опоздания порядке = пакетно» (property-тест
на синтетике).

Опоздание: `late_ms` = насколько время трафика алерта раньше максимума, уже виденного в
сеансе; больше `allowed_lateness_ms` (2 мин) → флаг `late` у алерта и счётчик в показателях.
Обработка та же (правило слияния делает результат независимым от порядка).

**Почему**: правило «окно вокруг интервала» + слияние даёт тот же разбиение на группы, что
пакетный «разрыв > W», при любом порядке прихода — это связность на прямой. Поэтому SC-004
достижим без придерживания данных (clarify Q2, вариант A).

**Альтернативы**: держать буфер 2 мин (ломает SC-003), никогда не сливать (ломает SC-004).

## R9. Плейбуки для растущего инцидента и решения аналитика (FR-017, US3 п. 4–5)

**Решение**: после каждого изменения инцидента правило плейбука пересчитывается
(`propose_action`). Если действие в `proposed` и результат другой — действие обновляется
(тип, объект, правило), `version` +1, аудит `action_reproposed`. Если действие уже решено или
инцидент закрыт — ничего не меняется, а у инцидента растут `alerts_after_decision` и
фиксируется `first_after_decision_ms` (пометка «новые алерты после решения», clarify Q1);
аудит `incident_updated` с `after_decision: true`. Обновление инцидента потребителем идёт через
оптимистичную блокировку, как решения аналитика: конфликт → перечитать и повторить (FR-020).

**Почему**: предложение должно соответствовать текущему инциденту, пока человек не решил;
после решения автоматика ничего не переписывает (принцип V).

## R10. Хранилище: схема 4

**Решение**: миграция 3 → 4 одной транзакцией:
- `runs`: `mode TEXT NOT NULL DEFAULT 'batch'` (`batch` | `stream`), `status TEXT NOT NULL
  DEFAULT 'completed'` (`running` | `stopped` | `completed`), `source_id TEXT`,
  `last_activity_at TEXT`, `model_version TEXT`;
- `incidents`: `merged_into TEXT`, `alerts_after_decision INTEGER NOT NULL DEFAULT 0`,
  `first_after_decision_ms INTEGER`, `last_alert_start_ms INTEGER` (для старых —
  `MAX(first_seen_ms)` его алертов, заполняется миграцией);
- `alerts`: `late INTEGER NOT NULL DEFAULT 0`, `received_at TEXT` (для задержки);
- новые таблицы `stream_offsets`, `stream_seen`, `stream_lease`, `stream_stats`,
  `stream_divergences`;
- новые события аудита `incident_updated`, `incident_merged`, `action_reproposed`,
  `session_status_changed` → таблица аудита пересоздаётся с сохранением `entry_id`, как в
  миграции 0 → 2 (новый CHECK), триггеры ставятся заново.

Цепочки 0 → 2 → 3 → 4 и 2 → 3 → 4. Старые прогоны получают `mode = batch`, `status = completed`.

**Почему**: только добавления, как в 003/004; аудит пересоздаётся по уже проверенному образцу.

## R11. Показатели и наблюдаемость (FR-022)

**Решение**: потребитель после каждой пачки пишет в `stream_stats` (раз в ≥ 1 с): число
обработанных за интервал, отставание (конец партиции − позиция, в сообщениях; и в секундах —
`now − sent_at` последнего обработанного), задержки `written_at − sent_at` по алертам пачки
(p50/p95 скользящим окном 60 с), отвергнутые, опоздавшие, аренда жива. `mlsiem stream status`
печатает это по сеансам и живость брокера; панель консоли для сеанса `running` показывает
значок «идёт» и те же показатели (опрос htmx 10 с, как у панели 003).

**Почему**: без внешнего стека мониторинга (Prometheus — отдельная фича) показатели живут там же,
где консоль их читает. Задержка считается по часам хоста с `sent_at` проигрывателя (обе
стороны на одном хосте в 005 — без рассинхронизации часов; для сенсора 006 — NTP).

## R12. Эквивалентность (FR-021, SC-004)

**Решение**: `mlsiem stream compare --session RUN --batch RUN` сравнивает: вердикты всех
потоков (все колонки, что есть у обоих; `flow_uid` ↔ `flow_uid`), инциденты по содержанию
(ключ, first/last_seen, n_alerts, severity, targets), предложенные действия (тип, объект,
правило). Выход — `reports/stream_compare_<session>.md/.json`: совпало/расходится, список
расхождений с причиной (`merge_blocked_by_decision`, `late_beyond_allowed`, `other`).

## R13. Консоль и API (только добавления)

- Прогоны: режим и статус сеанса; фильтр списка «новые алерты после решения»; в карточке —
  пометка «новые алерты после решения (N, с …)», для поглощённого — «объединён с <ссылка>».
- Панель: блок «Поток» для сеанса `running`/`stopped` (показатели R11).
- API: `Run` + `mode`, `status`, `source_id`; `Incident` + `merged_into`,
  `alerts_after_decision`, `first_after_decision_ms`; `GET /stream/status`. Новых изменяющих
  методов нет.
- Файлы вердиктов сеанса — каталог `verdicts/part-*.parquet`; `alert_probs` читает и файл, и
  каталог.

## R14. Производительность и ресурсы

- Потребитель: разбор JSON ~5–10 мкс на поток (orjson), модель на пачке 2000 — миллисекунды
  (LightGBM) / десятки мс (ансамбль), SQLite-транзакция пачки — десятки мс. Оценка: 282 тыс.
  потоков ≈ 1–3 мин при `--speed max` (цель SC-002 — 10 мин).
- Проигрыватель: сериализация + продюсер librdkafka ≥ 20 тыс. сообщений/с.
- Память: ВМ 2 ГБ; потребитель ~1 ГБ (модель + пачки); консоль ~200 МБ — SC-007 с запасом.

## R15. Совместимость (SC-008)

Пакетный `soc run` не меняется по поведению (пишет `mode = batch`); группировка пакетного режима
та же. Новые поля API и консоли — только добавления; старые прогоны открываются как раньше.
Зависимости: `confluent-kafka`, `orjson` (runtime), `pycdlib` (extra `stand`, только для
сборки seed-ISO).
