# Feature Specification: Потоковая обработка через Kafka

**Feature Branch**: `005-kafka-streaming-chain`

**Created**: 2026-09-25

**Status**: Draft

**Input**: User description: "Фича 005: потоковая обработка через Kafka. Kafka (режим KRaft, без
ZooKeeper) живёт в Linux-ВМ Hyper-V (Ubuntu Server, ~2 ГБ RAM) — это первая машина будущего
стенда (006); Docker/WSL2 не используются (ограничение конституции). Производители:
проигрывание размеченного разбиения 001 (например test unsw_time) и PCAP в топик потоков с
контролируемой скоростью (в реальном времени по меткам времени или ускоренно); позже (006) —
живой сенсор nfstream на интерфейсе стенда как ещё один производитель того же формата.
Потребитель на хосте Windows: онлайн-цепочка 002–004 (модель через load_model — детектор или
ансамбль, правило направления, группировка в инциденты с окном 15 минут, плейбуки, запись в
SQLite) обрабатывает потоки по мере поступления; инциденты открываются и дополняются
инкрементально, консоль 003 видит их без перезапуска (автообновление уже есть). Схема сообщений
= схема признаков 001 (train = serve), версия схемы в сообщении, отказ на несовместимой версии.
Требования: гарантии доставки (at-least-once + идемпотентность по flow_uid, без дублей алертов),
перезапуск потребителя без потерь (коммит смещений после записи в БД), наблюдаемость (задержка
поток→алерт, отставание потребителя, пропускная способность) в консоли или CLI, эквивалентность:
онлайн-обработка того же входа даёт те же вердикты и те же инциденты, что пакетный soc run.
Скрипты/инструкция развёртывания ВМ с Kafka воспроизводимы (Hyper-V, PowerShell), действия на
машине пользователя — по подтверждению. Железо: 16 ГБ RAM, CPU. Цель по производительности:
поток test unsw_time (282 тыс. потоков) в ускоренном режиме без отставания, задержка
поток→инцидент в реальном времени — секунды."

## Контекст

До этой фичи цепочка (002–004) работает **прогонами**: берётся готовый набор потоков (часть
разбиения или PCAP целиком), обрабатывается за один раз, результат появляется в консоли. Настоящий
SIEM так не работает: трафик идёт непрерывно, и инцидент должен появиться у аналитика через
секунды после атаки, а не после конца захвата. Фича 005 превращает цепочку в **потоковую**:
потоки сетевого трафика приходят сообщениями через брокер, цепочка обрабатывает их по мере
поступления, инциденты открываются и растут на глазах.

Брокер живёт на отдельной Linux-машине — это первая машина будущего стенда (фича 006), где потом
появится живой сенсор. В этой фиче источники потоков — проигрыватели уже имеющихся данных
(размеченное разбиение 001 и PCAP), так что поведение можно сравнить с пакетным прогоном «один в
один».

Термины: **поток** — запись nfstream в схеме признаков 001; **производитель** — то, что кладёт
потоки в брокер; **потребитель** — онлайн-цепочка на хосте; **сеанс** — непрерывная обработка
одного источника, в хранилище видна как прогон.

## Clarifications

### Session 2026-09-25

- Q: Новые алерты к инциденту, по которому уже принято решение или который закрыт? → A: дописываются
  в тот же инцидент с пометкой «новые алерты после решения»; статус, резолюция и решение не меняются.
- Q: Как поступать с опоздавшим потоком, который по времени трафика склеивает два открытых
  инцидента одного ключа? → A: обрабатывать сразу; более поздний инцидент сливается в более ранний
  (алерты переносятся, у поглощённого — пометка «объединён с …», событие в аудите); если по
  поглощённому уже принято решение — слияния нет, расхождение фиксируется в отчёте сравнения.
- Q: Кто в сети стенда может подключаться к брокеру? → A: две отдельные сети: служебная (хост,
  брокер, позже сенсор) и сеть стенда (атакующий, жертвы, интерфейс сенсора только на
  прослушивание); из сети стенда брокер недоступен.
- Q: Когда сеанс «завершён» и что при перезапуске потребителя? → A: сеанс привязан к источнику;
  перезапуск продолжает тот же сеанс («остановлен» → «идёт»); «завершён» — когда проигрыватель
  прислал отметку «конец данных» и всё до неё обработано; у живого сенсора — только явной командой.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Брокер на стенде поднимается по инструкции (Priority: P1)

Владелец проекта по воспроизводимой инструкции со скриптами создаёт на своём компьютере
Linux-машину с брокером сообщений, проверяет, что брокер доступен с хоста, и может в любой момент
пересоздать её с нуля с тем же результатом.

**Why this priority**: без брокера нет ни одного потокового сценария; это фундамент и 005, и 006.
Каждое действие на машине владельца (скачать образ, создать виртуальный коммутатор и машину)
выполняется только после его подтверждения.

**Independent Test**: выполнить инструкцию на чистой системе → машина запущена, команда проверки
с хоста показывает «брокер доступен, топики созданы»; удалить машину и повторить → тот же
результат.

**Acceptance Scenarios**:

1. **Given** Windows с включённым Hyper-V и без машины стенда, **When** владелец выполняет шаги
   инструкции, **Then** появляется машина с брокером, доступная с хоста по внутренней сети, с
   топиками потоков и служебными топиками, а команда проверки сообщает версию брокера и список
   топиков.
2. **Given** машина уже создана, **When** шаги инструкции выполняются повторно, **Then** ничего не
   ломается и не дублируется (повторный запуск безопасен).
3. **Given** машина выключена, **When** владелец запускает проверку, **Then** получает понятное
   сообщение «брокер недоступен» и подсказку, как запустить машину, а не зависание.
4. **Given** инструкция, **When** владелец читает её, **Then** перед каждым действием, меняющим
   систему (скачивание образа, создание сети и машины, выделение памяти), указано, что будет
   сделано и сколько ресурсов займёт.

### User Story 2 - Проигрывание данных в брокер (Priority: P2)

Разработчик отправляет в брокер потоки из размеченного разбиения 001 или из PCAP: либо в
«реальном времени» (с теми же паузами между потоками, что в исходном трафике, с возможным
ускорением в N раз), либо максимально быстро.

**Why this priority**: это единственный источник потоков, пока нет стенда (006), и основа для
проверки эквивалентности с пакетным прогоном.

**Independent Test**: проиграть test `unsw_time` в ускоренном режиме → число сообщений в топике
равно числу потоков части, у каждого сообщения версия схемы, порядок по времени начала потока.

**Acceptance Scenarios**:

1. **Given** брокер доступен, **When** проигрывается часть разбиения с ускорением ×60, **Then**
   сообщения приходят с паузами, пропорциональными исходным (1 час трафика ≈ 1 минута), а
   проигрыватель показывает прогресс и скорость.
2. **Given** режим «как можно быстрее», **When** проигрывается вся часть test, **Then** в топике
   ровно столько потоков, сколько в части, каждый ровно один раз с точки зрения потребителя.
3. **Given** PCAP, **When** он проигрывается, **Then** потоки извлекаются тем же экстрактором, что
   в 001/002 (та же схема и настройки), и отправляются в брокер.
4. **Given** брокер недоступен или пропал во время проигрывания, **When** проигрыватель пытается
   отправить, **Then** он сообщает об ошибке и завершается с ненулевым кодом, не делая вид, что всё
   отправлено; повторный запуск не требует ручной чистки.
5. **Given** поток, у которого в данных нет версии схемы или она несовместима, **When**
   проигрыватель его читает, **Then** проигрывание не начинается (отказ до отправки).

### User Story 3 - Онлайн-цепочка: инциденты появляются по мере поступления потоков (Priority: P3)

Аналитик открывает консоль, пока в брокер идут потоки. Инциденты появляются и растут на глазах:
новый алерт того же атакующего в пределах окна дополняет уже открытый инцидент, новые атакующие
дают новые инциденты, предложения плейбуков появляются вместе с инцидентом. Модель — та же, что
в пакетном режиме (детектор 002 или ансамбль 004), правило направления и группировка — те же.

**Why this priority**: это и есть смысл фичи — SIEM в реальном времени. Зависит от US1 и US2.

**Independent Test**: запустить потребителя и проигрыватель test `unsw_time` ×60 → в консоли за
время проигрывания появляются инциденты; после окончания состав инцидентов, алертов и
предложенных действий совпадает с пакетным прогоном того же входа.

**Acceptance Scenarios**:

1. **Given** запущенный потребитель и пустой топик, **When** в брокер приходит атакующий поток,
   **Then** в пределах нескольких секунд в консоли виден алерт и инцидент (новый или дополненный).
2. **Given** открытый инцидент атакующего, **When** приходит новый алерт того же ключа не позже
   окна группировки после предыдущего, **Then** он добавляется в тот же инцидент (число алертов,
   время последнего алерта, цели, при необходимости серьёзность обновляются), новый инцидент не
   создаётся.
3. **Given** разрыв больше окна группировки, **When** приходит алерт того же ключа, **Then**
   открывается новый инцидент — как в пакетном режиме.
4. **Given** серьёзность инцидента поднялась от роста числа алертов, **When** аналитик смотрит
   карточку, **Then** видно, что серьёзность изменилась и почему, а предложенное действие
   соответствует новой серьёзности, если по нему ещё не принято решение.
5. **Given** аналитик уже принял решение по действию или закрыл инцидент, **When** приходят новые
   алерты того же ключа в пределах окна, **Then** решение аналитика не отменяется и не
   переписывается автоматически, а новые алерты становятся заметны аналитику (см. FR-017).
6. **Given** один и тот же вход, **When** он обработан онлайн и пакетным `soc run`, **Then**
   вердикты всех потоков, набор инцидентов (ключ, границы, число алертов, серьёзность) и
   предложенные действия совпадают.
7. **Given** модель прогона — ансамбль или детектор, **When** потребитель запускается, **Then**
   все проверки модели 004 (эксперты на месте, версии, схема) выполняются до чтения первого
   сообщения; при ошибке потребитель не стартует.

### User Story 4 - Надёжность: перезапуск без потерь и без дублей (Priority: P4)

Потребитель можно остановить (Ctrl+C, сбой, перезагрузка хоста) и запустить снова: он продолжает
с того места, где остановился, ни один поток не теряется и ни один алерт не появляется дважды.
Повторная доставка сообщения брокером не создаёт дублей.

**Why this priority**: без этого потоковой цепочке нельзя доверять; но проверяется на уже
работающей цепочке US3.

**Independent Test**: прервать потребителя посреди проигрывания и запустить снова → итог в
хранилище такой же, как при непрерывной обработке; повторно отправить уже обработанную часть
сообщений → число алертов не изменилось.

**Acceptance Scenarios**:

1. **Given** потребитель обработал часть сообщений, **When** его принудительно прерывают и
   перезапускают, **Then** обработка продолжается с первого необработанного сообщения, итоговые
   инциденты совпадают с непрерывной обработкой.
2. **Given** сообщение доставлено повторно (перезапуск до подтверждения, повтор производителя),
   **When** потребитель его получает, **Then** алерт не дублируется, счётчики инцидента не растут.
3. **Given** хранилище недоступно (заблокировано, диск полон), **When** потребитель не может
   записать результат, **Then** он не подтверждает сообщения брокеру, сообщает об ошибке и
   останавливается (или ждёт), не теряя данные.
4. **Given** сообщение с несовместимой версией схемы или битое, **When** потребитель его
   получает, **Then** оно не роняет потребителя: откладывается в отдельный топик «отвергнутых» с
   причиной, счётчик отвергнутых виден в наблюдаемости.

---

### User Story 5 - Наблюдаемость потока (Priority: P5)

Разработчик и аналитик видят, как чувствует себя поток: сколько потоков в секунду обрабатывается,
на сколько потребитель отстаёт от брокера, какая задержка от появления потока до алерта, сколько
сообщений отвергнуто; видно, живы ли брокер и потребитель.

**Why this priority**: без этого невозможно доказать цели производительности и заметить
отставание; но сама цепочка работает и без экрана наблюдаемости.

**Independent Test**: во время проигрывания команда статуса (и панель консоли) показывают
пропускную способность, отставание, задержку и число отвергнутых; при остановленном потребителе
статус это честно показывает.

**Acceptance Scenarios**:

1. **Given** идёт проигрывание, **When** открыт статус потока, **Then** видны: потоков/с,
   отставание (сообщений и секунд), задержка поток→алерт (медиана и 95-й перцентиль), число
   отвергнутых, время последней обработки.
2. **Given** потребитель остановлен, а сообщения продолжают приходить, **When** открыт статус,
   **Then** видно растущее отставание и что потребитель не работает.
3. **Given** консоль аналитика, **When** идёт онлайн-сеанс, **Then** на панели видно, что сеанс
   «живой», и его основные показатели.

---

### Edge Cases

- **Потоки не по порядку.** Сенсор отдаёт поток, когда тот закончился, поэтому поток,
  начавшийся раньше, может прийти позже. Группировка должна давать тот же результат, что
  пакетная, если опоздание не больше допустимого (см. FR-013); сильно опоздавший поток всё равно
  обрабатывается, но это отмечается. Если опоздавший алерт «склеивает» два открытых инцидента
  одного атакующего, они сливаются (см. FR-013); аналитик, открывший поглощённый инцидент,
  видит ссылку на инцидент, в который он объединён.
- **Время трафика ≠ время на часах.** Окно 15 минут считается по времени трафика (как в
  пакетном режиме), а задержка — по часам; при проигрывании 2015 года оба времени живут
  отдельно.
- **Два потребителя одного топика одновременно** — не должно давать дублей и конфликтов в
  хранилище (второй либо не стартует, либо делит работу без повторов).
- **Пустой поток / тишина** — инциденты не «зависают»: статус показывает, что сообщений нет, а
  открытые инциденты остаются корректными.
- **Проигрывание того же входа второй раз** — это новый сеанс со своими инцидентами (как новый
  пакетный прогон), а не дубли в старом.
- **Брокер перезапустился** — потребитель переподключается сам, без потерь.
- **Машина стенда не хватает памяти / хост под нагрузкой** — отставание растёт, но данные не
  теряются; статус это показывает.
- **Модель заменили во время сеанса** (переобучили) — сеанс продолжает работать моделью, с
  которой стартовал; новая модель — только в новом сеансе.
- **Старые пакетные прогоны** в хранилище продолжают открываться в консоли как раньше.

## Requirements *(mandatory)*

### Functional Requirements

**Брокер и стенд**

- **FR-001**: Проект ДОЛЖЕН содержать воспроизводимые скрипты и инструкцию, создающие на хосте
  Windows с Hyper-V Linux-машину с брокером сообщений, внутреннюю сеть между хостом и машиной и
  нужные топики. Docker и WSL2 не требуются.
- **FR-002**: Каждый шаг, меняющий систему владельца (скачивание образа ОС, создание сети,
  машины, выделение памяти и диска), ДОЛЖЕН выполняться только после явного подтверждения и
  заранее сообщать, что будет сделано и сколько ресурсов займёт; повторный запуск шагов ДОЛЖЕН
  быть безопасным.
- **FR-003**: Брокер ДОЛЖЕН работать без отдельного сервиса координации, хранить сообщения на
  диске машины и переживать её перезагрузку без потери неподтверждённых сообщений; срок хранения
  сообщений задаётся в конфиге.
- **FR-003a**: Сеть стенда ДОЛЖНА быть разделена на две: **служебную** (хост, брокерная машина,
  в 006 — сенсор) и **сеть стенда** (в 006 — атакующий, жертвы и интерфейс сенсора только на
  прослушивание). Брокер слушает только служебную сеть; из сети стенда он недоступен. В 005
  создаётся служебная сеть и заготовка сети стенда, а команда проверки подтверждает, что брокер
  не отвечает с адреса сети стенда.
- **FR-004**: ДОЛЖНА быть команда проверки брокера с хоста: доступность, версия, список топиков,
  понятная ошибка за ограниченное время, если машина выключена.

**Сообщения**

- **FR-005**: Сообщение о потоке ДОЛЖНО содержать все поля схемы признаков 001 (те же имена и
  типы, что использует модель, — train = serve), идентификатор потока, источник и версию схемы.
  Формат описывается один раз и проверяется тестом на обоих концах.
- **FR-006**: Потребитель ДОЛЖЕН отвергать сообщения с несовместимой мажорной версией схемы или
  нарушением формата, не останавливаясь: такое сообщение попадает в топик отвергнутых с причиной.
- **FR-007**: Метка класса (для размеченного входа) МОЖЕТ передаваться в сообщении только для
  оценки и сводки; в модель она не подаётся (как в 002).

**Производители**

- **FR-008**: ДОЛЖЕН быть проигрыватель части разбиения 001 и проигрыватель PCAP (извлечение тем
  же экстрактором 001) с режимами «реальное время × N» (паузы по времени начала потоков) и «как
  можно быстрее», с прогрессом и итоговой сводкой.
- **FR-009**: Проигрыватель ДОЛЖЕН отправлять потоки в порядке времени трафика, с ключом,
  сохраняющим порядок потоков одного источника; повторная отправка того же потока ДОЛЖНА быть
  распознаваема потребителем как тот же поток.
- **FR-010**: Формат и путь сообщений ДОЛЖНЫ позволять в 006 подключить живой сенсор как ещё
  одного производителя без изменений потребителя.

**Потребитель (онлайн-цепочка)**

- **FR-011**: Потребитель ДОЛЖЕН использовать ту же модель и те же правила, что пакетный режим:
  загрузку модели и все её проверки (004), правило атакующей стороны, окно группировки,
  серьёзность, плейбуки с защищённым списком и страховкой класса `anomaly`. Правила не
  дублируются: пакетный и потоковый режимы вызывают одну и ту же логику.
- **FR-012**: Потребитель ДОЛЖЕН обрабатывать сообщения пачками по мере поступления и записывать
  алерты, новые и дополненные инциденты и предложения действий в хранилище так, чтобы консоль 003
  видела их без перезапуска.
- **FR-013**: Группировка в инциденты ДОЛЖНА давать тот же результат, что пакетная, для потоков,
  опоздавших по времени трафика не больше чем на заданную в конфиге величину; потоки, опоздавшие
  сильнее, обрабатываются и отмечаются как опоздавшие. Алерты и инциденты не придерживаются:
  опоздавший алерт, который по времени трафика сокращает разрыв между двумя инцидентами одного
  ключа до окна или меньше, вызывает слияние — более поздний инцидент поглощается более ранним
  (алерты переносятся, счётчики и серьёзность пересчитываются, у поглощённого статус «объединён с
  <id>», его предложение действия снимается, событие пишется в аудит). Если по поглощаемому
  инциденту уже есть решение аналитика, слияние не выполняется (FR-017), а случай попадает в
  расхождения отчёта сравнения (FR-021).
- **FR-014**: При дополнении инцидента ДОЛЖНЫ обновляться число алертов, время последнего
  алерта, цели, максимальный и средний скор и серьёзность (с пояснением); изменение серьёзности
  записывается в историю инцидента.
- **FR-015**: Идентичность алертов ДОЛЖНА определяться по (сеанс, поток): повторная доставка не
  создаёт дублей и не меняет счётчики.
- **FR-016**: Подтверждение обработки брокеру ДОЛЖНО происходить только после успешной записи
  результата в хранилище; после перезапуска потребитель продолжает с первого неподтверждённого
  сообщения.
- **FR-017**: Автоматика НЕ ДОЛЖНА менять решения аналитика: если по действию инцидента решение
  уже принято или инцидент закрыт, новые алерты того же ключа в пределах окна дописываются в
  тот же инцидент (состав инцидентов совпадает с пакетным режимом), статус, резолюция и решение
  по действию не меняются, а инцидент получает заметную пометку «новые алерты после решения» с
  их числом и временем первого такого алерта — в карточке, в списке (фильтр) и в аудите.
- **FR-018**: Онлайн-сеанс ДОЛЖЕН быть виден в хранилище и консоли как прогон со статусом
  «идёт»/«остановлен»/«завершён», с источником, моделью и временем начала; старые пакетные
  прогоны не меняются. Сеанс привязан к источнику: перезапуск потребителя продолжает тот же
  сеанс (статус «остановлен» → «идёт», прежние инциденты продолжают дополняться). Проигрыватель
  в конце данных отправляет отметку «конец данных»; сеанс становится «завершён», когда всё до
  неё обработано. Сеанс без конца (живой сенсор, 006) завершается только явной командой.
  Повторное проигрывание того же входа — новый источник и новый сеанс.
- **FR-019**: Одновременно ДОЛЖЕН работать не больше одного потребителя на сеанс; попытка запуска
  второго — понятный отказ (или безопасное разделение работы без дублей).
- **FR-020**: Запись в хранилище ДОЛЖНА сохранять гарантии 002/003: аудит только на добавление
  (появление/дополнение инцидента и предложение действия фиксируются), оптимистичная блокировка
  при одновременных решениях аналитика и дописывании алертов.

**Эквивалентность и наблюдаемость**

- **FR-021**: ДОЛЖНА быть команда сравнения онлайн-сеанса с пакетным прогоном того же входа:
  вердикты потоков, инциденты (ключ, границы, число алертов, серьёзность) и предложенные
  действия; расхождения перечисляются с причиной.
- **FR-022**: ДОЛЖНЫ собираться и показываться в CLI и на панели консоли: пропускная способность,
  отставание потребителя (сообщений и секунд), задержка «поток пришёл → алерт записан» (медиана и
  95-й перцентиль), число отвергнутых и опоздавших, время последней обработки, живость брокера и
  потребителя.
- **FR-023**: Все параметры (адрес брокера, имена топиков, размер пачки, допустимое опоздание,
  срок хранения, скорость проигрывания по умолчанию) ДОЛЖНЫ быть в конфиге, не в коде.
- **FR-024**: Сообщения, отчёты, комментарии и инструкция — на русском, как в 001–004.

### Key Entities

- **Сообщение о потоке**: поля схемы признаков 001, идентификатор потока, источник, версия
  схемы, время отправки; для размеченного входа — метка (только для оценки).
- **Топик потоков / топик отвергнутых**: очередь входящих потоков; очередь отвергнутых сообщений
  с причиной.
- **Сеанс (онлайн-прогон)**: непрерывная обработка одного источника; модель, источник, статус,
  время начала/последней обработки, показатели; в хранилище — прогон.
- **Позиция потребителя**: до какого сообщения обработка подтверждена; хранится так, чтобы
  перезапуск продолжал с неё.
- **Инцидент (дополняемый)**: как в 002–004, плюс история изменений от новых алертов
  (рост числа алертов, смена серьёзности).
- **Показатели потока**: пропускная способность, отставание, задержки, отвергнутые, опоздавшие.
- **Отчёт сравнения**: онлайн-сеанс против пакетного прогона того же входа, расхождения.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Машина с брокером поднимается по инструкции с нуля не более чем за 30 минут
  (без учёта скачивания образа) и повторно пересоздаётся с тем же результатом; проверка
  доступности с хоста отвечает не дольше 10 секунд.
- **SC-002**: Часть test `unsw_time` (≈282 тыс. потоков) в режиме «как можно быстрее» полностью
  обрабатывается онлайн-цепочкой не дольше 10 минут, а к моменту окончания проигрывания
  отставание потребителя не превышает 30 секунд.
- **SC-003**: В режиме «реальное время» задержка от поступления потока до появления алерта в
  хранилище — не больше 5 секунд для 95% алертов; инцидент появляется в консоли не позже чем
  через 15 секунд после поступления первого атакующего потока (с учётом автообновления 10 с).
- **SC-004**: Онлайн-обработка test `unsw_time` даёт 100% совпадение вердиктов потоков и
  набора инцидентов (ключ, границы, число алертов, серьёзность) и предложенных действий с
  пакетным `soc run` того же входа при потоках, пришедших в пределах допустимого опоздания.
- **SC-005**: При 3 принудительных прерываниях потребителя во время проигрывания итоговое
  состояние хранилища совпадает с непрерывной обработкой: 0 потерянных потоков, 0 дублей
  алертов.
- **SC-006**: 100% сообщений с несовместимой версией схемы или битых попадают в топик
  отвергнутых с причиной, потребитель при этом не останавливается.
- **SC-007**: Брокерная машина, потребитель и консоль вместе укладываются в 16 ГБ RAM хоста с
  запасом не меньше 4 ГБ для остальных программ владельца.
- **SC-008**: Все тесты 002–004 проходят без изменения ожиданий; пакетный `soc run` работает как
  раньше.

## Assumptions

- Hyper-V включён (Windows 11 Pro for Workstations), образ Ubuntu Server LTS скачивается один
  раз с официального сайта по подтверждению владельца; доступ машины в интернет нужен только при
  установке.
- Брокер — Apache Kafka в режиме KRaft (по выбору владельца), один узел, фактор репликации 1:
  отказоустойчивость кластера вне объёма (одна машина на стенде). Для тестов без машины брокер
  подменяется встроенной заглушкой, так что быстрые тесты не требуют ВМ.
- Машине выделяется ~2 ГБ RAM и ~20 ГБ диска. Брокер доступен только из служебной сети
  (FR-003a); аутентификация и шифрование брокера — вне объёма, защита — изоляция сетей.
- Потребитель работает на хосте Windows тем же пакетом `mlsiem`; хранилище — та же SQLite
  `var/soc.db` (схема мигрирует, если нужно), консоль 003 — без изменений в принципе работы.
- Эквивалентность проверяется на размеченном разбиении с проигрыванием в порядке времени
  трафика; допустимое опоздание по умолчанию — 2 минуты времени трафика.
- Сеанс = обработка одного источника (одно проигрывание или один сенсор) независимо от числа
  перезапусков потребителя (FR-018).
- Живой сенсор, машины жертвы и атакующего — фича 006; окна потоков и нейросетевой детектор —
  отдельная фича после стенда.
- Модель прогона выбирается как в 004 (`models/ensemble`, иначе `models/detector`).
