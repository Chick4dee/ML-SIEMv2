# Implementation Plan: Потоковая обработка через Kafka

**Branch**: `005-kafka-streaming-chain` | **Date**: 2026-09-25 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/005-kafka-streaming-chain/spec.md`

## Summary

Цепочка 002–004 становится потоковой. Брокер Apache Kafka 4.x (KRaft, один узел) работает на
Linux-машине Hyper-V `mlsiem-broker` в отдельной служебной сети `mlsiem-mgmt`; сеть стенда
`mlsiem-lab` (Private) создаётся заготовкой для 006, брокера в ней нет. Машина поднимается
идемпотентными PowerShell-скриптами с подтверждением и автоустановкой Ubuntu 24.04 (seed-ISO
собирается Python-командой). Проигрыватели разбиения 001 и PCAP шлют по одному потоку на
сообщение (JSON, все колонки схемы 001, версия схемы в заголовке) с паузами «реальное время × N»
или без пауз, в конце — отметка `end`. Потребитель на хосте (`confluent-kafka`) читает пачками,
считает вердикты той же `LoadedModel.verdict_frame`, применяет правило направления, группирует
**инкрементально** (окно вокруг интервала инцидента + слияние при «склейке» опоздавшим алертом)
и пишет алерты, инциденты, действия, аудит, вердикты пачки и позицию в одной транзакции SQLite;
в Kafka позиция подтверждается только после COMMIT. Дубли отсекаются по (сеанс, flow_uid).
После решения аналитика инцидент дополняется с пометкой «новые алерты после решения».
Показатели (скорость, отставание, задержка, отвергнутые) — в CLI и на панели консоли. Команда
сравнения доказывает совпадение онлайн-сеанса с пакетным `soc run`. Схема БД 4.
Подробности — [research.md](research.md).

## Technical Context

**Language/Version**: Python 3.11 (хост); на брокерной машине — Ubuntu Server 24.04 LTS,
OpenJDK 21 (headless), Kafka 4.x; PowerShell 5.1 для Hyper-V

**Primary Dependencies**: новые — `confluent-kafka` (клиент), `orjson` (JSON, уже в окружении —
делаем явной), `pycdlib` (extra `stand`: сборка seed-ISO); остальное из 001–004 (polars,
FastAPI/Jinja2/htmx, sklearn/LightGBM через `load_model`)

**Storage**: Kafka — топики `mlsiem.flows`, `mlsiem.flows.rejected` на диске ВМ (7 дней); SQLite
`var/soc.db` — схема 4 (сеансы, позиции, отметки обработанных, аренда, показатели); вердикты
сеанса — `var/runs/<run_id>/verdicts/part-*.parquet`

**Testing**: pytest; брокер-заглушка `MemoryBroker` (партиции, позиции, повторная доставка,
«сбой» между записью и подтверждением) — все быстрые тесты без ВМ; property-тест «инкрементально
пачками в любом допустимом порядке = пакетно» на синтетике; тесты миграции 3 → 4; маркер
`stand` — тесты на настоящем брокере (выключены по умолчанию), `slow` — полный test `unsw_time`

**Target Platform**: хост Windows 11 Pro for Workstations (Hyper-V), CPU; ВМ Gen 2, 2 vCPU, 2 ГБ

**Project Type**: Python-пакет с CLI, потоковым потребителем и локальным веб-сервисом + скрипты
развёртывания стенда

**Performance Goals**: 282 тыс. потоков при `--speed max` ≤ 10 мин (ожидание 1–3 мин),
отставание к концу ≤ 30 с (SC-002); задержка поток → алерт p95 ≤ 5 с в реальном времени,
инцидент в консоли ≤ 15 с (SC-003)

**Constraints**: без Docker/WSL2; 16 ГБ RAM хоста, запас ≥ 4 ГБ (SC-007); брокер без
аутентификации — защита изоляцией сетей (FR-003a); каждое действие на машине владельца — с
подтверждением (FR-002); одна логика правил для пакетного и потокового режимов (FR-011)

**Scale/Scope**: 1 брокер, 1 потребитель, 1–2 одновременных источника; ~8 тыс. алертов на
проигрывание; новые подпакеты `mlsiem.stream` и `mlsiem.stand`, каталог `stand/`

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Принцип | Как выполняется | Статус |
|---|---|---|
| I. Вертикальные срезы | Сквозной результат: машина с брокером → проигрыватель → онлайн-цепочка → инциденты в консоли в реальном времени; наблюдаемость (мониторинг) строится внутри этой фичи, где она нужна | ✅ |
| II. Train = serve | Сообщение несёт все колонки схемы 001 с версией; типы восстанавливаются по схеме; модель та же (`load_model`), вердикты — та же функция; PCAP — тот же экстрактор; метка в модель не попадает | ✅ |
| III. Честная оценка | Модели не обучаются; эквивалентность онлайн/пакет доказывается командой сравнения и тестом | ✅ (не применимо к обучению) |
| IV. Решения через эксперимент | Детекция не меняется | ✅ (не применимо) |
| V. Безопасный SOAR | Плейбуки те же; действия только предлагаются и симулируются; автоматика не меняет решений аналитика (пометка «после решения»); аудит только на добавление, новые события — от `system` | ✅ |
| VI. Воспроизводимость и понятный код | Стенд — идемпотентные скрипты + seed-ISO из шаблонов в git; параметры в `configs/stream.yaml`; тесты на гарантии доставки на заглушке; русские комментарии; журнал | ✅ |
| VII. Прозрачное авторство | Коммитит владелец | ✅ |
| Ограничения среды | Docker/WSL2 не нужны — брокер в Hyper-V (явно в плане); ВМ 2 ГБ, запас памяти хоста проверяется (SC-007) | ✅ |
| Язык | Сообщения, инструкции, комментарии — по-русски | ✅ |

Нарушений нет.

**Повторная проверка после фазы 1**: контракт сообщений фиксирует все колонки схемы и версию
(II); инкрементальная группировка — отдельная функция рядом с пакетной, а их равенство
закрепляет property-тест (VI; пакетный путь сознательно не переписывается ради SC-008, см.
Complexity Tracking); миграция 3 → 4 пересоздаёт аудит по проверенному образцу 003 с
сохранением `entry_id` (V); действия на машине владельца только из его PowerShell с
подтверждением (FR-002). Статус — ✅.

**Structure Decision**: весь транспорт — в новом подпакете `mlsiem.stream`, граница с брокером —
интерфейс `Broker` (реальный клиент и заглушка). Логика SOC не дублируется: потребитель зовёт те
же `load_model`, `compute_verdicts`/`alerts_from_verdicts`, `severity`, `propose_action`, а
новое — только инкрементальная группировка (`stream/incremental.py`) с доказательством
равенства пакетной. Инфраструктура стенда (PowerShell, шаблоны) — в `stand/` вне пакета, чтобы
006 добавил туда машины атакующего и жертвы.
