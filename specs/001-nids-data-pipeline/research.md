# Research: Пайплайн данных NIDS (001)

Решения фазы 0. Формат: решение → почему → что ещё рассматривали.

## R1. Экстрактор потоков

- **Решение**: nfstream 6.6 (нужен Npcap на Windows — установлен). Настройки фиксируются
  в одном месте и входят в схему признаков: `statistical_analysis=True`, `splt_analysis=0`,
  `n_dissections=20`, таймауты по умолчанию (`idle_timeout=120 c`, `active_timeout=1800 c`),
  `accounting_mode=0` (байты по уровню IP).
- **Почему**: тот же экстрактор можно направить на сетевой интерфейс — это и есть train = serve
  (конституция, II). В v1 он отработал на всех 93 захватах.
- **Альтернативы**: CICFlowMeter (Java, известные баги с TCP-завершением), Zeek (сильный,
  но на Windows только через WSL/Docker, которых пока нет), Argus (его выдачу используют
  авторы датасетов, но без live-режима под Windows).

## R2. Память и потоковая обработка

- **Решение**: не собирать весь захват в `DataFrame` в памяти. nfstream пишет потоки
  на диск построчно (`to_csv` во временный файл), затем polars лениво (`scan_csv` →
  `sink_parquet`) переводит их в parquet. Захваты обрабатываются по одному; nfstream
  внутри параллелит разбор по ядрам.
- **Почему**: пиковая память ограничена таблицей одного захвата при разметке (оценка — единицы
  ГБ для 2-гигабайтного PCAP), а не всем датасетом. Укладываемся в 16 ГБ (FR-010).
- **Оговорка**: сортировка (R3) требует держать таблицу одного захвата в памяти целиком —
  потоковой записи на этом шаге нет, и именно здесь пик. Поэтому пик проверяется заранее
  на самом большом PCAP UNSW, до полного прогона; если выйдет больше 12 ГБ — сортировать
  частями (по часовым окнам) и склеивать.
- **Альтернативы**: `to_pandas()` как в v1 — работает, но держит всё в памяти и даёт
  двойную копию pandas → polars; итерация по объектам `NFlow` в Python — медленно.

## R3. Детерминизм

- **Решение**: nfstream раздаёт потоки по нескольким «метрам», поэтому порядок строк между
  прогонами может отличаться. После извлечения таблица сортируется по
  (`bidirectional_first_seen_ms`, `src_ip`, `src_port`, `dst_ip`, `dst_port`, `protocol`,
  `bidirectional_last_seen_ms`, `bidirectional_packets`), затем по всем остальным колонкам
  схемы по порядку — иначе строки, совпавшие по этим 8 полям, встают в случайном порядке
  и получают разные номера между прогонами. Поле `id` отбрасывается,
  а `flow_uid` = `<capture_id>/<номер строки после сортировки>`. Идентичность проверяется
  хешем содержимого таблицы (не байтов файла), он пишется в манифест захвата.
- **Почему**: SC-003 требует совпадения результатов; байты parquet зависят от версии
  библиотеки, а хеш содержимого — нет.
- **Альтернативы**: `n_meters=1` — детерминированно, но в разы медленнее.

## R4. Возобновление после прерывания

- **Решение**: у каждого захвата — отпечаток (размер + mtime + SHA-256 первых и последних
  16 МБ) и манифест `<capture_id>.json` со статусом. Результат пишется во временный файл
  и переименовывается только после успешной записи (атомарно). При запуске захват
  пропускается, если есть готовый результат с тем же отпечатком входа, версией схемы
  и версией правил разметки.
- **Почему**: полный SHA-256 по 100 ГБ занимает минуты на каждый запуск; частичный
  отпечаток ловит подмену/обрезку файла на практике.
- **Альтернативы**: только стадии DVC — перезапускают всю стадию целиком, нет возобновления
  внутри 80 файлов; полный хеш — надёжнее, но медленно (оставлен как флаг `--full-hash`).

## R5. Разметка

- **Решение**: перенести проверенный алгоритм v1, переписав код с тестами:
  - совпадение 5-кортежа в любой ориентации; для протоколов без портов — 3-кортеж;
  - время: расстояние от старта потока до **интервала** записи разметки, допуск 60 с
    (nfstream режет длинные потоки по `active_timeout`, их сегменты стартуют позже записи);
  - при нескольких кандидатах — ближайший по времени, затем детерминированный тай-брейк
    по началу записи и метке;
  - UNSW: время в epoch-секундах (UTC), несопоставленное → `benign`;
  - CTU-13: время в локальном времени Праги → UTC явно; несопоставленное → `unlabeled`
    (FR-008); классы botnet / normal / background.
- **Почему**: в v1 доля сопоставления CTU-13 0.65–0.995, UNSW выровнен без сдвига.
- **Альтернативы**: перенос меток из готовых CSV авторов (UNSW-NB15_1..4.csv) без
  переэкстракции — ломает train = serve.

## R6. Таксономия

- **Решение**: канонические классы: `benign`, `background`, `botnet`, `dos`, `exploits`,
  `fuzzers`, `generic`, `reconnaissance`, `backdoor`, `analysis`, `shellcode`, `worms`,
  плюс служебный `unlabeled`. Подписи источника нормализуются (trim + lower) и сводятся
  таблицей; незнакомая подпись — ошибка с указанием значения.
- **Почему**: одна таблица соответствий, проверяемая тестом; `backdoors`/`backdoor` в UNSW
  реально встречаются оба.

## R7. Разбиение

- **UNSW-NB15 (основное, `unsw_time`)**: внутри каждого дня потоки упорядочены по
  `bidirectional_first_seen_ms`; границы — по квантилям числа потоков 0.70 и 0.85 (а не по
  часам, потому что трафик неравномерен). Вокруг каждой границы зазор ±10 минут: потоки,
  чей интервал [first_seen, last_seen] пересекает зону зазора, исключаются.
  10 минут > `idle_timeout` (2 мин) и перекрывают типичную длительность сессий атак.
- **UNSW-NB15 (дополнительное, `unsw_cross_day`)**: день 22-01-2015 целиком → train;
  день 17-02-2015: первые 15% потоков по времени → val, остальное → test (с тем же зазором).
  Изначально val брался из конца первого дня, но полный прогон показал, что атаки в разметке
  22-01-2015 есть только в первых ~40% потоков — val получался чистым benign, и ни порог,
  ни аудит на нём не подобрать. Начало второго дня содержит все 10 классов.
- **CTU-13 (`ctu13_scenario`)**: сценарий целиком в одной части; семейства определены
  по бинарникам в папках сценариев:
  - Neris 1, 2, 9; Rbot 3, 4, 10, 11; Virut 5, 13; Menti 6; Sogou 7; Murlo 8; NSIS.ay 12.
  - По умолчанию: train — 1, 2, 3, 4, 5, 6, 9, 13; val — 7, 10, 11; test — 8, 12
    (Murlo и NSIS.ay в train не встречаются → проверка на незнакомое семейство, FR-016a).
- Разбиение описывается манифестом (интервалы/сценарии, параметры, хеш) и отдельной
  таблицей `flow_uid → part`; исключённые из-за зазора потоки учитываются в отчёте.
- **Альтернативы**: случайный стратифицированный сплит — запрещён конституцией (III).

## R8. Проверка на артефакты датасета

- **Решение**: для каждого поля (признаки модели, служебные поля, DPI-поля) обучить
  дерево решений глубины 4 только на этом поле по train и посчитать macro PR-AUC на val.
  Базовая линия — macro PR-AUC «угадывания по доле класса» (= средняя доля классов).
  Выборка — до 500 тыс. потоков на часть, стратифицированно по классу, с фиксированным сидом.
  Статусы:
  - **dangerous** — служебное/идентификационное/DPI-поле (IP, порты, время, MAC, имя
    сервера и т. п.) с приростом над базовой линией ≥ 0.10;
  - **suspicious** — любой признак модели с одиночным macro PR-AUC ≥ 0.90 (требует ручного
    разбора: либо признак действительно сильный, либо это след генератора);
  - **ok** — остальные.
  Категориальные поля кодируются по частоте на train; IP-адреса дополнительно проверяются
  как «IP целиком» и как подсеть /24.
- **Почему**: дешёвая и объяснимая проверка, повторяющая урок v1; порог и все цифры
  попадают в отчёт (FR-018).
- **Альтернативы**: permutation importance на полной модели — зависит от выбранной модели,
  а её в 001 нет; SHAP — там же.

## R9. Отчёт

- **Решение**: самостоятельный HTML (стили и графики встроены: matplotlib → PNG в base64)
  плюс краткая Markdown-сводка. Шаблон — Jinja2.
- **Почему**: HTML открывается двойным кликом и на GitHub Pages; Markdown читается прямо
  в репозитории.
- **Альтернативы**: Jupyter-ноутбук — тяжелее читать без запуска; ydata-profiling — много
  лишнего и нет наших проверок.

## R10. Версионирование данных и окружение

- **Решение**: DVC 3.x, конвейер из стадий в `dvc.yaml` (`flows_unsw`, `flows_ctu13`,
  `split_*`, `audit_*`, `compare_v1`, `report`) с локальным remote `A:\dvc-remote-v2`. Окружение — uv
  (`pyproject.toml` + `uv.lock`), Python 3.11. Пути к датасетам — в `configs/data.yaml`,
  не в коде.
- **Почему**: большие файлы не в git (FR-013); `dvc repro` пересобирает только изменившееся;
  `uv.lock` фиксирует версии зависимостей для воспроизводимости.
- **Альтернативы**: Git LFS — лимиты GitHub и платные объёмы; pip + requirements.txt —
  без лок-файла.

## R11. Безопасность при работе с датасетами

- **Решение**: пайплайн выбирает только `*.pcap`, `*.pcapng`, `*.binetflow` и CSV разметки
  по явным шаблонам. В папках CTU-13 лежат настоящие бинарники ботнетов (`*.exe`) —
  код их не открывает, не копирует и не запускает; в `.gitignore` и в DVC они не попадают.
- **Почему**: случайный запуск малвари на рабочей машине недопустим.

## R12. Тесты

- **Решение**: pytest. Модульные тесты на разметку, таксономию, разбиение, аудит —
  на синтетических таблицах. Интеграционный тест на маленьком PCAP, сгенерированном
  scapy (фикстура < 100 КБ, коммитится). Опциональный «медленный» тест на реальном
  сценарии CTU-13 №7 (51 поток) — запускается, если датасет доступен (`-m slow`).
- **Почему**: быстрые тесты без 100 ГБ данных + одна проверка на реальном формате.
