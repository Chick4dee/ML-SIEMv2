# Feature Specification: Пайплайн данных NIDS

**Feature Branch**: `001-nids-data-pipeline`

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "Фича 001 — пайплайн данных для NIDS: из сырых сетевых захватов (PCAP)
получить размеченный, проверенный и готовый к экспериментам набор сетевых потоков. Источники
UNSW-NB15 и CTU-13; одна команда от PCAP до размеченной таблицы; одинаковое извлечение признаков
для обучения и нового PCAP; единая таксономия; разбиение без утечек; отчёт о качестве данных
с проверкой на артефакты датасета; укладываться в 16 ГБ RAM с продолжением после прерывания;
воспроизводимость; сверка с v1."

## Clarifications

### Session 2026-09-23

- Q: Как делить UNSW-NB15? → A: внутри каждого дня по времени (≈70/15/15) с зазором
  на границах; разбиение «день на день» считается дополнительно. *(Уточнено при анализе:
  доли — по числу потоков, упорядоченных по времени, а не по часам.)*
- Q: (после полного прогона) В «день на день» val из конца первого дня оказался без атак —
  атаки в разметке дня 22-1-2015 есть только в первых ~40% потоков. Как строить val?
  → A: val — начало второго дня (первые 15% потоков), test — остальная часть второго дня
  с зазором; первый день целиком — train.
- Q: Роль CTU-13? → A: отдельный набор со своим разбиением по сценариям, с UNSW-NB15
  не смешивается.

## User Scenarios & Testing *(mandatory)*

Главное действующее лицо — **исследователь** (владелец проекта), который готовит данные для
экспериментов с детекцией. Второстепенное — **зритель портфолио** (рекрутер, интервьюер),
который смотрит отчёт о данных.

### User Story 1 - Размеченный набор потоков из PCAP одной командой (Priority: P1)

Исследователь указывает датасет (или один захват/сценарий) и запускает одну команду. Система
извлекает из захватов сетевые потоки с фиксированным набором признаков, сопоставляет каждый поток
с разметкой датасета и сохраняет размеченную таблицу потоков с единой меткой класса.

**Why this priority**: без размеченных потоков невозможен ни один эксперимент; это минимальный
сквозной результат фичи.

**Independent Test**: запустить команду на одном небольшом захвате CTU-13 и получить таблицу
потоков, где у каждого потока есть признаки, исходная и каноническая метка, а сводка показывает
долю сопоставленных потоков.

**Acceptance Scenarios**:

1. **Given** скачанный сценарий CTU-13 с файлом разметки, **When** исследователь запускает
   команду для этого сценария, **Then** появляется размеченная таблица потоков и сводка
   (всего потоков, сопоставлено, распределение классов).
2. **Given** захват UNSW-NB15 и CSV ground truth, **When** запускается команда, **Then** потоки,
   попавшие в диапазоны атак, получают категорию атаки в единой таксономии, а несопоставленные —
   класс benign (фон генератора).
3. **Given** уже обработанный захват, **When** команда запускается повторно на тех же входах,
   **Then** результат совпадает с предыдущим побайтно (или по контрольной сумме содержимого),
   а повторная обработка не выполняется без необходимости.
4. **Given** обработка всего UNSW-NB15 была прервана на середине, **When** команда запускается
   снова, **Then** уже обработанные захваты пропускаются и работа продолжается с места остановки.

---

### User Story 2 - Разбиение train/val/test без утечек (Priority: P2)

Исследователь получает воспроизводимое разбиение набора на обучающую, валидационную и тестовую
части по времени/захватам, так что потоки одной сессии или соседние по времени фрагменты
не оказываются по разные стороны границы.

**Why this priority**: честная оценка моделей (конституция, принцип III) невозможна без
правильного разбиения; без него любые метрики будущих экспериментов недостоверны.

**Independent Test**: сформировать разбиение и автоматически проверить, что временные интервалы
частей не пересекаются, ни один поток не встречается в двух частях, а повторный запуск даёт
то же разбиение.

**Acceptance Scenarios**:

1. **Given** размеченные таблицы потоков, **When** исследователь формирует разбиение, **Then**
   каждая часть содержит потоки только из своего временного интервала/набора захватов, и это
   зафиксировано в манифесте разбиения.
2. **Given** класс атаки, который попал только в одну часть, **When** разбиение сформировано,
   **Then** это явно отражено в сводке, а не скрыто.

---

### User Story 3 - Отчёт о качестве данных с проверкой на артефакты (Priority: P3)

Исследователь (и зритель портфолио) открывает отчёт, где видно: сколько потоков сопоставилось
с разметкой по каждому захвату, распределение классов по частям разбиения, классы, отсутствующие
в какой-то части, и результат проверки на артефакты датасета — какие отдельные признаки
позволяют тривиальной модели угадывать класс «слишком хорошо» (идентификаторы, время, TTL
и т. п.). Такие признаки помечаются как опасные и рекомендуются к исключению.

**Why this priority**: превращает набор данных в показуемый результат и защищает будущие
эксперименты от завышенных метрик (урок v1 с ROC-AUC 0.98); но сам набор (P1) и разбиение (P2)
полезны и без отчёта.

**Independent Test**: сгенерировать отчёт для готового набора и убедиться, что он открывается
как самостоятельный документ, содержит все перечисленные разделы и список опасных признаков
с числовым обоснованием.

**Acceptance Scenarios**:

1. **Given** готовый набор и разбиение, **When** исследователь строит отчёт, **Then** отчёт
   содержит долю сопоставления по каждому захвату, распределение классов по частям и список
   опасных признаков с оценкой, насколько каждый из них в одиночку предсказывает класс.
2. **Given** признак-идентификатор (например, адрес источника), **When** выполняется проверка на
   артефакты, **Then** он попадает в список опасных, если в одиночку предсказывает класс выше
   порога.

---

### User Story 4 - Те же признаки для нового неразмеченного PCAP (Priority: P4)

Исследователь подаёт произвольный захват без разметки (например, записанный позже на стенде)
и получает таблицу потоков с точно той же схемой признаков и её версией, что и в обучающем
наборе, — только без меток.

**Why this priority**: фундамент для работы на живом трафике (конституция, принцип II);
в рамках 001 достаточно доказать идентичность схемы на файле.

**Independent Test**: прогнать один и тот же захват в режиме «с разметкой» и «без разметки»
и убедиться, что признаки потоков совпадают полностью, отличается только наличие меток.

**Acceptance Scenarios**:

1. **Given** PCAP без разметки, **When** запускается извлечение, **Then** результат имеет ту же
   схему признаков и ту же версию схемы, что и обучающий набор.

---

### User Story 5 - Сверка с v1 (Priority: P5)

Исследователь сравнивает новый набор с готовыми таблицами v1 и видит по каждому захвату/сценарию
разницу в числе потоков и распределении меток, с объяснением значимых расхождений.

**Why this priority**: подтверждает, что переписанный пайплайн не потерял и не испортил данные,
но не блокирует эксперименты.

**Independent Test**: построить таблицу сверки по всем захватам CTU-13 и UNSW-NB15 и проверить,
что расхождения выше порога сопровождаются объяснением.

**Acceptance Scenarios**:

1. **Given** таблицы v1 и новый набор, **When** строится сверка, **Then** по каждому захвату
   показаны число потоков и доли классов в обеих версиях и относительная разница.

---

### Edge Cases

- Захват повреждён или обрезан: обрабатывается всё читаемое, проблема фиксируется в сводке,
  остальные захваты продолжают обрабатываться.
- Захваты в разных форматах (классический pcap и pcapng) — оба поддерживаются.
- Разметка в локальном времени, а захват — в UTC (CTU-13, Прага): часовой пояс источника задаётся
  явно; неверный пояс проявляется резким падением доли сопоставления и виден в отчёте.
- Поток пересекает границу диапазона атаки или сопоставляется с несколькими записями разметки:
  правило выбора метки детерминировано и описано.
- Протоколы без портов (ICMP и др.): сопоставление не опирается на порты.
- Потоки CTU-13 класса background — непроверенный фон, не гарантированно benign: хранятся
  отдельным классом и не смешиваются с benign.
- Грязные подписи классов (регистр, пробелы, ед./мн. число): сводятся к канонической таксономии;
  незнакомая подпись — ошибка с указанием значения, а не молчаливый пропуск.
- Недостаток места на диске или памяти: прогон целиком останавливается (продолжать со
  следующими захватами бессмысленно — они упадут так же) с понятным сообщением; текущий
  захват помечается failed, частично записанных результатов, похожих на готовые, не остаётся.
  Ошибка чтения конкретного файла останавливает только этот захват.

## Requirements *(mandatory)*

### Functional Requirements

**Извлечение и схема признаков**

- **FR-001**: Система ДОЛЖНА извлекать сетевые потоки из PCAP (pcap и pcapng) с фиксированным,
  задокументированным набором признаков.
- **FR-002**: Схема признаков ДОЛЖНА иметь версию; каждая выходная таблица хранит версию схемы,
  с которой создана.
- **FR-003**: Извлечение для размеченных датасетов и для произвольного неразмеченного PCAP
  ДОЛЖНО выполняться одним и тем же кодом с одинаковыми настройками.
- **FR-004**: Для каждого потока ДОЛЖНЫ сохраняться служебные поля (адреса, порты, протокол,
  время начала и конца) для сопоставления и анализа, явно отделённые от признаков для моделей.

**Разметка и таксономия**

- **FR-005**: Система ДОЛЖНА сопоставлять потоки с разметкой UNSW-NB15 (CSV с временными
  диапазонами и 5-кортежами); несопоставленные потоки получают класс benign.
- **FR-006**: Система ДОЛЖНА сопоставлять потоки с разметкой CTU-13 (.binetflow) с явным учётом
  часового пояса источника и обеих ориентаций потока.
- **FR-007**: Каждый поток ДОЛЖЕН иметь исходную метку источника и каноническую метку из единой
  таксономии проекта; класс background CTU-13 остаётся отдельным каноническим классом.
- **FR-008**: Потоки, которые не удалось однозначно сопоставить там, где отсутствие
  сопоставления не означает benign (CTU-13), ДОЛЖНЫ помечаться как unlabeled, а не получать
  метку по умолчанию.

**Запуск, память, воспроизводимость**

- **FR-009**: Одна команда ДОЛЖНА прогонять выбранный датасет целиком или указанный
  захват/сценарий от PCAP до размеченной таблицы и сводки.
- **FR-010**: Обработка ДОЛЖНА укладываться в 16 ГБ RAM для любого захвата из датасетов
  (включая файлы UNSW-NB15 размером около 2 ГБ).
- **FR-011**: Прерванная обработка ДОЛЖНА продолжаться с места остановки без повторной
  обработки завершённых захватов; результаты записываются атомарно.
- **FR-012**: Повторный прогон на тех же входах и той же версии схемы ДОЛЖЕН давать идентичный
  результат; входы, версия схемы и параметры фиксируются в манифесте.
- **FR-013**: Выходные наборы ДОЛЖНЫ версионироваться отдельно от кода репозитория, чтобы
  большие файлы не попадали в git.

**Разбиение**

- **FR-014**: Система ДОЛЖНА формировать разбиение train/val/test по времени и/или захватам,
  без пересечения временных интервалов и без попадания одного потока в две части.
- **FR-015**: Разбиение ДОЛЖНО быть воспроизводимым и описываться манифестом (какие захваты
  и интервалы в какой части).
- **FR-016**: UNSW-NB15 ДОЛЖЕН делиться внутри каждого дня захвата по времени на
  train/val/test: потоки дня упорядочиваются по времени начала, границы ставятся по квантилям
  0.70 и 0.85 их числа (≈70/15/15 потоков, а не часов — трафик за день неравномерен),
  с защитным зазором на каждой границе; потоки,
  попадающие в зазор или пересекающие границу, в части не включаются. Дополнительно ДОЛЖНО
  формироваться альтернативное разбиение «день на день» (первый день целиком — train; второй
  день: первые 15% потоков по времени — val, остальное — test, с тем же зазором) для оценки
  переноса на другой день; оно отражается в отчёте отдельно.
- **FR-016a**: CTU-13 ДОЛЖЕН образовывать отдельный набор со своим разбиением по сценариям
  (сценарий целиком попадает в одну часть) и НЕ ДОЛЖЕН смешиваться с UNSW-NB15 в одном наборе.
  Распределение сценариев по частям фиксируется в манифесте так, чтобы в test было хотя бы одно
  семейство ботнета, отсутствующее в train.

**Отчёт о качестве данных**

- **FR-017**: Система ДОЛЖНА строить самостоятельный отчёт (открывается без запуска проекта),
  включающий: долю сопоставления по захватам, распределение классов по частям разбиения,
  классы, отсутствующие в какой-либо части, и результаты проверки на артефакты.
- **FR-018**: Проверка на артефакты ДОЛЖНА для каждого признака и каждого служебного поля
  оценивать, насколько оно в одиночку предсказывает класс. Служебные поля (идентификаторы,
  время, DPI), превышающие порог прироста над бейзлайном, помечаются как **опасные**;
  признаки модели, в одиночку дающие очень высокое качество, — как **подозрительные**
  (требуют ручного разбора: сильный признак или след генератора). Пороги и значения
  приводятся в отчёте.
- **FR-019**: Система ДОЛЖНА строить сверку с таблицами v1 по каждому захвату: число потоков,
  доли классов, доля сопоставления с разметкой, разница; расхождение числа потоков больше 5%
  (относительно), доли любого класса больше 5 процентных пунктов или снижение доли
  сопоставления требуют объяснения в отчёте.

### Key Entities

- **Захват (Capture)**: исходный PCAP-файл; источник (UNSW-NB15/CTU-13/произвольный),
  идентификатор (день и номер файла или номер сценария), контрольная сумма, статус обработки.
- **Поток (Flow)**: двунаправленный сетевой поток; служебные поля (адреса, порты, протокол,
  время), признаки по схеме, исходная и каноническая метка, ссылка на захват.
- **Схема признаков (Feature Schema)**: упорядоченный список признаков с типами и версией.
- **Таксономия (Taxonomy)**: канонические классы проекта и правила сведения к ним подписей
  каждого источника.
- **Разбиение (Split Manifest)**: состав частей train/val/test (захваты, временные интервалы),
  параметры, контрольная сумма.
- **Отчёт о качестве (Data Quality Report)**: сводки сопоставления, распределения классов,
  результаты проверки на артефакты, сверка с v1.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Полная обработка обоих датасетов (93 захвата, ~100 ГБ) завершается без ручного
  вмешательства; пиковое потребление памяти процессом вместе с дочерними не превышает 12 ГБ
  (из 16 ГБ машины — остальное нужно системе) и записывается автоматически.
- **SC-002**: После принудительного прерывания повторный запуск завершает обработку, повторно
  не обрабатывая ни одного завершённого захвата.
- **SC-003**: Два прогона на одних входах дают идентичные наборы (совпадение контрольных сумм
  содержимого) и идентичное разбиение.
- **SC-004**: Доля сопоставления с разметкой по каждому сценарию CTU-13 не ниже, чем в v1
  (0.65–0.995 по сценариям), либо снижение объяснено в отчёте.
- **SC-005**: По каждому захвату число потоков отличается от v1 не более чем на 5%
  (относительно), а доля каждого класса — не более чем на 5 процентных пунктов, либо
  расхождение объяснено.
- **SC-006**: Автоматическая проверка подтверждает 0 потоков, попавших в две части разбиения;
  для разбиений по времени (UNSW) — 0 пересечений временных интервалов частей внутри дня;
  для разбиения по сценариям (CTU-13) — каждый сценарий целиком в одной части.
- **SC-007**: Для одного и того же PCAP признаки в режимах «с разметкой» и «без разметки»
  совпадают на 100%.
- **SC-008**: Отчёт открывается как самостоятельный документ и позволяет человеку без доступа
  к коду за 5 минут ответить: сколько данных, какие классы, где дисбаланс и какие признаки
  опасны.

## Assumptions

- Датасеты уже скачаны: UNSW-NB15 (80 PCAP и CSV ground truth) в `A:\datasets\UNSW-NB15`,
  CTU-13 (13 сценариев с .binetflow) в `A:\datasets\CTU-13`.
- Метки UNSW-NB15: поток, не попавший ни в один диапазон атаки, — фон генератора трафика
  и считается benign (проверено в v1).
- Опубликованные PCAP CTU-13 содержат в основном трафик ботнета (в v1 normal ≈ 0, background
