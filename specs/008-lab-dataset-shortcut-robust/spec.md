# Feature Specification: Содержательный набор стенда, устойчивый к «ярлыкам»

**Feature Branch**: `008-lab-dataset-shortcut-robust`

**Created**: 2026-10-13

**Status**: Draft

**Input**: User description: "008 — собрать на лабораторном стенде 006 содержательный размеченный набор: несколько
сценариев атак и «сложная норма», разные инструменты и источники на каждый класс, повторы с разными
параметрами, норма отдельным клиентом и с хоста атакующего. Включить меры против обучения по «ярлыкам»
(почерк инструмента, хост, время): разнообразие инструментов и источников, оценка с исключением инструмента
и хоста, аудит признаков. Все развилки решать вариантами по умолчанию, фиксировать их в Assumptions."

## Контекст

После 006 на стенде есть живой сенсор и сценарии, но собранный набор одноклассовый: один источник,
один сценарий за сеанс, нет отдельного клиента с нормой (1042 потока, поймано 0,1%). Такой набор
не годится ни для содержательной оценки переноса, ни для обучения: модель способна выучить не
поведение атаки, а «почерк» инструмента или особенности хоста, потому что на стенде мало машин и
один набор инструментов.

Фича 008 расширяет стенд и процедуру сбора так, чтобы набор был содержательным и чтобы величину
эффекта «ярлыков» можно было **измерить**, а не только объявить. Итог: версия набора
`data/lab/<версия>` с несколькими классами атак, сложной нормой и повторами; отчёт оценки,
в котором перенос с чужих датасетов и поимка атак показаны вместе с оценкой при исключении
инструмента и хоста и аудитом признаков.

Термины: **сценарий** — именованная версионированная последовательность действий на атакующей
машине (из 006); **вариант** — сценарий с конкретным инструментом и набором параметров;
**источник** — машина или адрес, с которого идёт трафик; **ярлык** — признак, который отделяет
класс по причинам, не связанным с поведением атаки (инструмент, ОС хоста, время, скорость,
конфигурация стека); **повтор** — отдельный запуск варианта; **сложная норма** — легитимный
трафик, внешне похожий на атаку (мониторинг, нагрузочный тест, административное сканирование);
**неизвестная атака (аналог «нулевого дня»)** — класс или вариант, которых модель не видела при
обучении и выборе порога; в лабораторной постановке это класс, исключённый из обучения (протокол
«исключение класса»), либо сценарий «вне таксономии», либо вариант, зарезервированный только для
теста. Настоящая уязвимость нулевого дня моделируется только в этом смысле: набор проверяет
реакцию на непохожее на виденное, а не на конкретные неизвестные уязвимости.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Набор сценариев с разными инструментами и источниками (Priority: P1)

Владелец получает расширенный набор версионированных сценариев: для каждого класса атаки есть
несколько инструментов, а запуски идут с нескольких адресов и ОС; добавлена сложная норма и
второй клиент с нормой.

**Why this priority**: без разнообразия набор учит почерку, а не поведению; все остальные истории
зависят от него.

**Independent Test**: команда списка сценариев перечисляет классы, инструменты, источники и
параметры; для каждого класса не меньше двух инструментов; команда проверки готовности подтверждает
наличие всех инструментов и адресов.

**Acceptance Scenarios**:

1. **Given** стенд 006, **When** владелец выполняет шаги установки 008, **Then** добавлены второй
   клиент с нормой, дополнительные адреса атакующей машины (алиасы), недостающие инструменты, и
   команда проверки стенда по-прежнему подтверждает изоляцию.
2. **Given** конфиг сценариев, **When** выводится список, **Then** по каждому классу указаны
   инструменты и допустимые диапазоны параметров.

---

### User Story 2 - Автоматический сбор набора по расписанию с повторами (Priority: P2)

Владелец запускает одну команду, и планировщик сам прогоняет все варианты в случайном порядке с
паузами, повторами и разными параметрами, одновременно ведёт сложную норму, пишет журнал и записи
захвата, а по окончании выдаёт сводку.

**Why this priority**: набор нужного объёма вручную не собрать, а случайный порядок и перемешивание
нужны для устойчивости к ярлыкам по времени.

**Independent Test**: запуск на сокращённом плане завершается без вмешательства; журнал содержит
все запуски с параметрами, паузами и источниками; прерывание и повторный запуск продолжают план.

**Acceptance Scenarios**:

1. **Given** план сбора, **When** он запущен, **Then** варианты выполняются в случайном (по
   сиду) порядке с паузой между запусками не меньше заданной и с нормой от нескольких хостов.
2. **Given** сбой посреди сбора, **When** команда запущена снова, **Then** выполненные запуски не
   повторяются, остальные продолжаются.
3. **Given** запуск, цели которого вне стенда, **When** планировщик его проверяет, **Then**
   запуск отклоняется до первого пакета (как FR-013 006).

---

### User Story 3 - Разметка по журналу и контроль качества набора (Priority: P3)

Из записи захвата и журнала строится версионированный набор потоков с метками «класс / вариант /
источник / запуск / норма» и отчётом качества: доля неоднозначных потоков, объём по классам, по
инструментам, по источникам, баланс по времени.

**Why this priority**: качество набора определяет, чему вообще можно верить.

**Independent Test**: сборка из журнала и записи даёт набор и отчёт; доля неоднозначных не больше
порога; для каждого класса есть минимум потоков в каждой части разбиения.

**Acceptance Scenarios**:

1. **Given** журнал и запись, **When** строится набор, **Then** каждый поток получает метки
   класса, варианта (инструмент и параметры), источника и запуска либо метку «неоднозначный».
2. **Given** построенный набор, **When** запрашивается отчёт, **Then** он показывает, нет ли
   классов, целиком связанных с одним источником, одним инструментом или одним временем суток.

---

### User Story 4 - Оценка с исключением инструмента и хоста и аудит ярлыков (Priority: P4)

Владелец получает отчёт, показывающий, насколько качество модели держится на атаках, которые она
«не видела» по инструменту или по хосту, и какие признаки выдают ярлыки.

**Why this priority**: именно это превращает набор из «сбора трафика» в научно полезный.

**Independent Test**: отчёт содержит для каждого класса таблицу «обучение на инструментах A,
тест на инструменте B» и «обучение на источнике X, тест на источнике Y», перестановочную важность
и одиночные признаки; запуск воспроизводим по сиду.

**Acceptance Scenarios**:

1. **Given** набор с ≥ 2 инструментами на класс, **When** запускается оценка «исключение
   инструмента», **Then** для каждого инструмента класса считается поимка моделью, обученной на
   остальных, и разность с поимкой при инструменте в обучении.
2. **Given** набор с ≥ 2 источниками, **When** запускается оценка «исключение хоста», **Then**
   поимка считается на источнике, исключённом из обучения.
3. **Given** построенная модель, **When** запускается аудит, **Then** перечислены признаки,
   у которых одиночная полнота выше порога, и показано, как меняется качество без них.

---

### User Story 5 - Перенос и открытое множество на стенде (Priority: P5)

Владелец оценивает модели, обученные на чужих датасетах (UNSW-NB15 и другие), на новом наборе и
запускает протокол «исключение класса» на классах стенда.

**Why this priority**: это проверка того, что результаты исследования не специфичны для двух
чужих датасетов.

**Independent Test**: отчёт содержит поимку по классам при заданной доле ложных срабатываний,
рассчитанной по норме набора, доверительные интервалы и разбор непойманных классов.

**Acceptance Scenarios**:

1. **Given** модель и набор, **When** запускается оценка, **Then** отчёт содержит полноту по
   классам и инструментам при долях ложных срабатываний 0,1%, 1% и 5%.
2. **Given** набор, **When** запускается протокол «исключение класса», **Then** результаты
   записываются в эксперименты и журнал вместе с версией набора.

---

### Edge Cases

- Инструмент отсутствует в репозиториях ОС: сценарий помечается недоступным, набор строится без
  него, отчёт показывает пропуск.
- Класс получил меньше минимума потоков в части: оценка по нему помечается ненадёжной (как в 007).
- Один инструмент даёт на порядок больше потоков, чем другие: отчёт показывает долю инструментов,
  оценка использует равные веса.
- Две атаки одновременно: потоки размечаются по источнику и цели; неразличимые — «неоднозначный».
- Часы машин расходятся: границы запусков определяются по часам сенсора (как в 006).
- Загрязнение нормы: если «норма» с хоста атакующего содержит действия, схожие с атакой, они
  помечаются сложной нормой, а не сценарием.

## Requirements *(mandatory)*

### Functional Requirements

**Состав набора**

- **FR-001**: Для каждого класса атаки набор ДОЛЖЕН содержать не менее **двух различных
  инструментов** (например, сканирование: nmap и masscan; перебор паролей: hydra и medusa; медленные DoS:
  slowhttptest и скрипт slowloris; веб-фаззинг: ffuf и gobuster), а минимальный состав классов —
  сканирование портов, веб-фаззинг, перебор паролей SSH, медленный DoS, затопление с ограничением
  скорости, эксплуатация простого уязвимого веб-приложения, периодические «маячки» одному адресу.
- **FR-002**: Запуски ДОЛЖНЫ идти не менее чем с **двух адресов** атакующей стороны (алиасы адреса,
  второй хост), а не менее чем часть вариантов — с хоста клиента нормы; ОС источников ДОЛЖНЫ
  различаться хотя бы в одной паре (разные образы или настройки сетевого стека).
- **FR-003**: Норму ДОЛЖНЫ порождать **как минимум два хоста**, включая атакующий хост между атаками,
  так что адрес источника не определяет класс; доля трафика нормы с каждого адреса фиксируется
  и показывается в отчёте качества.
- **FR-004**: В набор ДОЛЖНА входить **сложная норма** (мониторинг, нагрузочный тест веб-службы,
  административное сканирование с меткой нормы), чтобы ложные срабатывания измерялись на трафике,
  похожем на атаку.
- **FR-005**: Каждый вариант ДОЛЖЕН иметь не менее **10 повторов** с разными параметрами
  (скорость, размеры, число потоков, диапазоны, словари), причём часть значений параметров
  ДОЛЖНА встречаться только в тестовых повторах.

**Сбор**

- **FR-006**: Планировщик ДОЛЖЕН выполнять варианты в порядке, определяемом сидом, с паузой между
  запусками не меньше таймаута простоя экстрактора плюс запас 30 с, вести журнал каждого запуска
  (как FR-014 006: сценарий, инструмент, параметры, источник, цели, время по часам сенсора, итог)
  и продолжать план после прерывания без повторения выполненного.
- **FR-007**: Не менее трети запусков ДОЛЖНА идти одновременно с нормой, не менее двух запусков —
  с двумя одновременными атаками; время суток запусков (по часам стенда) ДОЛЖНО быть перемешано
  между классами.
- **FR-008**: Планировщик ДОЛЖЕН соблюдать FR-002, FR-005, FR-013 006 (цели только в сети стенда),
  потребовать подтверждения перед стартом длительного плана и показывать оценку времени и объёма.

**Набор и разметка**

- **FR-009**: Набор ДОЛЖЕН строиться из записи и журнала тем же экстрактором и схемой, что 001/006
  (train = serve), версионироваться (`data/lab/<версия>`), содержать метки класса, варианта
  (инструмент, параметры), источника, запуска и признак «сложная норма»; адреса и порты НЕ
  попадают в признаки модели, но остаются в метаданных для аудита.
- **FR-010**: Доля неоднозначных потоков ДОЛЖНА быть не более 5% потоков сценариев; потоки в
  паузах и на стыке запусков размечаются как неоднозначные, а не относятся к ближайшему сценарию.
- **FR-011**: Разбиение набора ДОЛЖНО быть **по времени и по повторам** (ранние повторы — обучение,
  средние — валидация, поздние — тест, с зазором), с не меньше чем 100 потоками каждого класса
  в тесте; классы с меньшим числом потоков помечаются ненадёжными.
- **FR-012**: Отчёт качества набора ДОЛЖЕН показывать для каждого класса: число потоков по
  инструментам, источникам, частям разбиения и времени суток, и ПРЕДУПРЕЖДАТЬ, если класс
  целиком связан с одним инструментом, одним источником или одним временем суток.

**Оценка и меры против ярлыков**

- **FR-013**: Оценка «исключение инструмента»: для каждого класса и инструмента модель обучается
  без этого инструмента (но с остальными инструментами класса и всеми остальными классами) и
  оценивается на исключённом; результат сравнивается с оценкой при инструменте в обучении.
- **FR-014**: Оценка «исключение хоста»: модель обучается без данных одного источника (атак и
  нормы) и оценивается на нём; результат сравнивается с оценкой по остальным источникам.
- **FR-015**: Аудит ярлыков ДОЛЖЕН включать перестановочную важность признаков, полноту по одиночным
  признакам, а также повторную оценку без признаков, зависящих от окружения (например, поля
  стека: окно TCP, TTL, если они есть в схеме); результат ДОЛЖЕН отражаться в вердикте набора
  (`clean` / `suspect`) с указанием признаков (как артефактный аудит 001/007).
- **FR-016**: Оценка переноса и протокол «исключение класса» ДОЛЖНЫ повторять протоколы публикаций
  (порог по норме валидации, доли ложных срабатываний 0,1%/1%/5%, полнота по классам с интервалом
  Уилсона, парные сравнения по классам) и записываться в эксперименты и журнал.
- **FR-017**: Все оценки ДОЛЖНЫ выполняться с несколькими сидами (не меньше трёх) и показывать
  разброс; результат по классам с меньше чем 100 потоками в тесте не входит в средние.

**Общие**

- **FR-018**: Действия на машине владельца (создание машин, скачивание, выделение ресурсов) ДОЛЖНЫ
  выполняться только по подтверждению, как FR-002 006; изоляция сети стенда не нарушается.
- **FR-019**: Фича НЕ ДОЛЖНА менять код и модели 001–007, за исключением расширения конфигов
  сценариев и стенда; все тесты предыдущих фич ДОЛЖНЫ проходить.
- **FR-020**: `dvc push` набора выполняется только с явного разрешения владельца (как T059 006).

**Неизвестные атаки (аналог «нулевого дня»)**

- **FR-021**: Часть классов и вариантов набора ДОЛЖНА быть **зарезервирована как неизвестные**: не участвует в обучении и выборе порога, присутствует только в тесте. Резерв определяется конфигом и включает не менее одного класса «вне таксономии» (например, перебор паролей SSH, «маячки») и не менее одного варианта (инструмента или набора параметров) известного класса.
- **FR-022**: Отчёт оценки ДОЛЖЕН содержать раздел «неизвестные атаки», где для каждого резервного класса и варианта показаны полнота при долях ложных срабатываний 0,1% / 1% / 5%, разность с контролем (класс известен) и разбор: на какие известные классы или на норму модель его относит (как «на что похожи пропущенные» в публикациях). Для оценки применяются все способы оценки неизвестного, доступные в проекте, включая объединение оценок.
- **FR-023**: Отчёт и документация ДОЛЖНЫ явно оговаривать границу применимости: результат относится к «неизвестному в рамках таксономии и стенда», а не к реальным уязвимостям нулевого дня; формулировка «обнаружение нулевого дня» без этой оговорки не используется.

### Key Entities

- **Вариант сценария**: класс, инструмент, параметры, допустимые источники, ограничения скорости и
  длительности.
- **План сбора**: сид, список вариантов с повторами и параметрами, паузы, норма, оценка времени.
- **Запуск**: идентификатор, вариант, источник, цели, время начала и конца, итог.
- **Набор стенда (версия)**: потоки с метками класса, варианта, источника, запуска, части разбиения;
  отчёт качества; вердикт аудита.
- **Отчёт оценки**: полнота по классам, инструментам, источникам; перенос; исключение инструмента
  и хоста; аудит ярлыков.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Набор содержит не менее 7 классов атак, не менее двух инструментов на класс и не
  менее двух адресов источника атак; норма поступает не менее чем с двух хостов.
- **SC-002**: Набор содержит не менее 10 повторов каждого варианта, не менее 100 потоков каждого
  класса в тесте и не менее 20 000 нормальных потоков в тесте (для измерения 0,1% ложных
  срабатываний); доля неоднозначных потоков — не более 5%.
- **SC-003**: Сбор проходит без вмешательства владельца (кроме подтверждения старта) и
  завершается за время, указанное планировщиком, с отклонением не более 25%.
- **SC-004**: Отчёт качества не содержит классов, целиком связанных с одним инструментом, одним
  источником или одним временем суток; иначе набор получает вердикт `suspect` с перечнем.
- **SC-005**: Для каждого класса отчёт оценки показывает разность «инструмент в обучении» и
  «инструмент исключён» и разность «источник в обучении» и «источник исключён» с интервалами.
- **SC-006**: Аудит признаков даёт вердикт и список признаков; повторная оценка без них показана.
- **SC-007**: Оценка переноса и протокол «исключение класса» воспроизводятся по сиду и записаны
  в эксперименты и журнал с версией набора.
- **SC-008**: Набор содержит не менее одного резервного класса «вне таксономии» и не менее одного
  резервного варианта известного класса, оба не использованы в обучении и выборе порога; для них
  отчёт даёт полноту, разность с контролем и разбор.
- **SC-009**: Все тесты 001–007 проходят; пакетный `soc run`, проигрыватели 005 и живая цепочка
  006 работают как раньше.

## Assumptions

- Стенд, сенсор и сценарии берутся из 006; изоляция и скрипты `stand/hyperv/*.ps1` не меняются,
  кроме добавления машины клиента нормы и алиасов адреса атакующего.
- Инструменты сценариев ставятся из штатных репозиториев ОС на время установки (временный доступ в
  интернет по FR-002 006), после чего доступ отключается; недостающие инструменты не блокируют
  фичу (см. Edge Cases).
- Объём сбора и состав классов — минимальные, задаваемые конфигом; их можно увеличить, не меняя
  кода; 10–12 часов записи — ориентир, не требование.
- Метки класса берутся из таксономии UNSW-NB15 там, где соответствие очевидно (scan →
  reconnaissance, web fuzz → fuzzers, dos → dos, exploit → exploits), иначе класс помечается
  «вне таксономии» и входит в оценку открытого множества.
- Неизвестные атаки моделируются резервом классов и вариантов (FR-021); реальные уязвимости
  нулевого дня и эксплойты без публичных аналогов в набор не входят.
- Оценка переноса использует модели 001–007 как есть; новые модели в этой фиче не строятся.
- Все атаки — только в изолированной сети стенда; публикация набора вне владельца не
  предполагается (G8 плана публикаций).

## Out of Scope

- Новые модели (CNN+LSTM и т.п.) и переобучение на наборе стенда.
- Реальный трафик организации и сторонние публичные датасеты (подключаются в других фичах).
- Изменение потребителя, брокера, консоли и схемы признаков.
- Автоматическое исправление выявленных ярлыков (фича только измеряет и сообщает).
