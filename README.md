# ML-SIEM v2

SIEM/SOAR с ML-детекцией сетевых атак. Разработка идёт вертикальными срезами по
спецификациям в `specs/`; журнал решений — `docs/JOURNAL.md`.

## Быстрый старт

```
uv sync --extra dev
uv run pytest
uv run mlsiem data flows --dataset ctu13 --capture 7
```

Подробнее о пайплайне данных — `specs/001-nids-data-pipeline/quickstart.md`.

## Детекция, инциденты и API (фича 002)

Сквозная цепочка поверх данных фичи 001: детектор → алерты → инциденты → предложения
плейбуков → API аналитика. Реагирование только симулируется — никаких реальных сетевых действий.

```
uv run mlsiem detect train                              # эксперимент logreg vs lgbm, выбор детектора
uv run dvc repro train_detector                         # то же как стадия DVC
uv run mlsiem soc run --split unsw_time --part test     # прогон test через цепочку (--limit N — первые N потоков)
uv run mlsiem soc run --pcap FILE.pcap                  # новый неразмеченный PCAP тем же путём
uv run mlsiem soc status                                # какие прогоны лежат в хранилище
uv run mlsiem soc serve                                 # консоль http://127.0.0.1:8000/ и API /api/v1
```

Где что лежит:

- `models/detector/` — артефакт детектора (`model.joblib`, `model_card.json`, `experiment.json`),
  выход DVC; отчёт эксперимента — `reports/detector_experiment.md`;
- `var/soc.db` — SQLite с прогонами, алертами, инцидентами, действиями и аудит-журналом;
  `var/runs/<run_id>/` — вердикты всех потоков прогона (и `flows.parquet` для PCAP).
  `var/` — рабочее состояние аналитика, ни в git, ни в DVC;
- MLflow: метаданные в `mlflow.db`, файлы runs в `mlruns/` (оба вне git).
  Посмотреть: `uv run mlflow ui --backend-store-uri sqlite:///mlflow.db`;
- документация API (Swagger) — `http://127.0.0.1:8000/docs` при запущенном `soc serve`.
  Изменяющие запросы требуют заголовок `X-Analyst: <имя латиницей>`.

Конфиги — `configs/detect.yaml` (кандидаты, правило выбора, сид) и `configs/soc.yaml`
(окно группировки, серьёзность, защищённые адреса, правила плейбуков). Сценарии проверки —
`specs/002-detection-incident-chain/quickstart.md`.

## Консоль аналитика SOC (фича 003)

Веб-консоль поверх цепочки 002: панель прогона, список инцидентов с фильтрами и сортировкой,
карточка (алерты, вероятности детектора, гистограмма, хронология, аудит), решения аналитика
и журнал аудита. Серверные страницы на Jinja2 + htmx 2 (файл лежит в пакете, без сборки
и CDN) — консоль работает без интернета, основные страницы читаются и без JavaScript.

```
uv run mlsiem soc serve        # консоль http://127.0.0.1:8000/, API http://127.0.0.1:8000/api/v1
```

- **Одна команда, один порт**: консоль и API 002 в одном процессе; слушает только 127.0.0.1.
  При первом запуске база 002 автоматически переводится на схему 2 (поле «ответственный»,
  новое событие аудита) — одной транзакцией, все записи аудита сохраняются как есть.
- **Представиться**: кнопка «представиться» в шапке — имя (можно кириллицей) запоминается
  в браузере и подписывает каждое решение в журнале. Пароля нет: это подпись, а не вход.
- **Решения** идут через те же правила, что API 002: допустимые переходы статусов, резолюция
  при закрытии, подтверждение действия после явного вопроса (выполнение только симулируется),
  защита от одновременных правок. Если решает не ответственный — консоль предупреждает,
  а аудит отмечает `by_non_assignee`.
- **Метки «подозрительный источник»** — подсказка, а не решение: источник из сети жертв или
  фона (`networks` в `configs/soc.yaml`) или адрес, который сам бывает целью в других
  инцидентах прогона (признак ответного направления). Серьёзность и действие метка не меняет;
  есть фильтр «только/скрыть подозрительные».
- **Живое обновление**: панель, список и баннер «появился новый прогон» опрашивают сервер раз
  в `ui.refresh_seconds` (10 с) и не трогают формы; при недоступности сервера появляется
  полоса «данные могут быть устаревшими».
- **Защита**: изменяющие запросы консоли принимаются только со страниц самой консоли
  (проверка `Origin`/`Sec-Fetch-Site` + подписанный токен формы), чужие — 403 и запись
  в лог; строгая CSP без inline-скриптов; все данные выводятся экранированными.

Настройки — разделы `networks` и `ui` в `configs/soc.yaml`. htmx: версия и SHA-256 —
`src/mlsiem/ui/static/vendor/README.md`. Сценарии проверки —
`specs/003-soc-console-ui/quickstart.md`.

## Эксперты-детекторы и мета-слой (фича 004)

К классификатору 002 добавлен второй эксперт — детектор аномалий, обученный только на норме
(Isolation Forest против автокодировщика), и мета-слой (два правила без обучения и стекинг).
Эксперимент честно решает, идёт ли ансамбль в цепочку: только по val, с экспериментом
«скрытый класс» и аудитом артефактов. Цепочка группирует инциденты по атакующей стороне
(ответные потоки «сервер → клиент» больше не дают «атак с адресов жертв»).

```
uv run mlsiem detect ensemble                           # эксперимент 004 → models/ensemble, отчёт
uv run dvc repro train_ensemble                         # то же как стадия DVC
uv run mlsiem soc run --split unsw_time --part test     # модель: models/ensemble, если обучен,
                                                        #   иначе models/detector (--model DIR)
uv run mlsiem soc review-sources --run ID --after ID    # разбор инцидентов с адресов жертв/фона
```

- `--model DIR` — каталог ансамбля или детектора 002; `--detector` — прежнее имя опции.
- `models/experts/anomaly/` — эксперт аномалий; `models/ensemble/` — карточка ансамбля
  (выбранный вариант и **какое условие** выполнено), `experiment.json`; отчёт —
  `reports/ensemble_experiment.md`. Если ансамбль не прошёл правило FR-010, в карточке
  `single:classifier` и цепочка работает одиночным классификатором.
- Класс `anomaly` («аномалия (класс неизвестен)») — сработал только детектор аномалий;
  для него всегда предлагается только ручной разбор (правило + страховка в коде).
- В консоли: блок «Эксперты» в деталях алерта (объяснение, скоры и пороги экспертов),
  «Кто поднял алерты» в карточке, значок «ответный» у перевёрнутых потоков. Старые прогоны
  открываются с пометкой «до ансамбля»; база мигрирует до схемы 3 сама.
- `grouping.direction` в `configs/soc.yaml`: `auto` — атакующая сторона по TCP-флагам и портам
  потока, `as_is` — как в 002.

Конфиг эксперимента — `configs/ensemble.yaml`. Сценарии проверки —
`specs/004-detection-experts-ensemble/quickstart.md`.


## Потоковая обработка через Kafka (фича 005)

Цепочка 002–004 стала потоковой: потоки идут сообщениями через Apache Kafka (KRaft, один
узел) на Linux-машине Hyper-V `mlsiem-broker` в служебной сети `mlsiem-mgmt`; потребитель на
хосте считает вердикты той же моделью, группирует **инкрементально** (со слиянием, результат
совпадает с пакетным `soc run`) и пишет пачку одной транзакцией SQLite — позиция брокеру
подтверждается только после записи. Docker и WSL2 не нужны.

```
uv run mlsiem stand seed-iso                              # seed-ISO автоустановки (только файл)
uv run mlsiem stand check                                 # брокер, топики, изоляция сети стенда
uv run mlsiem stream consume [--model DIR] [--once]       # онлайн-цепочка (Ctrl+C — доделать пачку)
uv run mlsiem stream replay --split unsw_time --part test --speed 60   # или --speed max, --pcap F
uv run mlsiem stream status                               # скорость, отставание, задержка p50/p95
uv run mlsiem stream compare --session ID --batch ID      # эквивалентность с пакетным прогоном
uv run mlsiem stream close --session ID                   # завершить сеанс без отметки end
```

- Стенд поднимают скрипты `stand/hyperv/*.ps1` (от администратора; каждый меняющий шаг —
  с подтверждением, `-WhatIf` — только план) — пошагово в `stand/hyperv/README.md`.
  Шаблоны автоустановки Ubuntu 24.04 и Kafka — `stand/broker/`.
- Все параметры — `configs/stream.yaml` (адрес брокера, топики, пачки, допустимое опоздание,
  аренда, ресурсы машины, версия и SHA-512 Kafka).
- Сеанс — прогон с режимом «поток» и статусом «идёт / остановлен / завершён»; вердикты —
  `var/runs/<сеанс>/verdicts/part-*.parquet`. База мигрирует до схемы 4 сама (сделайте копию
  `var/soc.db` перед первым запуском).
- В консоли: значок «поток» у сеанса, блок «Поток» на панели, пометки «новые алерты после
  решения» и «объединён с …», фильтры по ним; `GET /api/v1/stream/status`.
- Быстрые тесты идут на брокере-заглушке в памяти; тесты на настоящем брокере —
  `uv run pytest -m stand` (после подъёма стенда).

Сценарии проверки — `specs/005-kafka-streaming-chain/quickstart.md`.


## Детектор на окнах потоков (фича 007)

Кроме вердикта по каждому потоку, цепочка может смотреть на **минуту трафика одного
атакующего целиком** («окно»: атакующая сторона × 60 с). Эксперимент честно сравнивает три
участника на окнах `unsw_time`: бустинг на сводных признаках окна, двунаправленный GRU на
последовательности потоков окна и текущую модель 002/004, сведённую к окну максимумом. Выбор —
только по val (macro PR-AUC надёжных классов, прирост ≥ 0.01 в два шага), принять модель в
цепочку может только аудит на артефакты.

```
uv sync --extra dev --extra nn                                 # PyTorch (cu128) — для нейросети
uv run mlsiem detect windows [--device auto|cuda|cpu] [--skip-nn]   # эксперимент → models/windows
uv run mlsiem detect windows-audit                             # артефакты, перенос → accepted
uv run mlsiem detect windows-errors [--part test]              # что ловят окна и чего нет
uv run dvc repro --single-item train_windows                   # эксперимент + аудит стадией DVC
uv run mlsiem soc run --split unsw_time --part test --windows auto   # auto | off | force
uv run mlsiem stream consume --windows auto                    # то же онлайн
```

- `models/windows/`: `window_card.json` (вид, версия, порог, параметры окна и **решение**:
  прошёл ли выбор, вердикт аудита, итоговое `accepted`), модель, `experiment.json`. Победитель
  сохраняется всегда, даже при отрицательном результате. Отчёты —
  `reports/windows_experiment.md`, `reports/windows_audit.md`, `reports/windows_errors.md`.
- Как читать решение: `passed_selection` — окна дали прирост над текущей моделью на val;
  `audit_verdict: clean` — без подозрительных признаков качество не падает на 0.10 и больше;
  `accepted = passed_selection И clean`. Цепочка в режиме `auto` включает эксперт окон только
  при `accepted: true`; `force` — включить и непринятую модель (с предупреждением), `off` —
  как в 005.
- Алерт окна — отдельная строка алертов (`kind: window`, описание окна в `window`), он
  группируется в инциденты вместе с алертами потоков. В консоли: метка «окно», переключатель
  «все / потоки / окна», раскрывающийся блок окна (интервал, цели, порты, подозрительные
  потоки, влиятельные признаки), значок и фильтр в списке, панель «эксперт окон», блок «Окна»
  у онлайн-сеанса. API — `kind`, `window`, `?kind=`, `n_window_alerts`, `has_window_alerts`,
  `windows` у прогона. База мигрирует до схемы 5 сама (сделайте копию `var/soc.db`).
- `--single-item` у `dvc repro` обязателен: без него DVC сначала пересобирает вышестоящие
  стадии, а `train_detector` зависит от всего `src/mlsiem/detect`. Любая правка там — и DVC
  удалит и переобучит детектор 002 (и ансамбль 004), сменив их версии под всеми прогонами в
  базе. Так 2026-09-26 прерванный repro оставил проект без `models/detector`.
- Без PyTorch работает всё, кроме обучения нейросети: `--skip-nn` сравнивает только бустинг и
  текущую модель. Тесты нейросети — `uv run pytest -m nn`.

Конфиг эксперимента — `configs/windows.yaml`. Сценарии проверки —
`specs/007-flow-window-detector/quickstart.md`.

## Лабораторный стенд и живой сенсор (фича 006)

Поверх брокера и сетей 005 на Hyper-V поднимаются две машины в сети стенда `mlsiem-lab`
(Private): **жертва** `10.88.0.20` (web/SSH/FTP/DNS) и **атакующий** `10.88.0.30` (nmap, ffuf,
hydra, slowhttptest, tcpreplay). **Живой сенсор** на брокерной машине принимает зеркало портов
`mlsiem-lab` и тем же экстрактором nfstream 001 превращает трафик стенда в потоки, отправляя их
в брокер как источник `sensor:live`. Дальше работает готовая онлайн-цепочка 005. Сквозной
результат: `mlsiem lab demo` → через минуты инцидент в консоли с атакующим адресом стенда.

```
uv run mlsiem stand seed-iso --role victim|attacker        # seed-ISO машины стенда (только файл)
uv run mlsiem stream sensor start [--iface eth1]           # живой сенсор → брокер (sensor:live)
uv run mlsiem stream sensor status | stop                  # показатели сенсора; завершить сеанс
uv run mlsiem lab scenario list                            # сценарии из конфига
uv run mlsiem lab scenario run <имя> [--version V]         # запуск на атакующей (через канал)
uv run mlsiem lab normal start | stop                      # фоновая норма (benign)
uv run mlsiem lab demo                                     # готовность → control_replay → сводка
uv run mlsiem lab report --run <run_uid>                   # отчёт по запуску сценария
uv run mlsiem lab dataset build --pcap … --journal …       # размеченный набор data/lab/<версия>
uv run mlsiem lab evaluate --dataset <версия> [--model DIR] # честная оценка переноса модели
```

- Машины стенда поднимают скрипты `stand/hyperv/40…91-*.ps1` (от администратора, с
  подтверждением, `-WhatIf` — план) — пошагово в `stand/hyperv/README.md`. Шаблоны
  автоустановки ролей — `stand/broker/user-data-{victim,attacker}.yaml.j2`.
- **Изоляция (FR-005):** у машин стенда только сеть `mlsiem-lab`, служебной сети нет; хост
  управляет атакующим по **COM-порту** его ВМ (канал гипервизора, не сеть); сенсор слышит
  стенд через зеркало портов, своего адреса в `mlsiem-lab` не имея; сценарии бьют только по
  целям из `lab.subnet`, иначе запуск отклоняется. Действия SOAR по инцидентам стенда только
  симулируются.
- **train = serve:** сенсор использует тот же `NFStreamer` и `SCHEMA.extractor`, что 001;
  idle/active-таймауты в живом режиме не меняются (поток уходит через ≥ idle_timeout). Буфер
  отправки переживает кратковременную недоступность брокера; потери честно считаются и
  поднимают флаг «с потерями» (виден в `stream sensor status` и на панели консоли).
- **Набор стенда** `data/lab/<версия>/` (DVC, стадия `lab_dataset`) — первый собственный
  размеченный набор (benign/класс/`ambiguous`), не смешивается с UNSW/CTU-13 и не используется
  для обучения в 006. `dvc repro --single-item lab_dataset` обязателен (как `train_windows`).
- **Оценка** берёт модель и порог из артефакта как есть (порог не подбирается на стенде),
  считает PR-AUC macro и «атака/нет», поимку по сценариям, FPR на норме; для непойманного —
  разбор причины (вне таксономии / вне распределения train / потери сенсора); пишет в MLflow
  (эксперимент `lab`) и `docs/JOURNAL.md`. Слабый перенос модели 2015 года на трафик стенда —
  это честная находка, а не сбой; демо держится на контрольном сценарии `control_replay`.
- Быстрые тесты не требуют ВМ и прав админа (захват — запись `tests/fixtures/lab_sample.pcap`,
  брокер — MemoryBroker 005). Живые проверки на поднятом стенде — `uv run pytest -m lab`. База
  мигрирует до схемы 6 сама (сделайте копию `var/soc.db`).

Все параметры стенда — `configs/stream.yaml` (разделы `lab`, `normal`, `scenarios`). Сценарии
проверки — `specs/006-lab-stand-live-sensor/quickstart.md`.
